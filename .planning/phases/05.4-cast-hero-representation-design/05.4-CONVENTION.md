## §2. Shared foundation — the op vocabulary + the named-color palette + the op-granularity disagreement RESOLUTION

This section is the foundation ALL 3 SCs build on. The user requires **internal consistency across SCs**: a SHARED MolAction op vocabulary + a SHARED named-color palette. This section documents both, and resolves the research disagreement on op granularity (the key decision of this plan).

### §2.1 The shared MolAction op vocabulary

The cast / hero representation is authored as `on_enter` MolAction sequences (per `c14/engine.py:163-194` — the engine replays `on_enter` per-action to `molops.apply`, the 02-04 contract). The op vocabulary is:

**EXISTING ops** (per `c14/pymol_layer/molops.py:114-144`, the Phase 3+4 dispatch — one `cmd.*` call per op):
- `hide_all` → `cmd.hide("everything", "all")` (`viewing.py:568`)
- `show` → `cmd.show(rep, sele)` (`viewing.py:491`) — turns ON only
- `show_as` → `cmd.show_as(rep, sele)` (`viewing.py:528`) — atomic ON + OFF (per-atom scoping, empirically confirmed RESEARCH-api §A.6)
- `select_focus` → `cmd.select(name, sele)` (`selecting.py:48`) — named persistent selection
- `zoom` → `cmd.zoom(sele)` (`viewing.py:65`)
- `color` → `cmd.color(color, sele)` (`viewing.py:1858`)
- `load` → delegates to `AssetManager` (fetch_pubchem / fetch_pdb / load_bundled per `args["source"]`)
- `delete` → `cmd.delete(target)` (`commanding.py:496`)

Plus the Phase 4 delegated ops (`edit` / `restore` / `protonate`) and the Phase 5.3 deferred `align` op (`05.3-CONVENTION.md §6`, dispatch lands in Phase 6).

**3 NEW ops this convention introduces** — all peer primitives wrapping ONE `cmd.*` call each (mirrors how `show` / `show_as` / `color` / `zoom` are each one `cmd.*` call; NO composite super-op):

1. **`op="set_color"`** — define a named color via `cmd.set_color(name, rgb)` (`viewing.py:2107`). Idempotent overwrite (re-running on `on_enter` replay / re-init is safe — `_invalidate_color_sc` refreshes the cache, `viewing.py:2161`). Auto-detects 0-1 vs 0-255 RGB range (`viewing.py:2155-2156`).

   ```jsonc
   {"op": "set_color", "target": null,
    "args": {"name": "hero_gold",            // the named color to define (idempotent overwrite)
             "rgb": [0.90, 0.62, 0.0]}}       // [r,g,b] in 0.0-1.0 OR 0-255 (auto-detected)
   ```

2. **`op="label"`** — set a text label via `cmd.label(sele, expression)` (`viewing.py:1332`). The dispatch wraps `text` as the quoted-string expression `'"C14"'` to avoid the bare-word footgun (RESEARCH-api §F Pitfall 2: a bare `"C14"` would try to evaluate the atom property `C14` and fail; empirically `'"C14"'` → iterate `label`==`'C14'`). `sele` defaults to `target`.

   ```jsonc
   {"op": "label", "target": "hero_atom",
    "args": {"sele": null,                   // optional explicit sele; defaults to target
             "text": "C14"}}                 // the label string (dispatch wraps as '"C14"')
   // clear: {"op":"label","target":"hero_atom","args":{"text":""}}
   ```

3. **`op="set"`** — set a per-atom setting via `cmd.set(name, value, selection)` (`setting.py:183`). Distinct primitive — `sphere_scale` is a per-atom setting that `show_as` / `color` don't cover. A generic `op="set"` (name / value / sele) is reusable beyond `sphere_scale` (future per-atom settings) and stays one-concern-per-op. `sele` defaults to `target`.

   ```jsonc
   {"op": "set", "target": "hero_atom",
    "args": {"name": "sphere_scale",         // the per-atom setting name
             "value": 1.0,                   // the value
             "sele": null}}                  // optional explicit sele; defaults to target
   ```

All 3 new ops are **pure data** — `MolAction(op, target, args)` in `c14/story/model.py:44-48` already supports arbitrary `args` dict keys. **NO model change is needed** — adding `"set_color"` / `"label"` / `"set"` to the documented op list + 3 `elif` branches in `molops.py` is the entire surface. The AST gate holds (`MolAction` is pure data, no pymol import in `c14/story/model.py`; the new ops are string keys + docstring lines).

### §2.2 The op-granularity disagreement RESOLUTION (the key decision)

The two research tracks disagreed on the dispatch granularity:

- **The API researcher** (RESEARCH-pymol-representation-api §E.4) recommends **2 new minimal ops `label` + `set_color` + reuse**, expressing hero-highlight + scene templates as MolAction SEQUENCES. Explicitly rejects a composite super-op (RESEARCH-api §E.3 Option 3 analysis: "one op = many `cmd.*` calls" violates the one-MolAction-one-concern dispatch).
- **The hero-design researcher** (RESEARCH-hero-highlight-design §B + §F Q5) recommends a **single composite `op="hero_highlight"` super-op** encapsulating `set_color` + `show_as spheres` + `set sphere_scale` + `color` + scoped-dim + `label` (6 `cmd.*` calls in one dispatch). Argues it makes `on_enter` readable + encapsulates the footguns + bakes in the colorblind default.

**ADOPTED: the minimal-orthogonal approach — 3 new peer-primitive ops (`set_color`, `label`, `set`), hero-highlight + scene templates expressed as SHORT MolAction sequences, NOT a super-op.**

This mirrors how Phase 5.3 resolved its naming disagreement by adopting the API researcher's recommendation (`05.3-CONVENTION.md §6` — ADOPT `target=mobile, args["reference"]=fixed` over the design researcher's `args.mobile/args.target`). The rationale:

1. **Keeps `molops.py` dispatch minimal and orthogonal.** The existing 02-04 dispatch is one-MolAction-per-`apply` (`molops.py:112-196`); each op is one `elif` wrapping one `cmd.*` call, the same shape as the existing `show` / `color` branches. A super-op would be one op = many `cmd.*` calls (violates the precedent the existing 8 peer-primitive ops establish).

2. **Most headless-testable per-step.** Each MolAction → one `cmd.*` → one post-condition (rep visible via `count_atoms("sele and rep <name>")` / color name round-trip via `get_color_indices` / label text via `iterate label`). A super-op hides intermediate state inside one dispatch, making per-step post-conditions impossible (you could only assert the FINAL state, not that each of the 6 sub-calls fired correctly). This is the RESEARCH-api §E.3 "unit-testable dispatch mapping (MockCmd)" criterion.

3. **Mirrors the 5.3 precedent.** 5.3 added ONE focused op `align` (NOT a composite "wt_reveal" super-op encapsulating `edit`+`load`+`align`+`show_as`+`color`+`zoom`). 5.4 adds 3 focused primitive wrappers because the representation / color / label surface is wider than 5.3's single align surface. 5.3 did NOT add a composite; 5.4 follows the same shape — focused primitives, NOT a super-op.

4. **The `set` op is the 3rd primitive** (justification for going beyond the API researcher's "2 ops"). `sphere_scale` is a per-atom setting that `show_as` / `color` don't cover; `cmd.set(name, value, selection)` (`setting.py:183`) is a distinct primitive from `cmd.show_as` / `cmd.color`. A generic `op="set"` (name / value / sele) is reusable beyond `sphere_scale` (future per-atom settings — e.g. `transparency`, `sphere_transparency`) and stays one-concern-per-op. The API researcher's "2 ops" undershot by one; this convention adopts 3.

**The REJECTED alternative — the `op="hero_highlight"` super-op (recorded for the record):**

The hero-design researcher proposed a single composite super-op encapsulating the 6-call hero-highlight sequence:

```jsonc
// REJECTED alternative (recorded; NOT adopted)
{"op": "hero_highlight", "target": "<hero_obj>",
 "args": {"selector": "<hero_selector>",   // resolves to exactly one carbon (§3.1 rule)
          "label": "C14",                  // the isotope tracking label (NOT the fate)
          "color": "hero_gold",            // colorblind-safe default
          "scale": 1.0,                    // sphere_scale
          "dim": "gray80",                 // scoped to <hero_obj> and not <hero_sele>
          "soul": false}}                  // true for post-CO2-shed nodes (highlight a non-carbon)
```

Its pros (noted): readable `on_enter` (one MolAction vs 6); footgun encapsulation (the label quoted-string + the dim scoping baked in); colorblind default baked in. Its cons (which lose): couples concerns (one op = many `cmd.*` calls); harder per-step testing (only the final state is assertable, not each sub-call); breaks the 5.3 precedent (5.3 did NOT add a composite). The minimal-orthogonal approach achieves the SAME readability by authoring the 6-call sequence as a documented, reusable `on_enter` block (§3.3) — the sequence is the readable unit, NOT a super-op dispatch. **The super-op is REJECTED.**

**Dispatch deferral (mirror 5.3 §6 / §8 Q3).** The 3 new-op `elif` branches + MockCmd unit tests **LAND IN PHASE 6, NOT 5.4.** 5.4 SPECIFIES the op shapes (§2.1) + prototypes `cmd.set_color` / `cmd.label` / `cmd.set` / `cmd.show_as` / `cmd.color` headlessly (direct `cmd.*` in the smokes, like `tools/wt_align_smoke.py` calls `cmd.super` directly per `05.3-CONVENTION.md §6`). This keeps 5.4 a pure design + prototype phase (0 new production-code requirements): it adds NO `elif` to `molops.py`, NO new op to `model.py`'s docstring — only a convention spec + headless smokes that call `cmd.*` directly. The AST gate, the alter gate (SC1, `molops.py:48`), and the existing dispatch are untouched. Flagged as **Open Question OQ-1** (§7) for the Plan 04 checkpoint — the human may override to "add in 5.4" (the 04-05 precedent of add-op+smoke-together); if overridden, Plans 02 / 03 gain tasks to edit `molops.py` + add unit tests.

## §3. SC1 — the C14 hero highlight convention

*(Per RESEARCH-hero-highlight-design §A-§C + RESEARCH-pymol-representation-api §C.)*

The hero highlight is how the player sees "their" carbon atom in any loaded structure. It is an **`on_enter` concern** (fires in the node's `on_enter` MolAction sequence, AFTER the `load` that brings the hero-bearing object into the session — exactly like the 5.3 WT-aligned reveal fires in the branch-node `on_enter`).

### §3.1 The hybrid selection rule (the core question)

*(Per RESEARCH-hero-highlight-design §A.)*

**Adopt hybrid option (iv): each hero-bearing asset carries an explicit `hero_selector` (a PyMOL selection resolving to EXACTLY ONE carbon); single-carbon objects auto-derive the unique C; multi-carbon objects WITHOUT a `hero_selector` FAIL LOUDLY at the human-verify gate (no silent best-guess for real content).**

The "which carbon is the hero" is a **pathway-science claim** (the hero is C1 of glucose *because that's the carbon that enters glycolysis*; C3 of pyruvate *because* C1 + C2 are shed at PDH; etc.) — HIGH-STAKES per-claim, `PROJECT.md` row 109. Silently highlighting the wrong carbon is a fabricated-science risk; the hero-identity is load-bearing for the whole game's narrative.

**The resolution rule (deterministic, re-evaluated each `on_enter`):**

1. If the asset's metadata carries a `hero_selector` → use it (Phase 7-authored per asset; deterministic).
2. Else if the object is a **single-carbon object** (`cmd.count_atoms("<obj> and elem C") == 1`) → the unique carbon IS the hero (auto-derived; deterministic — applies to `hero_atom` and any future single-carbon substrate).
3. Else (multi-carbon object, no `hero_selector`) → **FAIL LOUDLY** at the human-verify gate. No silent best-guess. (The prototype on placeholder structures uses a **known-by-construction** selector — documented, NOT a heuristic.)

The four selection-rule options analyzed (RESEARCH-hero-highlight §A table): (i) by element + name — FRAGILE (names differ across molecules); (ii) per-structure metadata `hero_selector` — DETERMINISTIC + CLEAN (requires Phase 7 authoring); (iii) mark-on-load — the MECHANISM, not the selector source (composes with (ii)); (iv) hybrid — RECOMMENDED (deterministic for authored assets + auto for the trivial single-C case + fail-loud for the ambiguous multi-C case). **Adopted: (iv).**

The `hero_selector` field lives in **asset metadata** (Phase 7-authored per asset, §6.2) OR as an **explicit `hero_highlight`-sequence arg** (for the prototype + for objects where the selector is intrinsic, like the single-atom `hero_atom`). It composes with the existing `{op:load, target:pdb:..., args:{object:...}}` pattern: the `load` MolAction brings the hero-bearing object into the session; the hero-highlight sequence (fired AFTER `load` in the `on_enter`, §3.3) takes the `hero_selector` + applies the highlight.

### §3.2 The 3 structural cases

*(Per RESEARCH-hero-highlight-design §A.)*

The frozen skeleton (`data/story_glucose/*.json`, 55 nodes) defines three structural cases for where the hero carbon lives relative to the loaded object:

| Case | Skeleton example | Loaded object | Where the hero is | Handling |
|------|------------------|---------------|-------------------|----------|
| **(1) Hero-alone** | `intro.preface`, `intro.shell_glucose` | `hero_atom` (single-atom object, `pdb:TBD_HERO_CARBON`) | the object IS the hero | Auto-derive (rule step 2); the highlight applies trivially. |
| **(2) Hero-in-substrate** | `gly.start`, `tca.entry`, `tca.co2_turn1`/`turn2` | `glucose` / substrate (multi-carbon, `pdb:TBD_*`) | ONE carbon (e.g. C1) IN the substrate object | Requires explicit `hero_selector` (rule step 1); e.g. `"glucose and name C1"`. The dim (§3.3 step 5) is scoped to the substrate. |
| **(3) Hero-at-enzyme-cast** | `gly.pfk`, `pyr.pdh`, `tca.citrate_synthase`, `tca.isocitrate_dh`, `etc.complex_iv` | the ENZYME (e.g. `pdb:TBD_*` — placeholder; real PDBs Phase 7) | the hero is in the **SUBSTRATE** — which the skeleton does NOT load at these nodes | 3 sub-options below. |

**Case 3 is the central tension.** At enzyme-cast nodes the loaded structure is the enzyme (a cast member per `spec.md`'s "Protein cast of ~20+ enzymes"); the hero carbon is in the substrate, which the skeleton does NOT load. So the hero is NOT directly highlightable in the loaded enzyme. Three sub-options:

| Sub-option | What it does | Tradeoff |
|-----------|--------------|----------|
| **(3a) Co-load the substrate** | the enzyme-cast node's `on_enter` ALSO loads the substrate as a separate small object (e.g. `load pdb:TBD_FBP → "fbp"`), highlight the hero in it alongside the enzyme | Hero always visible; MORE assets (per-enzyme substrate PDBs / SDFs, Phase 7); the large-enzyme visibility / zoom is a Phase 9 concern (§6.3). |
| **(3b) Suspend the highlight** | the hero is "inside the enzyme's active site" narratively but NOT visually marked; the enzyme is the focus | Simpler, fewer assets; the player LOSES sight of "their" atom at the most dramatic moments (when the enzyme acts on the hero). |
| **(3c) Hybrid (RECOMMENDED)** | co-load the substrate + highlight the hero WHERE the substrate is small enough (pyruvate at PDH, citrate at citrate_synthase, etc.); SUSPEND where co-loading is impractical (huge membrane proteins like `pdb:TBD_COMPLEX_IV`) | Balances visibility vs asset cost; the DECISION is per-node Phase 7 content; the convention specifies the MECHANISM (works whenever a hero-bearing object is loaded — cases 1/2/3a) + the SUSPEND fallback (3b). |

**The convention specifies the MECHANISM** (the highlight applies whenever a hero-bearing object is loaded — cases 1 / 2 / 3a) **+ the SUSPEND fallback** (3b). **Whether to co-load the substrate at a given enzyme-cast node is a Phase 7 content decision** (per-enzyme, per the substrate's size + the pedagogical intent) — mirroring 5.3's OQ-DM2 per-enzyme deferral (`05.3-CONVENTION.md §3`: "the mechanism is always specified; whether it fires is a per-enzyme Phase 7 decision"). The large-enzyme visibility / zoom (when the co-loaded substrate is tiny vs a huge enzyme like `pdb:TBD_COMPLEX_IV`) is **Phase 9** (§6.3).

The 5.4 prototype (Plans 02 / 03) demonstrates case 3a (hero highlighted in a small co-loaded substrate + a placeholder enzyme); the large-enzyme zoom composition is Phase 9.
