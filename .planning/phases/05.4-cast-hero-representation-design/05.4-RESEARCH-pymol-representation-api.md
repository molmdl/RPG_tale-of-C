## Summary

This is the API-facts file for Phase 5.4. Every signature below is read from `tmp/pymol-src/modules/pymol/` (PyMOL 2.5.0 open-source, read-only symlink) and cited `file:line`. The five claims the planner most needs — and which are **empirically confirmed** here via a 45-check headless run (command + raw output in §A.6) — are:

1. **The headless "representation visible" primitive is `count_atoms("<sele> and rep <name>")`.** The `rep <name>` selection keyword selects atoms with that representation enabled (empirically: `count_atoms("mol and name C1 and rep spheres")==1` after `show spheres`; `count_atoms("cast and rep cartoon")==17` after `show_as cartoon` on a 2-residue peptide). `show_as` turns ON the named rep AND turns OFF all others **on the selected atoms only** (per-atom scoping — confirmed: `show_as sticks` on `name C1` left `O1`/`C2` with their existing spheres). `show` turns ON only; `hide` turns OFF. Reps available: `lines, sticks, spheres, dots, surface, mesh, nonbonded, nb_spheres, cartoon, ribbon, labels, slice, ellipsoids, volume` (`viewing.py:51-53`).
2. **A named colorblind-safe color is defined via `cmd.set_color(name, rgb)` and verified via `cmd.iterate(...,"color")` (an int index) + `cmd.get_color_indices()`.** `cmd.set_color("hero_orange", [1.0,0.5,0.0])` (`viewing.py:2107`) auto-detects 0-1 vs 0-255 range. `cmd.color("hero_orange", sele)` (`viewing.py:1858`) applies it. Headlessly, `cmd.iterate(sele, "out.append(color)", space=...)` returns the color as an **integer index**; `cmd.get_color_indices()` (`querying.py:843`) returns a `[(name, index), ...]` list to map index→name (empirically: `hero_orange`→index 5388, round-tripped). `cmd.get_color_tuple(name)` (`querying.py:825`) returns the RGB tuple. No colorblind-safe palette ships built-in — you `set_color` your own named colors from a published palette's RGB (the RGB values are a Phase 7 source/approval decision, not this file's).
3. **The hero is identified by a DETERMINISTIC SELECTION RULE, not a runtime session-state marker — because save/load replays `on_enter` MolActions, not a `.pse` session.** `c14/persist.py:1-8,50-51` saves ONLY `GameState` JSON (no `.pse`); `c14/engine.py:203-213` `load()` re-enters the current node → replays its `on_enter` MolActions → the molecular scene is a **pure function of game state** (Pattern 6; Anti-Pattern 5 = saving `.pse` is explicitly forbidden). Therefore any `cmd.alter`/`cmd.flag`/`cmd.label` marker set at runtime but NOT encoded as a MolAction is **lost on load**. The robust hero identity is: (a) load the hero as its **own single-atom object** `hero_atom` (the `intro.json` placeholder pattern) → `count_atoms("hero_atom")==1` + `iterate elem=='C'`; OR (b) a deterministic selection expression like `name C1` replayed in every `on_enter` `show_as`/`color`/`label` MolAction. **No marker op is needed for persistence** — the selection rule IS the marker (§C).
4. **`cmd.zoom`/`cmd.orient` DO mutate the view matrix headlessly** (`cmd.get_view`, `viewing.py:605`, returns an 18-element tuple; empirically the matrix changed after both `zoom` and `orient`). So `get_view` is a headless-verifiable *camera-state* primitive — but the robust, semantic, fixture-independent post-condition is the **selection + representation + color + label**, not the view-matrix floats (which are fixture-coordinate-dependent). `cmd.scene` (`viewing.py:993`) store/recall **works headlessly** and restores rep+color state (empirically: `scene H1 store` → mutate → `scene H1 recall` restored spheres+hero_orange), BUT a scene is **session state** → lost on game save/load → it is NOT the right primitive for persistent scene templates; **MolAction sequences are** (§B.4).
5. **Label + named-color + hero-highlight are expressible as a minimal set of new MolAction ops reusing the existing dispatch pattern.** The current `MolOps` has `color`, `show`, `show_as`, `select_focus` (named select), `zoom` but NO `label`, NO `set_color`. **Recommendation (§E): add 2 new ops — `label` (encapsulates the quoted-string-expression footgun) + `set_color` (encapsulates the RGB-list/auto-range footgun); reuse `show_as`/`color`/`select_focus`/`zoom` for the rest; express the hero highlight + scene templates as MolAction SEQUENCES (not a composite `scene` op). Hero identity = deterministic selection (own-object or `name C1`), no marker op.** Boundary: 5.4 prototypes `cmd.label`/`cmd.set_color` headlessly (direct `cmd.*` in the smoke, mirroring `wt_align_smoke.py` calling `cmd.super` directly); the `molops` `op="label"`/`op="set_color"` dispatch + unit test land in **Phase 6** (mirrors the 5.3 `op="align"` boundary — keeps 5.4 a pure design+prototype phase).

**Primary recommendation:** The cast/hero-representation convention uses **`show_as` (atomic per-atom rep) + a `set_color`-defined colorblind-safe named palette + a `label` op for the "C14"/"YOU" hero text + `select_focus` for named selections + `zoom` for framing**, composed as **MolAction sequences in `on_enter`** (the scene-template library is a set of authored MolAction sequences, NOT `cmd.scene` keys, because scenes don't survive save/load). The hero is identified by a **deterministic selection** — own-single-atom-object `hero_atom` for the placeholder, `name C1` (or a per-structure rule) for real glucose — re-derived on every `on_enter` replay, so **no runtime marker** (alter/flag/b) is needed for save/load persistence. The headless prototype verifies via **`count_atoms("<sele> and rep <name>")` + `iterate` (elem/color/label) + `get_color_indices` index→name** post-conditions on the bundled `_smoke.pdb`/`_edit_smoke.pdb` placeholders (§D).

### A.1 Representation — `cmd.show` / `cmd.hide` / `cmd.show_as` (a.k.a. `as`)

```python
# src: tmp/pymol-src/modules/pymol/viewing.py:491 cmd.show
def show(representation="wire", selection="", *, _self=cmd):
    return _showhide(representation, selection, 1, _self)     # value=1 -> turn ON only

# src: tmp/pymol-src/modules/pymol/viewing.py:528 cmd.show_as
def show_as(representation="wire", selection="", *, _self=cmd):
    return _showhide(representation, selection, 2, _self)     # value=2 -> turn ON + turn OFF others (atomic)

# src: tmp/pymol-src/modules/pymol/viewing.py:568 cmd.hide
def hide(representation="everything", selection="", *, _self=cmd):
    return _showhide(representation, selection, 0, _self)     # value=0 -> turn OFF

# src: tmp/pymol-src/modules/pymol/viewing.py:477  _showhide  (the shared helper)
def _showhide(rep, selection, value, _self):
    ...
    repn = _rep_to_repmask(rep)
    r = _cmd.showhide(_self._COb, str(selection), int(repn), value)
    return r
```

| param | default | meaning |
|-------|---------|---------|
| `representation` | `"wire"` (show/show_as) / `"everything"` (hide) | a rep name from `rep_list` (`viewing.py:51-53`): `lines, sticks, spheres, dots, surface, mesh, nonbonded, nb_spheres, cartoon, ribbon, labels, slice, ellipsoids, volume`; plus `"everything"` (all reps) and `"wire"` (alias for lines) |
| `selection` | `""` | atom selection-expression; `""`/`"all"` resolves to all (`_showhide` line 483: `selector.process(selection) or "all"`) |

**Return value:** `r = _cmd.showhide(...)` then `return r` (`viewing.py:487-489`) — an int status (PyMOL `DEFAULT_SUCCESS`/error); **not meaningful for the prototype** — discard it. The post-condition is the `rep <name>` selection keyword (§A.6).

**Key behavioral facts (all empirically confirmed, §A.6):**
- **`show` turns ON only** — it does NOT turn off other reps. After `hide everything, all` + `show spheres, mol and name C1`: `count_atoms("mol and rep lines")==0` (lines stayed off), `count_atoms("mol and name C1 and rep spheres")==1`.
- **`show_as` is atomic per-atom**: turns ON the named rep AND turns OFF all other reps **on the atoms in the selection**. After `show_as sticks, mol and name C1`: `count_atoms("mol and name C1 and rep sticks")==1` AND `count_atoms("mol and name C1 and rep spheres")==0` (spheres turned off on C1).
- **`show_as` on a SUB-selection leaves other atoms untouched** (per-atom scoping, NOT whole-object): `show_as spheres, mol` (all 3 atoms) then `show_as sticks, mol and name C1` → `O1` and `C2` keep spheres (`count_atoms("mol and name O1 and rep spheres")==1`), only `C1` switched to sticks. This is the mechanism for "highlight one atom in a molecule without disturbing the rest" — exactly the hero-highlight need.
- **`hide` turns OFF** the named rep (or all reps with `"everything"`). The existing `op="hide_all"` dispatches `cmd.hide("everything", "all")` (`molops.py:114-116`).

**When to use:** `show_as` is the cleanest "set this object's representation" for the game (atomic, no leftover reps). `show` is for *adding* a rep on top of existing ones (e.g. show spheres on the hero while keeping the cast's cartoon). `hide`/`hide_all` clears. The `intro.json` placeholders already use `show_as` (`{"op":"show_as","target":"hero_atom","args":{"rep":"spheres"}}`) — keep that.

| function | purpose | key args |
|----------|---------|----------|
| `set_color` | **define** a new named color from RGB `[r,g,b]` (0-1 OR 0-255, auto-detected) | `name` (str), `rgb` (list/tuple/str of 3 numbers) |
| `color` | **apply** a named-or-indexed color to a selection | `color` (name str OR int index), `selection` |

**Color verification (headless) — the critical mechanism the planner needs:**
- `cmd.iterate(sele, "out.append(color)", space={"out": out})` returns the color as an **INTEGER index** (`editing.py:1448` lists `color` in the alter/iterate namespace). Empirically: `hero_orange` → index `5388`.
- `cmd.get_color_indices(all=0)` (`querying.py:843`) returns a list of `(name, index)` tuples, e.g. `[('white',0), ('black',1), ('blue',2), …, ('hero_orange',5388)]`. Build `idx2name = {idx: name for (name,idx) in get_color_indices()}` to map an iterate color-index back to its name (empirically confirmed round-trip).
- `cmd.get_color_index(name)` (`querying.py:851`) → int index for a color name (round-trip with the iterate index).
- `cmd.get_color_tuple(name, mode=0)` (`querying.py:825`) → `(r,g,b)` tuple in 0.0-1.0 (empirically: `get_color_tuple("hero_orange")==(1.0,0.5,0.0)`). Accepts a name OR an int index.

**Colorblind-safe palette:** PyMOL ships NO built-in "colorblind-safe" palette name. The mechanism is: `cmd.set_color("c14_<name>", [r,g,b])` for each color in a published colorblind-safe palette (e.g. a Wong-style set), then reference those names in `cmd.color`. The **RGB values themselves are a Phase 7 source/approval decision** (spec.md: all citations/claims must be human-approved) — this file only verifies the `set_color` API mechanics, not the palette's science. `cmd.spectrum`'s built-in palettes (`viewing.py:2057-2073`) are diverging/rainbow ramps (NOT colorblind-safe by default); use them only for per-property gradients (e.g. b-factor), not for categorical hero/cast coloring.

| param | default | meaning |
|-------|---------|---------|
| `name` | (required) | unique name for the selection (a named selection is a **first-class session object**, registered & reusable across cmd calls) |
| `selection` | `""` | a selection-expression (see grammar below) |
| `enable` | `-1` | `-1` = enabled (visible as the magenta selection dashes); `0` = disabled (exists but not highlighted). A named selection is **persistent across cmd calls** until deleted/overwritten. |

**Selection-expression grammar (all empirically confirmed, §A.6, on the 3-atom `_smoke.pdb` / 2-residue `_edit_smoke.pdb`):**
- `elem C` / `elem O` — by element symbol (uppercase). `count_atoms("mol and elem C")==2`.
- `name C1` / `name CA` — by atom name. `count_atoms("mol and name C1")==1`.
- `resi 1` — by residue number (1-based). `count_atoms("mol and resi 1")==3`.
- `chain A` — by chain id. `count_atoms("mol and chain A")==3`.
- `resn ALA` — by residue name (3-letter). (standard; not separately smoke-tested but is a core grammar token.)
- `segi HERO` — by segment id (settable via `cmd.alter`, §C). `count_atoms("mol and segi HERO")==1` after `alter segi='HERO'`.
- `flag 0` — by flag number (0=`focus`, 1=`free`, …; §C). `count_atoms("mol and flag 0")==1` after `flag focus, …, reset`.
- compound: `chain A and resi 1 and name C1` — AND-combine. `count_atoms(...)==1`.
- by object name: `mol` (bare object name = all its atoms). `count_atoms("mol")==3`.
- `rep <name>` — **atoms with representation `<name>` enabled** (the headless "rep visible" primitive, §A.1). `count_atoms("mol and rep spheres")`.
- `?`-prefix on object name: safe count on a possibly-deleted object. `count_atoms("?hero_atom")` returns `0` (never raises); bare `count_atoms("hero_atom")` on a DELETED object **raises `CmdException`** (empirically confirmed, §A.6; matches `molops_smoke.py`).

**Named-selection persistence:** a `cmd.select("hero_sele", …)` registers `hero_sele` in the session; `cmd.get_names("selections")` (`querying.py:1148`) lists it (empirically: `['hero_sele']`), and `count_atoms("hero_sele")` works in any later cmd call. **But** — a named selection is SESSION state: it is lost on game save/load (no `.pse` is saved, §H). So a named selection is a *convenience* within a single play session, NOT a hero-identity mechanism. The hero identity must be a selection EXPRESSION re-evaluated on each `on_enter` replay (§C).

**Critical read-back pitfall (empirically hit, §A.6 first run):** the `cmd.iterate` `space={}` collector key **MUST NOT collide with an atom-property name**. Naming the collector `segi` (e.g. `space={"segi": lst}` with expression `"segi.append(segi)"`) makes the atom's `segi` field shadow the collector → `AttributeError: 'str' object has no attribute 'append'`. Use a non-colliding collector name (`segi_out`, `cidx`, `lbl`, `bb`, `elems`). The same applies to `color`, `label`, `b`, `flags`, `elem`, `name`, `chain`, `resn`, `resi`, etc. (See §F Pitfall 1.)

**`cmd.sort` after `alter`** (`editing.py:1257`, WARNING at `editing.py:1457-1460`): after altering `name`/`chain`/`segi` (properties affecting canonical atom ordering), issue `cmd.sort(obj)` or subsequent `create`/`byres` operations are confounded. The existing `edit_ops.py` alter→sort pattern already follows this; any new `alter`-based marker must too.

**Empirical findings (§A.6):**
- **`cmd.zoom` and `cmd.orient` BOTH mutate the view matrix headlessly** — `cmd.get_view()` returned a different 18-tuple after `zoom("hero_atom", buffer=5.0)` and again after `orient("hero_atom")`. So `get_view` IS a headless-verifiable camera-state primitive. **However**, the view-matrix floats are fixture-coordinate-dependent (arbitrary on a placeholder), so a hardcoded view-matrix assertion is brittle; the robust post-condition is selection+rep+color+label (§D). `zoom`/`orient` return a C status int — discard.
- **`cmd.scene` store/recall works headlessly** and restores rep + color: `scene H1 store` (after `show_as spheres` + `color hero_orange`), then mutate to `show_as sticks` + `color gray`, then `scene H1 recall` → `count_atoms("hero_atom and rep spheres")==1` AND the color index maps back to `hero_orange`. So a scene captures & restores the representation/color state, not just the camera. **BUT a scene is session state** → not saved by `SaveStore` (§H) → **lost on game save/load**. Therefore `cmd.scene` is NOT the right primitive for the *persistent* scene-template library; MolAction sequences are (§B.4). `cmd.scene` could still be useful *within* a session for user-driven "view presets" (a Phase 6/7 UX nicety), but the authoritative scene state lives in `on_enter` MolActions.

## §B. When to use which (representation / color / zoom / scene-template)

### B.1 Representation choice per role

| Role (from the design) | Recommended rep | Why | Call |
|------------------------|-----------------|-----|------|
| **Hero (single carbon, `hero_atom`)** | `spheres` | a single sphere is the unambiguous "you are here" marker; big, bright, labelable | `show_as spheres, hero_atom` |
| **Hero-within-a-molecule (e.g. C1 of glucose)** | `spheres` on the 1-atom sub-sele | `show_as spheres, glucose and name C1` highlights just C1; per-atom scoping leaves the rest of glucose alone (empirically confirmed §A.6) | `show_as spheres, glucose and name C1` |
| **Cast (20 AA / enzyme)** | `cartoon` | standard protein overview; lights up backbone atoms even on a tiny peptide (empirically `rep cartoon=17` on a 2-residue stub) | `show_as cartoon, aa_cast` |
| **Substrate/small molecule (glucose shell)** | `sticks` | standard ligand depiction; `rep sticks=17` confirmed | `show_as sticks, glucose` |
| **Active-site zoom-in** | `sticks` + `spheres` on the hero | layer `show spheres` on top of `sticks` (show ADDS, doesn't clear) | `show spheres, <hero_sele>` after `show_as sticks, <site>` |

**Anti-pattern:** using `show` (not `show_as`) for the *primary* scene rep leaves default `lines`/`nonbonded` on (the `molops_smoke.py` `hide_all_cleared` bonus proves `hide_all` is needed first). The `intro.json` convention already starts every `on_enter` with `{"op":"hide_all"}` then `show_as` — **keep that contract**: `hide_all` → `show_as <primary>` → optional `show <overlay>`.

### B.2 Color choice

- **Define the palette ONCE** via `cmd.set_color` (at controller init in Phase 6, or as a one-shot `on_enter` `set_color` MolAction on the first node) — a small colorblind-safe set of named colors (hero color, cast color, active-site color, …). Re-defining an existing name is idempotent (`set_color` overwrites; `_invalidate_color_sc` refreshes the cache, `viewing.py:2161`), so re-running on `on_enter` replay / re-init is safe.
- **Apply via `cmd.color("<c14_name>", sele)`** — reference the named color, never a raw index (the index is session-allocated and unstable across runs; empirically `hero_orange` got index 5388 in this run — a different session could differ).
- **Verify headlessly** by `iterate` color-index → `get_color_indices` index→name map (§A.2). Do NOT assert a hardcoded color index in the prototype (it's session-dependent); assert the **name** round-trips.

### B.3 Zoom / orient — framing the hero / active site

- `cmd.zoom("<hero_sele>", buffer=<Å>)` frames the camera on the hero; `buffer` adds margin so the sphere isn't clipped (`viewing.py:65`, `complete=1` guarantees no clipping — use for the hero close-up).
- `cmd.orient("<sele>")` aligns principal axes — useful for a "standard view" of an active site; rarely needed for a single atom (a sphere has no preferred axis).
- **Headless verifiability:** `get_view()` changes (§A.6), but the floats are fixture-dependent. The robust post-condition is that the SELECTION is non-empty + the rep is visible; the view is a GUI concern verified by humans in a real session (the same boundary as 5.3's "RMSD is real, the camera is presentation"). The `op="zoom"` MolAction's `apply` returns `None` (consistent with all ops); the smoke verifies the selection, not the view.

### B.4 Scene templates = MolAction SEQUENCES, not `cmd.scene` keys

**Recommendation: the scene-template library is a set of authored `on_enter` MolAction sequences, NOT `cmd.scene` keys.** Reasoning:
- `cmd.scene` store/recall works headlessly (§A.6) but a scene is **session state** — `SaveStore` saves only `GameState` JSON, no `.pse` (§H), so a `cmd.scene` key is **lost on game save/load**. A scene template that must survive save/load cannot be a `cmd.scene` key.
- A MolAction sequence in `on_enter` IS replayed on load (`engine.py:203-213`) → it IS the persistent, save/load-safe scene template. This is exactly the existing `intro.json` pattern (`hide_all` → `load` → `show_as` → …).
- `cmd.scene` remains a useful *in-session* primitive for Phase 6/7 user-driven "view presets" (e.g. bind F-keys to camera angles the user set), but the authoritative scene state is the MolAction sequence. **Do not build the scene-template library on `cmd.scene`.**

## §C. Hero-atom identification mechanics (CRITICAL)

The hero is a single **carbon atom** (C14 is its isotope *label*, not its identity — per AGENTS.md hero-identity note). The design needs: (a) find "the carbon atom" in a loaded structure, (b) mark/persist it as the hero across MolAction replay + save/load, (c) verify headlessly `count==1` and `elem=='C'`.

### C.1 The two hero-identity strategies (recommend strategy A for the prototype)

**Strategy A — Hero as its OWN single-atom object (the `intro.json` placeholder pattern). RECOMMENDED for Phase 5.4 + the placeholder prototype.**
The `intro.json` already does `{"op":"load","target":"pdb:TBD_HERO_CARBON","args":{"object":"hero_atom"}}` — load the hero as a dedicated 1-atom object `hero_atom`. Then:
- Identity post-condition: `count_atoms("hero_atom")==1` AND `iterate("hero_atom","out.append(elem)")` → `['C']` (empirically confirmed §A.6: `hero_atom atoms=1`, `elem=['C']`).
- Highlight: `show_as spheres, hero_atom` + `color <hero_color>, hero_atom` + `label hero_atom, '"C14"'`.
- **No marker needed** — the object IS the marker. Save/load safe: on load, `on_enter` replays `load hero_atom` → `show_as spheres` → the hero is back. (For the prototype, `cmd.create("hero_atom", "mol and name C1")` extracts a 1-atom object from the fixture — empirically confirmed.)

**Strategy B — Hero as a deterministic sub-selection within a larger molecule (e.g. C1 of glucose). RECOMMENDED for real structures (Phase 7) + any case where the hero is part of a molecule.**
- The hero is identified by a **deterministic selection expression** authored per-structure: `glucose and name C1` (standard glucose numbering — C1 is the carbon that enters glycolysis), or `elem C and resi 1 and …`, or `name C1` for a PDB-format small molecule.
- Every `on_enter` MolAction that touches the hero uses that SAME expression in its `sele`/`target`: `show_as spheres, glucose and name C1`, `color <hero_color>, glucose and name C1`, `label glucose and name C1, '"C14"'`.
- **No `alter`/`flag`/`b` marker is needed for persistence** — the selection expression is re-evaluated on every replay, so the hero is re-derived from the structure + the rule each time. This is the save/load-safe design: the marker is the *rule*, not a *mutation*.
- Optionally, a `select_focus` MolAction can create a named selection `hero_sele` for readability (`{"op":"select_focus","args":{"name":"hero_sele","sele":"glucose and name C1"}}`), but the named selection is session state (lost on load) — it's a convenience, not the identity mechanism; the `sele` expressions in the `show_as`/`color`/`label` MolActions are the identity.

### C.2 Why NO runtime marker (alter/flag/label-as-marker) is needed — and when one might still be useful

The four marker candidates (§A.4) are all headless-verifiable, BUT they are **session state**: a `cmd.alter("segi='HERO'")` / `cmd.flag("focus")` / `cmd.alter("b=14")` set at runtime, NOT encoded as a MolAction, is **lost on save/load** (no `.pse` is saved, §H). So:
- **For identity/persistence: do NOT use a marker.** Use Strategy A (own object) or B (deterministic sele). The selection rule is replayed → re-derived → save/load safe.
- **A marker IS useful only if** (a) it is itself a MolAction in `on_enter` (so it replays), AND (b) you need a *stable handle* that survives atom reordering / a re-fetch within a session. The `segi='HERO'` alter is the most robust such handle (a string field, selectable via `segi HERO`, survives `sort`; §A.4 candidate (a)) — but it requires an `op="alter"` MolAction (which would be a NEW op touching `cmd.alter`, currently gate-restricted to `edit_ops.py` per `molops.py:48` SC1). **Recommendation: do NOT add an `op="alter"` marker op in 5.4** — Strategy A/B cover the hero identity without touching the alter gate. Reserve `segi`-marking for a Phase 7 real-structure case where atom reordering across a re-fetch actually breaks a `name C1` rule (and even then, prefer an own-object or a `select_focus` named-sele over a mutating alter).
- **`label` is NOT a marker** — it's the visual "C14"/"YOU" text (§A.4 candidate (c)). It's a rep + a string field, useful for the hero's on-screen identity label, NOT for selection persistence. Add it as the new `op="label"` (§E).

### C.3 The "which carbon in glucose" question (real-structure, Phase 7)

- **Placeholder (Phase 5.4):** sidestepped — the hero is its own `hero_atom` object (Strategy A) or `name C1` on the 3-atom `_smoke.pdb` fixture (which has C1/C2/O1). No real glucose loaded.
- **Real glucose (Phase 7):** a PDB-format glucose (e.g. from a ligand HETATM block) names carbons `C1..C6` (standard IUPAC carbohydrate nomenclature) — `name C1` deterministically picks the anomeric carbon that enters glycolysis. The author encodes that rule in the `on_enter` MolAction `sele`.
- **PubChem `fetch type='cid'` small molecules (CAST-02):** a fetched SDF names atoms by **element symbol only** (`C`, `O`, `H` — no `C1`/`C2`), so `name C1` does NOT work on a fetched PubChem glucose; you'd select by `elem C and index <n>` or by coordinates. **This is an OPEN QUESTION** (§I) — it cannot be verified headlessly without a network fetch + a real CID, which is Phase 7 source/approval content (spec.md: no fabricated science). The robust mitigation: load the hero as its own object (Strategy A), OR fetch the small molecule as a PDB-format ligand (which preserves atom names), OR author a per-structure `index`-based rule. **The 5.4 prototype does NOT fetch** — it uses the bundled placeholder, so this question does not block 5.4.

## §E. New `MolAction` op vs reuse — recommendation (the key integration question)

### E.1 The current state

`MolOps.apply` (`molops.py:112-196`) currently dispatches: `hide_all, show, show_as, select_focus, zoom, color, load, delete, edit, protonate, restore`. The `select_focus` op (`molops.py:123-125`) already does **named selection**: `cmd.select(args.get("name","focus"), args["sele"])` — so a named persistent selection is REUSABLE via `select_focus` with `args["name"]` (no new op needed for named selections). Missing for the cast/hero design: **`label`** (no op), **`set_color`** (no op — can't define a named colorblind-safe palette). No `flag`/`alter`/`hero_highlight`/`scene` op.

### E.2 The three options

**Option 1 — Reuse existing ops only (`color` + `show_as` + `select_focus` + `zoom`).** What's missing: the hero's "C14"/"YOU" text label (no `label` op) and the ability to define a named colorblind-safe color (no `set_color` op — `color` only *applies* an already-defined name). The hero highlight would be `show_as spheres` + `color <name>` + `zoom`, but no label, and the palette must be defined out-of-band (controller init, not a MolAction). Workable but leaves two real gaps.

**Option 2 — Add a minimal set of new ops: `label` + `set_color` (2 new ops); reuse the rest; hero highlight = a MolAction SEQUENCE.** `label` encapsulates the quoted-string-expression footgun (`cmd.label(sele, '"C14"')` — the expression must be a quoted string, §A.4); `set_color` encapsulates the RGB-list/auto-range footgun (`cmd.set_color(name, [r,g,b])`). Hero highlight = `show_as spheres` + `color <hero_color>` + `label '"C14"'` + `zoom` (a sequence of 4 MolActions, composable, one-concern-each). Scene templates = authored MolAction sequences (§B.4). No `flag`/`alter`/`hero_highlight`/`scene` op.

**Option 3 — A single composite `op="scene"` op carrying a template id.** One MolAction whose dispatch looks up a template id ("hero_reveal", "active_site_zoom") and runs a hardcoded sequence of `cmd.*` calls.

### E.3 Analysis against the existing architecture

| Criterion | Option 1 (reuse only) | Option 2 (`label`+`set_color` + sequences) | Option 3 (composite `scene` op) |
|-----------|----------------------|--------------------------------------------|--------------------------------|
| Covers the hero-label + named-color gaps | ❌ no label, no set_color | ✅ both | ✅ (hardcoded in the dispatch) |
| Matches one-MolAction-one-concern dispatch (`molops.py:112-196`) | ✅ | ✅ each new op is one concern | ❌ one op = many `cmd.*` calls |
| Matches the multi-method dispatch precedent (`load`→`source`, `edit`→`edit_type`) | N/A | ✅ `label`/`set_color` are peer primitives | ❌ couples a whole template |
| Composable / reusable across scenes | ✅ (limited) | ✅ `label`/`set_color` reusable anywhere | ❌ each template is a hardcoded branch |
| Unit-testable dispatch mapping (MockCmd) | N/A | ✅ `MockCmd.assert label(sele,expr)` / `set_color(name,rgb)` | ⚠️ one assert per template, more brittle |
| Encapsulates API footguns (label quoted-string, set_color RGB-range) | ❌ authors hit them raw | ✅ the dispatch normalizes them once | ✅ (but per-template) |
| Declarative `on_enter` authoring (story data, not controller code) | ✅ | ✅ sequences authored per node | ✅ one action per template |
| Domain tier stays pure (AST gate) | ✅ | ✅ new ops = string keys + docstring lines, no pymol import | ✅ |
| Save/load safe (on_enter replay reconstructs scene) | ✅ | ✅ sequences replay | ✅ (the op replays) |
| Avoids touching the `cmd.alter` gate (SC1, `molops.py:48`) | ✅ | ✅ (no `alter`/`flag` op) | ⚠️ if a template needs a marker, it'd hit the gate |

### E.4 Recommendation: **Option 2 — add `label` + `set_color`; reuse the rest; hero highlight + scene templates = MolAction sequences**

Reasoning (mirrors 5.3 §E's "Option 1, one new op with `args["method"]` dispatch"):
- **It is the exact structural parallel** of the existing dispatch: `show`/`show_as`/`color`/`zoom` are already peer primitives wrapping one `cmd.*` call each; `label` wraps `cmd.label`, `set_color` wraps `cmd.set_color`. The planner adds two `elif` branches — the same shape as the existing `show`/`color` branches (`molops.py:117-131`).
- **It encapsulates the two real footguns** (§F): `label`'s expression must be a quoted string (`'"C14"'`, not `"C14"` — the latter evaluates the atom property `C14` and fails); `set_color`'s `rgb` must be a 3-list/tuple (or a parseable string) and the 0-1/0-255 auto-range is implicit. ## §F. Common pitfalls

### Pitfall 1 — `cmd.iterate` `space` collector key MUST NOT collide with an atom-property name
**What goes wrong:** `cmd.iterate("sele", "segi.append(segi)", space={"segi": lst})` raises `AttributeError: 'str' object has no attribute 'append'`. The atom's `segi` field (a string) shadows the collector `segi` (your list) in the expression namespace, so `segi.append(segi)` becomes `'<atom segi string>'.append(...)`.
**Why:** PyMOL merges the atom-property namespace with the `space` dict; atom properties take precedence, so a same-named collector is unreachable.
**How to avoid:** use a non-colliding collector name (`segi_out`, `cidx`, `lbl`, `bb`, `elems`, `flags_out`). Never name a collector `segi`/`color`/`label`/`b`/`flags`/`elem`/`name`/`chain`/`resn`/`resi`/`alt`/`ss`/`ID`/`index`/`rank`/…
**Warning signs:** `AttributeError: 'str' object has no attribute 'append'` (or `'int'` for `b`/`color`/`flags`) on an iterate call. (Empirically hit + fixed in §A.6 first run.)

### Pitfall 2 — `cmd.label` expression must be a QUOTED string, not a bare word
**What goes wrong:** `cmd.label("sele", "C14")` tries to evaluate the atom property named `C14` (which doesn't exist) → error/empty label. The label *expression* is Python code evaluated per atom; a literal text label must be a quoted string: `cmd.label("sele", '"C14"')`.
**How to avoid:** the `op="label"` dispatch wraps `args["text"]` as `'"%s"'` (§E.5) so authors write `"text":"C14"`. In raw `cmd.label` calls, always wrap: `cmd.label(sele, '"' + text + '"')`.
**Warning signs:** label is empty / `NameError` on a `cmd.label` call. (Empirically: `'"C14"'` → iterate `label`==`'C14'`.)

### Pitfall 3 — `cmd.alter` of `name`/`chain`/`segi` REQUIRES a `cmd.sort` after (canonical ordering)
**What goes wrong:** after `cmd.alter("sele","segi='HERO'")` without `cmd.sort`, subsequent `cmd.create`/`byres`/selection-by-order operations are confounded (atoms out of canonical order).
**How to avoid:** issue `cmd.sort(obj)` after any alter of `name`/`chain`/`segi`/`resn` (WARNING at `editing.py:1457-1460`). The existing `edit_ops.py` alter→sort pattern follows this; any marker strategy using `alter` must too. (Empirically: `alter_segi` + `sort` → `segi HERO` selectable.)
**Warning signs:** `create`/`byres` returns wrong atoms after an alter; selections-by-index shift.

### Pitfall 4 — `cmd.color`'s `color` arg resolves a NAME or an INT index, but the index is session-unstable
**What goes wrong:** asserting `iterate` color-index == a hardcoded int (e.g. `5388`) is brittle — the index is allocated per-session; another run assigns a different index to the same named color.
**How to avoid:** assert the color NAME via the `get_color_indices()` index→name round-trip (§D.1). Apply colors by NAME (`cmd.color("c14_hero", sele)`), never by raw index.
**Warning signs:** a color post-condition passes on one run, fails on another with no code change. (Empirically: `hero_orange`→5388 this run; do not hardcode 5388.)

### Pitfall 5 — `cmd.scene` is session state — NOT save/load-safe (do NOT build scene templates on it)
**What goes wrong:** a "scene template" stored via `cmd.scene("H1","store")` is lost on game save/load (no `.pse` is saved, §H), so the recalled scene is empty after load.
**How to avoid:** build scene templates as `on_enter` MolAction SEQUENCES (§B.4, §E.5) — they replay on load. Reserve `cmd.scene` for in-session user view-presets (Phase 6/7), not the authoritative scene state.
**Warning signs:** scene recall works during a session, fails after save/load.

### Pitfall 6 — a hero marker set at runtime (alter/flag/b/label) but NOT in `on_enter` is lost on save/load
**What goes wrong:** `cmd.alter("glucose","segi='HERO'")` at runtime (controller code, not a MolAction) marks the hero, but on save/load the `on_enter` replays WITHOUT that alter → the hero is unmarked → the highlight sele finds 0 atoms.
**How to avoid:** the hero identity is a DETERMINISTIC SELECTION RULE (own-object, or `name C1`) encoded in the `on_enter` `sele` args — NOT a runtime mutation (§C). If a marker is truly needed, it must be a MolAction in `on_enter` (so it replays) — but §C recommends avoiding markers entirely.
**Warning signs:** hero highlight present in-session, gone after save/load.

### Pitfall 7 — bare `cmd.count_atoms("obj")` on a DELETED object RAISES; use the `?`-prefix
**What goes wrong:** after `cmd.delete("hero_atom")`, `cmd.count_atoms("hero_atom")` raises `CmdException` (not returns 0).
**How to avoid:** use `count_atoms("?hero_atom")` (the `?`-prefix is safe; returns 0 for a non-existent object). This is the existing `delete`-op post-condition pattern (`molops_smoke.py:163-175`). (Empirically confirmed §A.6.)

### Pitfall 8 — PubChem `fetch type='cid'` small molecules name atoms by ELEMENT only (no `C1`/`C2`)
**What goes wrong:** a hero rule `name C1` works on a PDB-format small molecule but NOT on a PubChem-SDF-fetched one (atoms named `C`/`O`/`H` only) → `count_atoms("... and name C1")==0`.
**How to avoid:** for fetched small molecules, use `elem C and index <n>` or load the hero as its own object (Strategy A, §C). This is a Phase 7 real-structure concern (OPEN QUESTION §I); the 5.4 placeholder does NOT fetch.

## §G. Don't hand-roll

`show`/`hide`/`show_as`/`color`/`set_color`/`select`/`label`/`flag`/`zoom`/`orient`/`scene` are all BUILT-IN `cmd.*` — do NOT reimplement representation/selection/labeling. The only custom code Phase 5.4 adds is (a) the 2 `elif` branches in `molops.py` (`op="label"`, `op="set_color"` — ~6 lines each, §E.5), (b) the convention spec (a doc), and (c) the headless smoke. The value-add of the new ops is **encapsulating the footguns** (label quoted-string, set_color RGB-range), not reimplementing the APIs.

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| "is rep X visible on sele Y?" | manual per-atom rep-bit tracking | `count_atoms("sele and rep <name>")` | the `rep` selection keyword is the headless primitive (§A.1, empirically confirmed) |
| colorblind-safe palette | a custom color-renderer | `set_color` named colors from a published palette + `color` by name | `viewing.py:2107`/`:1858` — named colors are cache-managed, idempotent, index-stable-by-name |
| hero identity / persistence | a custom marker system (alter/flag/b at runtime) | a deterministic selection rule (own-object or `name C1`) in `on_enter` | the rule replays on save/load; runtime markers are lost (§C, §H) |
| scene templates | `cmd.scene` keys | `on_enter` MolAction sequences | scenes are session state (lost on load); MolActions replay (§B.4) |
| headless color verification | guessing the color index | `iterate` color-index → `get_color_indices` index→name map | the index is session-allocated; the name is stable (§A.2) |

**Key insight:** the ONLY custom logic Phase 5.4 adds is 2 trivial dispatch branches + a convention doc. The representation/selection/label/color math is entirely PyMOL's. The new ops' value-add is encapsulating the `label` quoted-string + `set_color` RGB-list footguns so story authors never hit them.

## §H. Persistence across save/load (CONFIRMED — the decisive architectural constraint)

**Claim: the hero marker + representation state must be re-derivable from a DETERMINISTIC selection rule (not session state), because save/load replays `on_enter` MolActions, not a `.pse` session. CONFIRMED by source:**

- `c14/persist.py:1-8` — *"SaveStore: serialize/restore GameState to human-readable JSON. … the engine owns the on_enter MolAction replay on load (Pattern 6: the scene is a pure function of game state, not a .pse session). … SaveStore does NOT save a .pse PyMOL session (Anti-Pattern 5)."*
- `c14/persist.py:50-51` — `save` writes ONLY `json.dump(state.to_dict(), …)` — pure `GameState`, no PyMOL session, no `.pse`.
- `c14/engine.py:203-213` — `load()` → `self.state = SaveStore.load(path)` → `return self._enter(self.state.current_node, record_visit=False)` — **re-enters the current node → replays its `on_enter` MolActions** (the docstring: *"re-enter the current node (replaying its on_enter MolActions to reconstruct the scene -- Pattern 6)"*).
- `c14/engine.py:21` — *"of game state, NOT a saved .pse session -- Anti-Pattern 5 avoided"*.

**Implication for the design (CONFIRMED, not refuted):**
- On save/load, the PyMOL session (named selections, flags, labels, colors set via `cmd.*` at runtime, `cmd.scene` keys) is **NOT persisted** — only `GameState` (story position + rng + flags). The molecular scene is **reconstructed by replaying the current node's `on_enter` MolActions** (which re-load, re-`show_as`, re-`color`, re-`label`, re-`zoom`).
- Therefore: **everything that must survive save/load must be a MolAction in `on_enter` (or re-derivable from one).** A runtime `cmd.alter`/`cmd.flag`/`cmd.label`/`cmd.color` NOT driven by a MolAction is lost on load (Pitfall 6).
- The hero-identity recommendation (§C) follows directly: **the hero is a deterministic selection rule** (own-object `hero_atom`, or `name C1`) — the `on_enter` `load`/`show_as`/`color`/`label` MolActions replay it on load, re-highlighting the hero. No runtime marker needed. The `set_color` palette is re-defined on replay (idempotent) or at controller re-init — also save/load safe.
