## Summary

This is a DESIGN phase (0 requirements — `REQUIREMENTS.md:145`). It produces a **reviewable convention artifact** + a **headless prototype** + a **human design-review checkpoint**, mirroring the 05.3 pattern (`05.3-CONVENTION.md` + `05.3-RESEARCH-integration-design.md`). The convention specifies *how the player sees "their" carbon atom* in any loaded structure — the **selection rule** (which atom is the hero), the **color + representation + label** (how it's marked), the **persistence** (how it survives `on_enter` replay + save/load), and the **CO2-shed climax** (what happens when the hero's carbon body is shed and the "soul" follows the electrons). It enables **CHAR-02** (`REQUIREMENTS.md:19` — "The C14 hero is identified/highlighted in the loaded 3D structure at game start so the player can see 'their' atom") delivery in Phase 6, without Phase 6 re-designing it.

The central design tension: **the hero is a carbon atom that is PART OF whatever molecule is currently loaded, and which carbon / which molecule changes per stage.** Across the glucose pathway the hero is a carbon in: the single-atom `hero_atom` object (`intro.preface`) → C1 of `glucose` (`intro.shell_glucose`) → G6P/FBP intermediates (narrative-only, no PDB) → C3 of pyruvate → C2 of acetyl-CoA → citrate/TCA intermediates → **shed as CO2** at `tca.co2_turn1`/`tca.co2_turn2` (the RNG-weighted climax) → its **electrons** (the "soul") continue via NADH/FADH2 → ETC → ATP (`etc.*` → `end.true`). At enzyme-cast nodes (`gly.pfk`→4PFK, `pyr.pdh`→6CFO, `tca.citrate_synthase`→1CSC, `tca.isocitrate_dh`→5GRF, `etc.complex_iv`→1OCC) the **loaded structure is the ENZYME** (the cast member), and the hero is in the **substrate** — which the skeleton does NOT load. So the hero-highlight must handle three structural cases: hero-alone, hero-in-substrate, and hero-at-enzyme-cast (substrate not loaded). This is the "how is the hero represented" question the ROADMAP SC1 (`ROADMAP.md:187`) makes an explicit, reviewable spec.

The key persistence finding (from `c14/engine.py:20-22, 163-194, 203-213`): **the PyMOL session is NOT part of save state** (Anti-Pattern 5). Save/load replays the current node's `on_enter` MolActions (`load` → `_enter(current_node, record_visit=False)`). Therefore the hero-highlight is a **pure function of the `on_enter` sequence** — re-derived from a deterministic selection rule + re-applied by a `hero_highlight` MolAction **every time the node is entered**. It CANNOT depend on session-only state (a `cmd.flag`/`cmd.alter` b-object set once and never re-applied). Any marker is a RUNTIME convenience re-set each `on_enter`, not a cross-save dependency. This is the §C contract: the highlight is re-derived from the deterministic rule, NOT stored in PyMOL session state — exactly the "persistence across MolAction replay" the SC1 demands.

**Primary recommendation:** Adopt a **hybrid selection rule** — each hero-bearing asset carries an explicit `hero_selector` (a PyMOL selection expression resolving to exactly one carbon, Phase 7-authored per asset); single-carbon objects auto-derive the unique carbon; multi-carbon objects WITHOUT a `hero_selector` FAIL LOUDLY at the human-verify gate (no silent best-guess for real content — the "which carbon is the hero" is a pathway-science decision, `AGENTS.md` no-fabricated-science). Apply the highlight via a **single `op="hero_highlight"` MolAction** (encapsulating `set_color` + `show_as spheres` + `set sphere_scale` + `color` + dim-non-hero + `label`), fired AFTER `load` in the `on_enter` sequence. Use a **colorblind-safe `hero_gold`** (Okabe-Ito orange [0.90, 0.62, 0.0]) + **spheres scaled up** + **label "C14"** (the isotope tracking label — the hero's name tag, NOT its fate). At the **CO2-shed climax** (`tca.co2_turn1`/`turn2`), the highlight FADES on the departing CO2 (the carbon body — the "chrysalis") and TRANSFERS to the NADH/electron carrier (the "soul") for the ETC → `end.true` arc — the metamorphosis visual — with a MANDATORY anti-confusion `text_teaching` note that the transfer is a narrative device, NOT a claim the carbon becomes NADH/ATP.

## §A. The hero selection rule (the core question)

### Where it fires in the data flow

The hero-highlight is a **`on_enter` concern**, exactly like the 05.3 WT-aligned reveal (05.3-CONVENTION.md §2). The trace (verified against `c14/engine.py:163-194`):

1. `engine.start` / `engine.choose` / `engine.apply_player_edit` / `engine.load` → `_enter(node_id)` (`engine.py:104, 133, 161, 213`).
2. `_enter` runs `interpreter.enter_node(node, ...)` → returns the node's `on_enter` MolActions (`engine.py:176-177`).
3. Each MolAction is dispatched per-action to `molaction_sink` (`engine.py:187-189` → `molops.apply(action)` in the Phase 4+ controller).
4. **The hero-highlight fires HERE, in the node's `on_enter` sequence, AFTER the `load` MolAction that brings the hero-bearing object into the session.** (`engine.load` replays this on save/load with `record_visit=False`, `engine.py:213` — so the highlight is re-derived each replay; see §C.)

### The three structural cases the rule must handle

The frozen skeleton (`data/story_glucose/*.json`) defines three structural cases for where the hero carbon lives relative to the loaded object:

| Case | Skeleton example | Loaded object | Where the hero is | `on_enter` (current placeholders) |
|------|------------------|---------------|-------------------|-----------------------------------|
| **(1) Hero-alone** | `intro.preface` | `hero_atom` (single-atom object, `pdb:TBD_HERO_CARBON`) | the object IS the hero | `hide_all` → `load hero_atom` → `show_as spheres hero_atom` → `load aa_cast` → `show_as cartoon aa_cast` (`intro.json:8-14`) |
| **(2) Hero-in-substrate** | `intro.shell_glucose`, `gly.start` | `glucose` (multi-carbon, `pdb:TBD_GLUCOSE`) | ONE carbon (C1) IN the substrate object | `hide_all` → `load glucose` → `show_as sticks glucose` (`intro.json:39-43`; `glycolysis.json:8-11`) |
| **(3) Hero-at-enzyme-cast** | `gly.pfk`, `pyr.pdh`, `tca.citrate_synthase`, `tca.isocitrate_dh`, `etc.complex_iv` | the ENZYME (e.g. `pfk`=4PFK, `pdh`=6CFO, `citrate_synthase`=1CSC, `isocitrate_dh`=5GRF, `complex_iv`=1OCC) | the hero is in the **SUBSTRATE** — which the skeleton does NOT load at these nodes | `hide_all` → `load <enzyme>` (`glycolysis.json:35-38`; `pyruvate_branch.json:21-24`; `tca.json:21-24, 90-93`; `etc_atp.json:62-65`) |

**Case 3 is the central tension.** At enzyme-cast nodes the loaded structure is the enzyme (a cast member per `spec.md`'s "Protein cast of ~20+ enzymes"); the hero carbon is in the substrate, which the skeleton does NOT load. So the hero is NOT directly highlightable in the loaded enzyme. Three sub-options for case 3:

| Sub-option | What it does | Tradeoff |
|-----------|--------------|----------|
| **(3a) Co-load the substrate** | the enzyme-cast node's `on_enter` ALSO loads the substrate as a separate small object (e.g. `load pdb:TBD_FBP → "fbp"`), highlight the hero in it alongside the enzyme | Hero always visible; MORE assets (per-enzyme substrate PDBs/SDFs, Phase 7); the large-enzyme visibility/zoom is a Phase 9 concern (ROADMAP §E) |
| **(3b) Suspend the highlight** | the hero is "inside the enzyme's active site" narratively but NOT visually marked; the enzyme is the focus | Simpler, fewer assets; the player LOSES sight of "their" atom at the most dramatic moments (when the enzyme acts on the hero) |
| **(3c) Hybrid (RECOMMENDED)** | co-load the substrate + highlight the hero WHERE the substrate is small enough (pyruvate at PDH, citrate at citrate_synthase, etc.); SUSPEND where co-loading is impractical (huge membrane proteins like 1OCC Complex IV) | Balances visibility vs asset cost; the DECISION is per-node Phase 7 content; the convention specifies the MECHANISM (works whenever a hero-bearing object is loaded) + the SUSPEND fallback |

The convention specifies the **MECHANISM** (the highlight applies whenever a hero-bearing object is loaded — cases 1, 2, 3a) + the **SUSPEND fallback** (case 3b). **Whether to co-load the substrate at a given enzyme-cast node is a Phase 7 content decision** (per-enzyme, per the substrate's size + the pedagogical intent) — mirroring 05.3's "the mechanism is always specified; whether it fires is a per-enzyme Phase 7 decision" (05.3-CONVENTION.md §3). The Phase 5.4 prototype demonstrates case 3a (hero highlighted in a small co-loaded substrate + a placeholder enzyme); the large-enzyme visibility/zoom composition is Phase 9 (see §E).

### The four selection-rule options analyzed

| Option | Rule | Verdict |
|--------|------|---------|
| **(i) By element + name** | e.g. "the carbon named `C1` in glucose" | **FRAGILE — REJECT as sole rule.** Names differ across molecules (glucose C1, pyruvate C3, acetyl-CoA C2, citrate's prochiral carbons...). No consistent naming spans the pathway. A pure name rule breaks the first time the hero is in a molecule whose atoms aren't named "C1". |
| **(ii) Per-structure metadata `hero_selector`** | each loaded asset carries a `hero_selector` field (a selection expression like `"resi 1 and name C1"`) | **DETERMINISTIC + CLEAN.** Requires per-asset authoring (Phase 7). The selector EXPRESSION is a structural fact (which atom in the PDB); the CHOICE of which carbon is the hero is a pathway-science claim (Phase 7 per-claim approval — see §E). |
| **(iii) Mark-on-load** | a `hero_highlight` MolAction takes a selector + marks that atom (segi/flag/b-object/label) as the hero at load time; the marker persists for the session + is re-applied on `on_enter` replay | **This is the MECHANISM, not the selector source.** (iii) applies the highlight; (ii) provides the selector. They COMPOSE. The "persistence" is re-application on each `on_enter` (§C), NOT a session-only marker relied on across saves. |
| **(iv) Hybrid (RECOMMENDED)** | (ii) `hero_selector` from asset metadata is primary; a default HEURISTIC for single-carbon objects (the unique C); multi-carbon objects WITHOUT a `hero_selector` FAIL LOUDLY (no silent best-guess for real content); a documented best-guess is used ONLY for the prototype on placeholders (known-by-construction) | **RECOMMENDED.** Deterministic for authored assets; auto-derivation for the trivial single-carbon case (the `hero_atom` object); fail-loud for the ambiguous multi-carbon case (no-fabricated-science — the "which carbon" is a content decision). |

### Recommendation (§A) — the selection-rule contract

**Adopt the hybrid (iv): an explicit `hero_selector` per hero-bearing asset, with a single-carbon auto-derivation + a multi-carbon fail-loud gate.**

**The field:** `hero_selector` — a PyMOL atom-selection expression (string) that resolves to **EXACTLY ONE carbon atom** in the loaded object. Lives in: **asset metadata** (Phase 7-authored per asset), OR as an **explicit `hero_highlight` MolAction arg** (for the prototype + for objects where the selector is intrinsic, like the single-atom `hero_atom`).

**The resolution rule (deterministic, re-evaluated each `on_enter`):**
1. If the asset's metadata carries a `hero_selector` → use it (Phase 7-authored; deterministic).
2. Else if the object is a **single-carbon object** (`cmd.count_atoms("<obj> and elem C") == 1`) → the unique carbon IS the hero (auto-derived; deterministic — applies to `hero_atom` and any future single-carbon substrate).
3. Else (multi-carbon object, no `hero_selector`) → **FAIL LOUDLY** at the human-verify gate. For real content, the "which carbon is the hero" is a **pathway-science decision** (the hero is C1 of glucose *because that's the carbon that enters glycolysis* — a pathway fact, source-approved per the `AGENTS.md` no-fabricated-science rule). No silent best-guess. (The prototype on placeholder structures uses a **known-by-construction** selector — documented, not a heuristic.)

**Composes with the existing `{op:load, target:pdb:..., args:{object:...}}` pattern:** the `load` MolAction brings the hero-bearing object into the session; the `hero_highlight` MolAction (fired AFTER `load` in the `on_enter` sequence) takes the `hero_selector` + applies the highlight (§B). The convention specifies the `on_enter` ORDER (§C): `hide_all` → `load` → `show_as` → `hero_highlight` → `zoom`.

### The contract for the three placeholder structures Phase 5.4 prototypes on

*(All placeholders marked `pdb:TBD_*` — NO fabricated PDB IDs, per `AGENTS.md`.)*

**(a) Single-atom hero object** (`intro.preface`, `pdb:TBD_HERO_CARBON` → `"hero_atom"`):
- `hero_selector` = `"hero_atom and elem C"` (or simply `"hero_atom"` — the object IS the hero; the single-carbon auto-rule (step 2) applies).
- Verification: `count_atoms("hero_atom and elem C") == 1`. Trivial — the auto-derivation handles it; no Phase 7 authoring needed.

**(b) Glucose** (`intro.shell_glucose` / `gly.start`, `pdb:TBD_GLUCOSE` → `"glucose"`):
- Multi-carbon (6 C) → REQUIRES an explicit `hero_selector` (step 1, Phase 7-authored). For the prototype, the placeholder PDB is **hand-written with a known C1**, so the selector is known-by-construction: e.g. `"glucose and name C1"` (or `"glucose and resi 1 and name C1"`).
- Phase 7 fills the real selector for the real glucose PDB (which atom is C1 — a structural fact, source-approved) + the pathway fact (C1 is the hero because it enters glycolysis — source-approved).

**(c) An enzyme active site** (a placeholder enzyme + a co-loaded substrate, case 3a):
- The hero is in the **SUBSTRATE object** (co-loaded, e.g. `"substrate"`), NOT in the enzyme object (e.g. `"enzyme"`).
- `hero_selector` = a selector in the substrate object (e.g. `"substrate and name C1"`). The prototype demonstrates the hero highlighted in a small substrate alongside a placeholder enzyme. The enzyme keeps its cast representation (cartoon, its own color); the dim (§B) is scoped to the substrate, NOT the enzyme.
- The large-enzyme visibility/zoom (when the substrate is tiny vs a huge enzyme like 1OCC) is **Phase 9** (§E) — the 5.4 prototype uses a small enough placeholder enzyme that the hero is visible without active-site zoom.

## §B. Color + representation + label of the hero

### Color — a colorblind-safe named default

**Phase 10 owns the full colorblind-safe palette** (`ROADMAP.md` Phase 10), but 5.4 picks a default that is colorblind-safe + documents it so Phase 6 implements an already-reviewed choice.

**Recommendation: a named color `hero_gold`.** Define via `cmd.set_color("hero_gold", [0.90, 0.62, 0.0])` (the Okabe-Ito colorblind-safe palette's orange/amber #E69F00 — the established colorblind-safe standard for scientific visualization). Rationale:
- **Colorblind-safe** — Okabe-Ito orange is distinguishable under deuteranopia/protanopia/tritanopia (the palette was designed for this; Okabe-Ito 2008).
- **Distinctive** — gold/amber does not collide with the common enzyme cast colors (green cartoon, blue sticks) nor with the dim gray (§spotlight) nor with standard atom colors (CPK red O / blue N / white H).
- **"Heroic"** — warm gold reads as "the protagonist / the treasure / the highlighted one" to the player.

**Alternative considered:** `hero_cyan` — also colorblind-safe but collides with common atom/stick colors; less distinctive as a "hero" read. `hero_yellow` — colorblind-safe but low-contrast against gray dim. Recommend `hero_gold`; flag for Phase 10 finalization at the §F checkpoint.

> **API grounding (HIGH confidence, read from source):** `cmd.set_color(name, rgb)` exists at `tmp/pymol-src/modules/pymol/viewing.py:2107-2136` — defines a named color from RGB in (0.0,1.0) or (0,255). `cmd.color(color, selection)` exists at `viewing.py:1858` (already dispatched by `molops.py:129-131` as `op="color"`). The sibling API researcher verifies the exact RGB + the `recolor`-after-`set_color` note (`viewing.py:2135`).

### Representation — spheres, scaled up

**Recommendation: the hero is shown as SPHERES, scaled UP** so it stands out among the other atoms (sticks/cartoon). The skeleton ALREADY uses `show_as spheres` for `hero_atom` (`intro.json:11`) — the convention builds on this.

- `cmd.show_as("spheres", "<hero_sele>")` — hero as spheres (turns off other reps atomically, `viewing.py:528`; already dispatched as `op="show_as"`).
- `cmd.set("sphere_scale", <radius>, "<hero_sele>")` — scale the hero sphere UP. Default PyMOL sphere_scale is ~0.25; recommend **`sphere_scale = 1.0`** for the hero (4x the default — clearly visible; the exact value is a §F checkpoint item + the sibling verifies the per-atom selection scoping of `sphere_scale`).
- Non-hero atoms in the hero-bearing object: their existing representation (sticks for substrates, cartoon for enzymes) — NOT spheres — so the hero sphere stands out.

> **API grounding (HIGH confidence):** `cmd.set(name, value, selection, ...)` exists at `tmp/pymol-src/modules/pymol/setting.py:183` — supports per-atom selection scoping (the `selection` arg). `cmd.show_as` at `viewing.py:528`. The sibling verifies `sphere_scale` accepts per-atom selection scoping (vs per-object only) — the convention's `set sphere_scale <hero_sele>` assumes per-atom; if per-object-only, the dispatch falls back to a per-object setting on a hero-only object (the `hero_atom` case is already per-object).

### Label — "C14" (the isotope tracking label, NOT the fate)

**Recommendation: label the hero `"C14"`.**

- The label is the hero's **isotope tracking label** (the "C14" name tag from `spec.md` / `PROJECT.md` — "the player controls a C14 atom, the hero"). It is the hero's IDENTITY LABEL, not a fate claim.
- **MANDATORY anti-confusion note (AGENTS.md + PROJECT.md row 107):** "C14" is the **tracking isotope label**, NOT the hero's fate or identity-as-ATP. The carbon body is shed as CO2; its electrons (the "soul") flow via NADH/FADH2 → ETC → ATP. The label "C14" does NOT assert the carbon becomes ATP, enters oxidative phosphorylation, or radioactively decays (C14-decay was DROPPED, `PROJECT.md` row 108). The label is purely "this is your atom; here is its name tag."
- Label expression: `cmd.label("<hero_sele>", '"C14"')` — per `viewing.py:1364` ("All strings in the expression must be explicitly quoted"), the expression is a **quoted string literal** `'"C14"'` (single-quoted Python string containing a double-quoted PyMOL literal). This is a footgun for story authors → encapsulated by the `hero_highlight` op (§C).
- **Alternative label wording** (§F checkpoint): `"YOU"` (player-facing "this is you") as an OPTIONAL secondary label; `"HERO"`. Recommend `"C14"` primary (the canonical identity); the human may prefer `"YOU"` for player-friendliness.

### The spotlight — dim non-hero atoms (scoped)

**Recommendation: dim non-hero atoms in the hero-bearing object to `gray80`** (the "spotlight" effect — the hero gold sphere pops against a dim background).

- `cmd.color("gray80", "<hero_obj> and not <hero_sele>")` — dim the non-hero atoms IN THE HERO-BEARING OBJECT.
- **CRITICAL scoping:** the dim is scoped to the **hero-bearing object's** non-hero atoms, NOT globally. At `intro.preface`, the `aa_cast` object (the 20-AA cast, cartoon) is a SEPARATE object — the dim must NOT dim the cast (the cast is the cast, shown in its own color). At enzyme-cast case-3a nodes, the dim is scoped to the **substrate** object (the hero-bearing object), NOT the enzyme (the enzyme keeps its cast color). The dim is a within-hero-object spotlight, not a global mute.

## §C. Persistence across MolAction replay + save/load + the CO2-shed climax

### Persistence — the highlight is a pure function of `on_enter`, re-derived each replay

**The key finding (HIGH confidence, read from `c14/engine.py:20-22, 163-194, 203-213`):**

- `engine.py:20-22` (docstring): *"the molecular scene is a pure function of game state, NOT a saved .pse session -- Anti-Pattern 5 avoided."*
- `engine.load` (`engine.py:203-213`): restores `GameState` + rebuilds `RngEngine` + **`return self._enter(self.state.current_node, record_visit=False)`** — re-enters the current node, **replaying its `on_enter` MolActions** to reconstruct the scene.
- `_enter` (`engine.py:163-194`): runs `on_enter` + dispatches each MolAction per-action to the sink (`engine.py:187-189`).

**Therefore:** the hero-highlight is **re-derived from the deterministic `hero_selector` rule (§A) + re-applied by the `hero_highlight` MolAction EVERY time the node is entered** — on `start`, `choose`, `apply_player_edit`, AND `load` (save/load). It CANNOT depend on session-only state (a `cmd.flag`/`cmd.alter` b-object set once and relied on across saves). Any marker is a RUNTIME convenience, re-set each `on_enter`.

**This is the "persistence across MolAction replay" the SC1 demands** (`ROADMAP.md:187`): the highlight survives (1) `on_enter` replay when re-entering a node, and (2) save/load — BECAUSE on save/load the `on_enter` replays from scratch and re-applies the highlight. It is NOT stored in PyMOL session state; it is re-derived from the deterministic rule each time.

> **Marker note (medium confidence):** `cmd.flag("focus", "<hero_sele>")` (`editing.py:2538-2587`; flag 0 = "focus" = "Atoms of Interest") and `cmd.alter("<hero_sele>", "b=99")` (`editing.py:1424`) are both available as RUNTIME markers (a 32-bit flag / a b-object value). They MAY be used WITHIN a single `on_enter` sequence so subsequent MolActions can reference "the hero" by the marker. But they are **re-set each `on_enter`** (not relied on across saves) — the deterministic `hero_selector` is the cross-save source of truth. The convention does NOT require a marker; the `hero_selector` + the `hero_highlight` op suffice. (The sibling API researcher verifies whether a marker is needed for the dim's `not <hero_sele>` selection to compose correctly.)

### The canonical `on_enter` sequence for a "hero stage" node

```jsonc
// A node where the hero is highlighted in a loaded substrate (case 2 / 3a)
"on_enter": [
  {"op": "hide_all"},                                                              // 1. clear the scene
  {"op": "load", "target": "pdb:<asset>", "args": {"object": "<hero_obj>"}},        // 2. load the hero-bearing structure
  {"op": "show_as", "target": "<hero_obj>", "args": {"rep": "sticks"}},             // 3. base representation (sticks for substrates; cartoon for enzymes)
  {"op": "hero_highlight", "target": "<hero_obj>", "args": {                        // 4. the hero highlight (encapsulates §B's 6 calls)
    "selector": "<hero_selector>",   // e.g. "glucose and name C1" (Phase 7-authored) or "hero_atom and elem C" (auto)
    "label": "C14",                  // the isotope tracking label (NOT the fate)
    "color": "hero_gold",            // colorblind-safe default
    "scale": 1.0,                    // sphere_scale
    "dim": "gray80"                  // dim non-hero in <hero_obj> (scoped — NOT the cast/enzyme)
  }},
  {"op": "zoom", "target": "<hero_obj>"}                                           // 5. frame the hero-bearing object
]
```

For the **single-atom `hero_atom`** (`intro.preface`, case 1), the sequence is simpler — no `dim` (a single atom has no non-hero atoms in its object), and the `aa_cast` co-load + `show_as cartoon aa_cast` happen alongside (the cast is a separate object, not dimmed):
```jsonc
"on_enter": [
```
