"Gate green at phase end" concretely means: every `claim_id` in the 7 manifest-listed story files is `approved` in `data/citations.json` — including the two `PLACEHOLDER_PHASE8` stub references that are Phase 8 scope but gate-blocking today (a planner decision).

The citation workflow's operational shape: sources are registered then approved in `data/sources.json` (the gate never reads this file — approval is recorded there, enforced via claims), claims land in `data/citations.json` with `approval_status == "approved"` (strict equality, `rpg/citations.py:109`), and the extended hybrid-workflow fields (`review_tier`, `inherits_source_approval`, `review_notes`, `source_id`, `claim_text`) load cleanly and are ignored by the loader — the Phase 5 precedent shows the exact record shape to replicate. Batch-by-source ordering keeps human burden low: one source approval unlocks every routine claim that inherits it.

**Primary recommendation:** slice Phase 7 into ~18–22 fine-grained plans in 5 waves — [registry/infra + source-approval checkpoints] → [per-segment content plans, parallel-safe per story file] → [edits.json + restoration branches] → [cross-cutting passes: claim-swap completion, scene-template fills, test-count updates] → [final gate-green verification]. Shared files (`data/citations.json`, `tests/test_glucose_reachability.py`, `rpg/data/edits.json`) get single-owner plans per wave; per-segment story files are disjoint and parallel-safe.

## 4. edits.json authoring spec + restoration-branch analysis

### 4.1 Schema (from rpg/edit_router.py + tests/fixtures/edit_routing/edits.json + Phase 4 tests)

```json
{
  "version": 1,
  "bad_ending_pool": ["bad.lost_connection", "bad.released_from_host"],   // global pool (MUST be non-empty; pool nodes must be endings)
  "enzymes": {
    "<enzyme_id>": {                       // enzyme_id == the node tag edit:enzyme:<id> value
      "edits": [
        {
          "signature": {"op": "point_mutation", "target": "resi 209 and chain a", "args": {"new_res": "GLY"}},
          "branch_node": "gly.pfk.restored",     // MUST exist in the story graph (validate_edits_table: dangling_edit_branch)
          "claim_id": "DIS-PFKM-01"              // NOT gate-checked (see §2.5); convention: the claim backing the known-edit fact
        }
      ],
      "bad_ending_pool": ["bad.cofactor_lost"]   // OPTIONAL per-enzyme override (non-empty wins over global; OVERRIDE semantics, not merge)
    }
  }
}
```

**Signature normalization contract (EditIntent.signature(), rpg/story/model.py:112-126):** `{op verbatim, target.strip().lower(), {k: str(v) or json.dumps(sort_keys=True) for dicts/lists}}`. Compared with `==` against the table entry (edit_router.py:142). Practical rules for authors:
- `op` ∈ `point_mutation` | `substrate_edit` | `protonation_change`.
- **Write the `target` in edits.json already lowercase** (e.g. `"resi 209 and chain a"`) — the dialog reads the signature verbatim and the router lowercases, so lowercase keeps the round-trip identity-proof.
- point_mutation args key is **`new_res`** (EditIntent side). The routed branch node's `on_enter` **`MolAction(op="edit")` uses DIFFERENT keys: `edit_type`, `sele`, `new_resn`** (molops.py:252-254: `point_mutation(target, args["sele"], args["new_resn"])`). Two carriers, two arg names — do not mix them.
- Duplicate signatures within one enzyme → `duplicate_signature` issue (validate_edits_table:207-211).
- Unknown edit / unknown enzyme → per-enzyme pool if non-empty else global pool, picked uniformly via the injected RngEngine (`weighted_pick(pool, [1.0]*n)`) — seeded-reproducible. Empty pool → `EditRoutingError` (fail-loud).

### 4.2 What the EditDialog does with the table (rpg/ui/edit_dialog.py — verified)

- Known entries are offered as radio options labeled `"Restore <target> to <new_res> (the correct fix)"` with `(op, target, args)` taken **verbatim from the signature** — so the player's known-fix EditIntent matches the table by construction. **The dialog is the restoration UX: filling edits.json IS wiring the correct-fix choice.**

## 5. cast.json + PDB asset pipeline

### 5.1 How a `pdb:XXXX` on_enter load resolves (verified end-to-end)

`MolAction(op="load", target="pdb:XXXX", args={"object": ...})` → molops target-prefix fallback (molops.py:221-225) → `AssetManager.fetch_pdb(code, obj)` → `cmd.fetch(code, obj, type="pdb", async_=0, path=rpg/data/assets/downloaded)` (asset_manager.py:114-127). **This is a NETWORK fetch on first encounter.** PyMOL's fetch reuses a local file when present (importing.py:1211-1213: `elif os.path.exists(file): # skip downloading`) — so once `rpg/data/assets/downloaded/<code>.lower().pdb` exists (via the bulk download or a prior fetch), on_enter loads work OFFLINE. The `downloaded/` dir is gitignored and excluded from the zip (Pitfall 4) — users get it via the 06-10 bulk-download prompt.

### 5.2 Bundled vs fetched (hybrid decision, PROJECT.md row 103)

- Bundled = `rpg/data/assets/bundled/` (committed, ships in zip; loads via `load_bundled`, target = bare filename e.g. `_smoke.pdb`). Currently only fixtures (5 files). **Start nodes are tested to be bundled-only** (`test_start_nodes_do_not_reference_real_pdb_fetch` — no `pdb:` targets on intro.preface/shell_glucose/select).
- Fetched = cast.json entries with `source: "download"` + real `pdb_id` → `missing_large_pdbs()` (bulk_download.py:120-177) checks `downloaded/<pdb_id>.lower().pdb`, fetches missing ones pre-play, locks the character on failure (`characters_to_lock`). The `PLACEHOLDER` pdb_id guard currently keeps the prompt silent.
- Phase 7 must populate cast.json with real entries (id/label/source/pdb_id/character/claim_id) for the enzymes the story loads: 4PFK, 7FS3, 6CFO, 5W8J, 1CSC, the aconitase cast PDB, 5GRF, 1OCC. Which are bundled vs download is a zip-size/latency tradeoff — **Checkpoint M8**. Note: bundling a real PDB into the repo makes it a committed asset (license/repro fine for RCSB files, but the human should approve the list).
- 6 PDBs are ALREADY in the local dev cache `rpg/data/assets/downloaded/` (1crn, 1csc, 1occ, 4pfk, 5grf, 6cfo, 7fs3 — from Phase 6 dev), which speeds human-verify but proves nothing about fresh installs.

## 7. Flag-setter mechanism options (`host_o2_low`)

**Current state (verified):** the reader exists — `pyr.branch` aerobic choice `cond: "not flags.get('host_o2_low')"` + anaerobic choice `cond: "flags.get('host_o2_low')"` (the 06-05 dict-method fix; runtime-eligibility tested in `TestPyrBranchRuntimeEligibility`, 5 tests). **Option B — weighted RNG "host condition" event node (data-only + 1 new node).** A new node (e.g. `pyr.host_condition`) with 2 weighted choices (e.g. w=0.85 air fine / w=0.15 air runs low), each with `effects.set host_o2_low false/true`, both → pyr.branch. **Option D — manifest/character config `initial_flags` → ENGINE SURGERY** (GameState.new_game + engine.start + manifest schema + save-compat). Violates "content + data + minimal hooks". **Flag only; do not plan.**

## 8. Approval workflow operational loop (hybrid, PROJECT.md row 109 — mechanics)

**Files + schemas (from the approved Phase 5 batch — copy these shapes exactly):**
- `data/sources.json`: `{ "<SOURCE-ID>": { reference, url?, license?, pdb_doi?, source_type, approval_status, approved_by: "human", approved_date, notes } }`. `rejected` entries are RETAINED for provenance (LEHNINGER-CH-CITRIC_ACID_CYCLE precedent) and fail the gate identically to pending — but note the gate never reads sources.json; rejection is recorded here and by NOT approving claims.
- `data/citations.json`: `{ "<CLAIM-ID>": { claim (short), source_type, source, claim_text, source_id, review_tier: "routine"|"high-stakes", inherits_source_approval: bool, review_notes (required for high-stakes + on source changes), pdb_id?/resolution_angstrom? for PDB claims, approval_status, approved_by: "human", approved_date } }`. **Loader requirements (rpg/citations.py:68-98):** JSON object, unique keys, every entry a dict, `approval_status` ∈ valid set. All other fields are load-and-ignore.
- Workflow routing per tier: **high-stakes** (RNG weights, protonation defaults, carbon-fate, contested) → individual per-claim review with `review_notes` evidence trail; **routine** (enzyme-catalyzes-X, name/EC/cofactor, PDB existence/resolution, pathway ordering) → source-inherited fast-track + the two visibility flags; the human spot-checks at leisure (non-blocking).

**The operational loop per plan (recommended cadence: one approval checkpoint per segment plan):**
1. **Candidate presentation:** the plan's checkpoint (GSD `checkpoint:decision` / `checkpoint:human-verify` per repo convention) lists, grouped BY SOURCE: proposed source records (reference, URL, license) + each claim's `claim_text` + proposed claim_id + tier. Sibling research supplies the evidence; the mechanics plan only needs the ledger format.
2. **On approval:** agent writes `sources.json` entries (`approved`) + `citations.json` entries (`approved`, `review_tier`, `source_id`, flags) in the SAME commit as the story-JSON claim_id swap for that segment.
3. **Immediate gate re-run** (§3 block) — red until the segment's swaps complete is fine mid-phase; the phase-final plan requires exit 0.
4. **Rejection path:** record the source `rejected` in sources.json (provenance), do not delete; find an alternative source; re-checkpoint.

**Batch-by-source ordering (burden minimizer):** group a segment's claims so one source approval unlocks N claims — e.g. all LibreTexts-glycolysis claims in one checkpoint; all RCSB PDB entries are inherently 1:1 (source==structure) but each is a single routine approval. Front-load: a single early plan can register ALL candidate sources as `pending` + present the full Phase 7 approval ledger, letting the human approve in 2–3 sittings instead of 20 (this mirrors Phase 5's 05-04 → 05-05 shape: populate-pending auto, approve human).
