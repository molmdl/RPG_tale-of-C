## Summary

This is the API-facts file for Phase 5.3. Every signature below is read from `tmp/pymol-src/modules/pymol/fitting.py` (PyMOL 2.5.0 open-source, read-only symlink) and cited `file:line`. The four claims the planner most needs — and which were previously MEDIUM/unverified — are **empirically confirmed** here via a scratch headless run (command + raw output in §A.5):

1. **`cmd.align`/`cmd.super` return a TUPLE** `(RMSD, natoms, …)`: `ret[0]` = post-outlier-rejection RMSD (float), `ret[1]` = matched-atom-count (int). Capturable programmatically as `rmsd, natoms = cmd.align(mobile, target)[0], cmd.align(mobile, target)[1]`. (`fitting.py:306` align, `fitting.py:242` super.)
2. **Mobile moves, target stays fixed.** `cmd.align(mobile, target)` transforms `mobile` into `target`'s frame; `target` is the FIXED reference. Empirically: `align("wt","mut")` moved `wt` (x: 5→0) and left `mut` at 0. **Critical naming-collision pitfall:** PyMOL's `target` arg means *fixed reference* — the opposite of English "target = thing aimed at." See §G Pitfall 1.
3. **Selection scoping works + transforms the whole object.** `cmd.align("wt and name CA", "mut and name CA")` aligned on the 2 CA atoms and transformed the WHOLE `wt` object (x: 5→0). This is the mechanism for domain-shift mutants: align on a stable core substructure, the whole object moves into the reference frame (§C).
4. **`cmd.super`/`cmd.align`/`cmd.rms_cur`/`cmd.rms` all run headlessly** via `run-conda-pymol.bat -cq` (cmd-only, no viewer). `cmd.cealign` also runs headlessly but **fails on tiny fixtures** (`len(sel) >= 2*window`, default window=8 → ≥16 CA atoms; `fitting.py:81-92`) — so the prototype must use `super`/`align`, NOT `cealign`. `cmd.superpose` does **not exist** in PyMOL 2.5.0 (§B).

**Primary recommendation:** The WT-aligned load uses **`cmd.super` as the default method** (sequence-independent structural alignment — the right tool for the phase's "major conformational difference (domain shift)" case, per the `align` docstring at `fitting.py:317-320`), scoped to a **stable-substructure CA selection** for domain-shift mutants, with the **WT as `mobile`** (moved into the edited-mutant's frame so the camera doesn't jump). Expose this as a single new **`MolAction(op="align", …)`** dispatch in `MolOps` — mirroring the existing `load` (args["source"]) / `edit` (args["edit_type"]) multi-method dispatch pattern — with `args["method"]` ∈ `{"super"|"align"|"cealign"}` (default `"super"`). The op is pure data (no pymol import in `c14/story/model.py`), so the domain-tier AST gate holds; the dispatch branch lives in `molops.py` (gate-excluded `pymol_layer/`). The prototype verifies via **atom-count + finite-RMSD + coords-changed** post-conditions (NOT a hardcoded RMSD threshold — placeholder geometry makes thresholds meaningless; §D).

## §A. Signatures + return values (file:line cited; empirically verified)

All functions are defined in `tmp/pymol-src/modules/pymol/fitting.py` and bound to `cmd.<name>` via PyMOL's keyword system (verified empirically: `from pymol import cmd; cmd.align(...)` resolves to `fitting.align`). The project's citation convention is `# src: tmp/pymol-src/modules/pymol/fitting.py:<line> cmd.<name>` on the line above the call.

### A.1 `cmd.align` — sequence alignment + structural superposition (`fitting.py:306`)

```python
# src: tmp/pymol-src/modules/pymol/fitting.py:306 cmd.align
def align(mobile, target, cutoff=2.0, cycles=5, gap=-10.0,
          extend=-0.5, max_gap=50, object=None, matrix="BLOSUM62",
          mobile_state=0, target_state=0, quiet=1, max_skip=0,
          transform=1, reset=0, *, _self=cmd):
```

| param | default | meaning |
|-------|---------|---------|
| `mobile` | (required) | atom selection of the MOBILE object (**moved** by the superposition) |
| `target` | (required) | atom selection of the FIXED reference object (**stays**) |
| `cutoff` | 2.0 | outlier-rejection cutoff in Å |
| `cycles` | 5 | max outlier-rejection cycles (set `cycles=0` for all-atom RMSD with NO outlier rejection — `fitting.py:359-361`) |
| `gap`/`extend`/`max_gap` | -10.0/-0.5/50 | sequence-alignment gap penalties |
| `object` | None | name of an alignment-viz object to create (paired-atom indicators) |
| `matrix` | "BLOSUM62" | substitution matrix for the sequence alignment |
| `mobile_state`/`target_state` | 0/0 | object state (0 = all states) |
| `quiet` | 1 | 0 = print RMSD to stdout; 1 = silent; -1 = print rotation matrix |
| `transform` | 1 | **1 = apply the superposition to `mobile` (default); 0 = compute RMSD only, don't move** |
| `reset` | 0 | 1 = delete an existing alignment object first |

**Return value:** `r = _cmd.align(...)` then `return r` (`fitting.py:394`). **Empirically a TUPLE** — see §A.5. `ret[0]` = post-outlier-rejection RMSD (float); `ret[1]` = matched-atom-count (int); the remaining elements are internal alignment stats. Confirmed by `extra_fit`'s return-handling at `fitting.py:183-184`: `if _self.is_sequence(x): print('… RMSD = %8.3f (%d atoms)' % (model, x[0], x[1]))`.

**When to use:** same-protein / >30% sequence identity (`fitting.py:317-320`: *"align does a good job on proteins with decent sequence similarity (identity >30%). For comparing proteins with lower sequence identity, the super and cealign commands perform better."*).

### A.2 `cmd.super` — sequence-INDEPENDENT structural alignment (`fitting.py:242`)

```python
# src: tmp/pymol-src/modules/pymol/fitting.py:242 cmd.super
def super(mobile, target, cutoff=2.0, cycles=5, gap=-1.5, extend=-0.7,
          max_gap=50, object=None, matrix="BLOSUM62", mobile_state=0,
          target_state=0, quiet=1, max_skip=0, transform=1, reset=0,
          seq=0.0, radius=12.0, scale=17.0, base=0.65, coord=0.0,
          expect=6.0, window=3, ante=-1.0, *, _self=cmd):
```

| param | default | meaning |
|-------|---------|---------|
| `mobile`/`target` | (required) | same as `align`: `mobile` MOVED, `target` FIXED |
| `cutoff`/`cycles` | 2.0/5 | outlier rejection (same semantics as `align`) |
| `gap`/`extend` | -1.5/-0.7 | **different defaults than `align`** (-10.0/-0.5) — `super` weights structural similarity over sequence |
| `transform` | 1 | same as `align` (1 = move `mobile`) |
| `seq`/`radius`/`scale`/`base`/`coord`/`expect`/`window`/`ante` | various | `super`-specific tuning knobs for the structural-alignment scoring; **leave at defaults** for the convention |

**Return value:** `r = _cmd.align(...)` then `return r` (`fitting.py:304`) — same C call as `align`, **empirically a TUPLE** with the same `[0]=RMSD, [1]=natoms` shape (see §A.5).

**When to use:** low sequence identity / conformational divergence / domain shifts — the phase's primary case. **DEFAULT METHOD for the convention.**

### A.3 `cmd.cealign` — CE algorithm; DIFFERENT arg order + return type (`fitting.py:27`)

```python
# src: tmp/pymol-src/modules/pymol/fitting.py:27 cmd.cealign
def cealign(target, mobile, target_state=1, mobile_state=1, quiet=1,
            guide=1, d0=3.0, d1=4.0, window=8, gap_max=30, transform=1,
            object=None, *, _self=cmd):
```

| param | default | meaning |
|-------|---------|---------|
| **`target`** | (required, 1st arg) | **REVERSED arg order vs `align`/`super`** — `cealign(target, mobile)`, NOT `(mobile, target)`. Critical pitfall (§G Pitfall 2). |
| **`mobile`** | (required, 2nd arg) | the MOBILE object (moved) |
| `guide` | 1 | 1 = align on CA (guide) atoms only (default); 0 = all atoms |
| `window` | 8 | CE window size; **requires `len(selection) >= 2*window`** (≥16 CA atoms with default `guide=1`, `window=8`) — `fitting.py:81-92`. **Fails on tiny placeholder fixtures.** |
| `transform` | 1 | same as `align`/`super` |

**Return value:** a **DICT** `{"alignment_length": aliLen, "RMSD": RMSD, "rotation_matrix": rotMat}` (`fitting.py:135`) — DIFFERENT from `align`/`super`'s tuple. Capture RMSD as `cmd.cealign(target, mobile)["RMSD"]`.

**When to use:** the hardest structural alignments (very low homology, large domain rearrangements) where even `super` fits poorly. **NOT for the Phase 5.3 prototype** (tiny fixture fails the min-size check); an option for Phase 7 real-structure content. The `op="align"` dispatch must **handle the reversed arg order** (§E).

### A.4 `cmd.rms_cur` / `cmd.rms` / `cmd.fit` — RMSD utilities (no sequence alignment)

```python
# src: tmp/pymol-src/modules/pymol/fitting.py:666 cmd.rms_cur  (NO fit, NO transform — raw current RMSD)
def rms_cur(mobile, target, mobile_state=0, target_state=0, quiet=1,
            matchmaker=0, cutoff=2.0, cycles=0, object=None, *, _self=cmd):

# src: tmp/pymol-src/modules/pymol/fitting.py:620 cmd.rms  (fits internally to compute min RMSD, does NOT transform)
def rms(mobile, target, mobile_state=0, target_state=0, quiet=1,
        matchmaker=0, cutoff=2.0, cycles=0, object=None, *, _self=cmd):

# src: tmp/pymol-src/modules/pymol/fitting.py:543 cmd.fit  (superposes matching atoms; matchmaker-based, no seq alignment)
def fit(mobile, target, mobile_state=0, target_state=0, quiet=1,
        matchmaker=0, cutoff=2.0, cycles=0, object=None, *, _self=cmd):
```

**Return values:** all three **return a FLOAT** (the RMSD), empirically confirmed (§A.5). Key distinction:
- **`rms_cur`** — the CURRENT RMSD between the two selections as they sit now (no fitting, no transform). Use to *measure* divergence after an align.
- **`rms`** — computes the RMSD after an optimal fit internally, but does **NOT** apply the transform (empirically: `rms("wt","mut")` returned 0.0 and `wt` stayed at its translated position). Use to *know what the post-fit RMSD would be* without moving anything.
- **`fit`** — superposes (transforms `mobile`) on matching atoms with NO sequence alignment; only useful for very similar structures (same atom ordering). Use `matchmaker=0` (default) for identifier-matched atoms.

`matchmaker` (`fitting.py:567-572`): 0/1 = match on all atom identifiers (segi,chain,resn,resi,name,alt); -1 = assume identical atom order; 2 = by ID; 3 = by rank; 4 = by index.

## §B. align vs super vs superpose — when to use which

**`cmd.superpose` does NOT exist in PyMOL 2.5.0.** I read `fitting.py` in full (756 lines): the defined alignment functions are `cealign`, `extra_fit`, `alignto`, `super`, `align`, `intra_fit`, `intra_rms`, `intra_rms_cur`, `fit`, `rms`, `rms_cur`, `pair_fit`. There is no `superpose`/`cmd.superpose`. ("Superposition" appears in docstrings as a noun; `super` is the verb.) The planner should NOT look for a `cmd.superpose` — use `super`/`align`/`cealign`.

| Method | Algorithm | Best for | Arg order | Return | Min size |
|--------|----------|----------|-----------|--------|----------|
| `align` | sequence alignment + structural refinement (outlier rejection) | same protein / >30% seq identity; same-protein point mutants (e.g. 6CFO WT vs 6CER V138M — identical sequence, one residue) | `(mobile, target)` | tuple `[0]=RMSD [1]=natoms` | none (works on 2 residues) |
| `super` | sequence-INDEPENDENT structural alignment + refinement | low homology; **conformational divergence / domain shifts** (the phase's primary case); unknown conformational state | `(mobile, target)` | tuple `[0]=RMSD [1]=natoms` | none (works on 2 residues) |
| `cealign` | CE (Combinatorial Extension) — pure structural, no sequence | the hardest cases (very low homology, large rearrangements) where `super` fits poorly | **`(target, mobile)` — REVERSED** | dict `{"RMSD", "alignment_length", "rotation_matrix"}` | **≥ `2*window` CA atoms** (default 16) — fails on tiny fixtures |
| `fit` / `pair_fit` | direct atom-pair superposition (no sequence alignment) | very similar structures with matched atom ordering | `(mobile, target)` | float | none |

**Recommendation for Phase 5.3:**

- **Default method: `cmd.super`.** Per the `align` docstring (`fitting.py:317-320`), `super` is the right tool for "proteins with lower sequence identity" / structural divergence. The phase goal explicitly targets "mutants with major conformational differences (e.g. a large domain shift)" — `super`'s sequence-independent scoring handles the case where sequence homology is confounded by conformational divergence. `super` also works on the tiny placeholder fixture (empirically confirmed), so it is the right default for BOTH the prototype and the real-structure convention.
- **`cmd.align` as the option for known same-protein point mutants.** For the realistic cast case of a same-protein point mutant (e.g. 6CFO WT vs 6CER V138M — one residue, identical sequence), `align` is sufficient and faster (the sequence alignment is trivial for identical sequence; the structural refinement rejects outliers). For a single-residue point mutant that does NOT cause a domain shift, `align` over the whole structure or over CA gives a good fit. **Does it matter?** For a non-domain-shift point mutant, `align` and `super` give near-identical results; `align` is the conventional choice. The convention lets the scene author pick via `args["method"]`; default `"super"` is the safer choice for unknown conformational states.
- **`cmd.cealign` as the Phase 7 option for true hard cases.** Only when `super`'s fit is poor (low `ret[1]` or high `ret[0]` on a real structure). NOT in the prototype (tiny fixture fails). The `op="align"` dispatch handles its reversed arg order + dict return (§E).
- **Do NOT use `fit`/`pair_fit`** for the WT-aligned load — they assume matched atom ordering / very similar structures, which a domain-shift mutant violates.

## §C. Selection scoping for domain-shift mutants (empirically confirmed)

**Confirmed:** `cmd.align("wt and name CA", "mut and name CA")` aligned on the 2 CA atoms and **transformed the WHOLE `wt` object** (`AFTER align(wt+CA, mut+CA): wt x=0.000 (whole wt object moved)`). Both `align` and `super` accept arbitrary atom selections as `mobile`/`target` (`fitting.py` selection-processing at lines 277-278 / 372-373); `transform=1` (default) applies the superposition to the whole object(s) referenced by the selection, not just the matched atoms.

**Why this matters for domain-shift mutants:** a global `cmd.super` over all atoms of a domain-shift mutant gives a poor, misleading fit — the outlier-rejection cycles discard the shifted domain, the RMSD is dominated by the shift, and the "restored" overlay looks wrong. The fix (recommended by the sibling design file §C and confirmed feasible here):

- **Align on a stable substructure** (a conserved domain / active-site core / set of CA atoms unlikely to move) — e.g. `cmd.super("<enzyme>_wt and name CA and resi 100-160", "<enzyme> and name CA and resi 100-160")`.
- The **whole `<enzyme>_wt` object** then moves into the `<enzyme>` frame using the transform derived from the stable core.
- The shifted domain shows as the conformational difference (the player SEES the domain shift as the offset between the aligned WT and the mutant) — exactly the "this is what healthy looks like / here's the real WT vs your edited model" payoff the phase wants.

**Convention contract for the selection:** expose it as `args["align_sele"]` (a selection fragment like `"name CA and resi 100-160"`, default `"name CA"`). The dispatch composes `"{mobile} and {align_sele}"` / `"{reference} and {align_sele}"` (mirroring the protonation.py `_apply_alter` target-scoping pattern at `protonation.py:215-217`, which scopes each `h_op` sele to `"{target} and {h_op_sele}"` to avoid cross-object bleed). Default `align_sele="name CA"` is the standard structural-alignment choice (CA-only, residue-paired); domain-shift mutants override it to a stable-core CA selection authored in Phase 7.

## §D. RMSD capture + verification post-condition recommendation

### How to capture the RMSD programmatically

| Method | Capture expression | Returns |
|--------|-------------------|---------|
| `cmd.align` / `cmd.super` | `ret = cmd.align(mobile, target); rmsd = ret[0]; natoms = ret[1]` | tuple — `ret[0]`=RMSD, `ret[1]`=matched atoms (empirically confirmed §A.5) |
| `cmd.cealign` | `ret = cmd.cealign(target, mobile); rmsd = ret["RMSD"]; nres = ret["alignment_length"]` | dict (DIFFERENT — note the reversed arg order) |
| `cmd.rms_cur` | `rmsd = cmd.rms_cur(mobile, target)` | float — current RMSD, no fit, no transform |
| `cmd.rms` | `rmsd = cmd.rms(mobile, target)` | float — post-fit RMSD, does NOT transform |

**For the WT-aligned load's runtime:** `MolOps.apply()` currently returns `None` for all ops (the engine does not consume MolAction return values). The `op="align"` dispatch should follow suit — call `cmd.super(...)`, **discard** the RMSD tuple (or log it at `quiet=0`), return `None`. Surfacing the RMSD to the UI ("aligned with RMSD 1.2 Å") is a **Phase 6 enhancement**, not a v1 requirement; the smoke verifies the return directly (see §F).

### Verification post-condition for the headless prototype — recommendation

The prototype runs on a **placeholder/bundled structure** (hand-written tiny PDB, approximate/arbitrary coordinates — NOT real science). The project's existing headless smokes (`tools/edit_smoke.py`, `tools/protonation_smoke.py`) use **atom-count + residue-signature** post-conditions (`edit_ops.py:246-255`). For alignment verification on a placeholder:

- **A hardcoded RMSD threshold is NOT robust.** The placeholder has arbitrary coordinates; the "expected" RMSD is meaningless (an identical-copy pair gives RMSD ≈ 0; a shifted pair gives RMSD = the offset). A threshold either always passes (too loose) or is brittle to fixture tweaks. **Do not assert `RMSD < X` on a placeholder.**
- **Atom-count + finite-RMSD + coords-changed IS robust** — it proves the align API was called correctly + produced a finite alignment + actually transformed the mobile, without claiming a scientific RMSD.

**Recommended post-conditions** (all assertable headlessly via `run-conda-pymol.bat -cq`; matches the sibling design file §E):

1. **Both objects non-empty after `load`** — `cmd.count_atoms("<mut>") > 0` AND `cmd.count_atoms("<wt>") > 0` (reuses the `asset_manager.load_bundled` post-condition pattern, `asset_manager.py:90-94`).
2. **The align call returned a finite tuple with `ret[1] > 0`** — `ret = cmd.super("<wt>", "<mut>")`; assert `isinstance(ret, tuple)` and `len(ret) >= 2` and `math.isfinite(float(ret[0]))` and `int(ret[1]) > 0`. (The robust form the sibling suggested — `val = r if isinstance(r,(int,float)) else r[0]` — is confirmed correct; my empirical run shows it's always a tuple for `align`/`super`, so `ret[0]`/`ret[1]` indexing is safe. `cmd.align`/`cmd.super` raise `pymol.CmdException` on match failure (`fitting.py:303`, `fitting.py:393`), so a non-exception return already implies ≥1 matched pair — `ret[1] > 0` is belt-and-suspenders.)
3. **The mobile object's coordinates changed (proves `transform=1` worked)** — capture one CA coord of `<wt>` BEFORE align (`cmd.get_model("<wt> and name CA").get_coord_list()[0]`), translate `<wt>` away, run `super`, assert the coord CHANGED. (`transform=1` is the default, `fitting.py:245` / `fitting.py:308`; empirically confirmed: `wt` x went 5→0.)
4. **(Optional, for the "edit then align" full sequence) the edit round-trip still holds** — if the prototype applies a correct edit before aligning, assert the edit took (reuses `tools/edit_smoke.py` Stage 4 pattern) — but the WT-aligned-load prototype can also SKIP the edit (the edit path is already proven by `edit_smoke.py`); the new thing to prove is load→align→verify.

**Honesty note:** the prototype proves the **`cmd.super`/`cmd.align` API contract** (load → align → finite RMSD → mobile transformed), NOT real science. A *real* RMSD-quality gate ("post-align active-site-core RMSD < 2 Å implies a meaningful restoration") is **Phase 7 content**, evaluated per-enzyme on real PDBs with source approval — explicitly out of scope for 5.3. The 5.3 prototype's `SMOKE_RESULT: PASS` asserts the *mechanism*, not the *science*. (Mirrors the sibling design file §E honesty note.)

## §E. New `MolAction` op vs reuse — recommendation (the key integration question)

### The three options

**Option 1 — Reuse `load` + a NEW `op="align"` op (two MolActions in `on_enter`).** `MolAction("load", target="<enzyme>_wt", args={source:"pdb", code:<WT_PDB>})` then `MolAction("align", target="<enzyme>_wt", args={reference:"<enzyme>", method:"super", align_sele:"name CA"})`. The `align` dispatch in `molops.py` calls `cmd.<method>(mobile, reference)`.

**Option 2 — A single new composite `op="load_aligned_wt"` op.** One MolAction that loads + aligns in one branch.

**Option 3 — No new op; align is a presentation-layer concern** handled by the Phase 6 controller / Phase 5.4 scene template calling `cmd.super` directly, not via a MolAction.

### Analysis against the existing architecture

| Criterion | Option 1 (load + `align` op) | Option 2 (composite `load_aligned_wt`) | Option 3 (no op, controller calls `cmd.super`) |
|-----------|------------------------------|---------------------------------------|------------------------------------------------|
| Matches existing one-MolAction-one-concern dispatch (`molops.py:112-196`) | ✅ load + align are peer primitives | ❌ two `cmd.*` calls per action | N/A (no MolAction) |

```python
elif op == "align":
    method = action.args.get("method", "super")
    reference = action.args["reference"]
    sele = action.args.get("align_sele")  # None => whole object
    mobile = action.target if sele is None else "{0} and {1}".format(action.target, sele)
    ref = reference if sele is None else "{0} and {1}".format(reference, sele)
    if method == "super":
        # src: tmp/pymol-src/modules/pymol/fitting.py:242 cmd.super  (mobile MOVED, target FIXED)
        self._cmd.super(mobile, ref)
    elif method == "align":
        # src: tmp/pymol-src/modules/pymol/fitting.py:306 cmd.align  (mobile MOVED, target FIXED)
        self._cmd.align(mobile, ref)
    elif method == "cealign":
```

## §G. Common pitfalls

### Pitfall 1 — PyMOL's `target` arg means FIXED reference, not "the thing aimed at" (naming collision)

**What goes wrong:** `cmd.align(mobile, target)` / `cmd.super(mobile, target)` — English intuition says "target = the thing you're moving toward / aiming at = the thing that moves." PyMOL's convention is the **opposite**: `mobile` is MOVED, `target` is the FIXED reference. (Empirically confirmed §A.5: `align("wt","mut")` moved `wt`, left `mut` fixed.) A developer who writes `cmd.align(mutant, wt)` expecting `wt` to move onto `mutant` gets the inverse — `mutant` moves, `wt` stays — and the camera/zoom jumps away from where the player was looking.

**How to avoid:** in the `op="align"` MolAction, name the FIXED object `args["reference"]` (NOT `args["target"]`) to keep the data shape intuitive (`target`=mobile, `reference`=fixed). The `molops` dispatch maps `cmd.<method>(mobile=action.target, target=action.args["reference"])` and documents the collision in a comment. For the WT-aligned load, WT = `target` (mobile, moves), edited enzyme = `reference` (fixed, stays).

**Warning signs:** after an `align`, the wrong object moved; the camera jumps; the "overlay" looks like the mutant moved onto a stationary WT instead of WT sliding onto the mutant.

### Pitfall 2 — `cmd.cealign` arg order is REVERSED + needs ≥16 CA atoms + returns a dict

**What goes wrong:** `cealign(target, mobile)` — the args are in the **opposite order** from `align`/`super` (`fitting.py:27`). Copy-pasting an `align` call and renaming it `cealign` silently swaps mobile/target. Additionally, `cealign` requires `len(selection) >= 2*window` (default `window=8` → ≥16 CA atoms with `guide=1`; `fitting.py:81-92`) — a tiny placeholder fixture raises `CmdException: Your target selection is too short.` (empirically reproduced §A.5). And `cealign` returns a **dict** `{"RMSD","alignment_length","rotation_matrix"}` (`fitting.py:135`), NOT the tuple `align`/`super` return — so `ret[0]` indexing throws `KeyError`.

**How to avoid:** the `op="align"` dispatch **normalizes** the reversal — it always calls `cmd.cealign(ref, mobile)` (reference first) so the MolAction author writes the same `target=mobile, args["reference"]=fixed` shape regardless of method. The dispatch treats `cealign`'s dict return opaquely (discards it at runtime; the smoke handles dict-vs-tuple in the post-condition). Do NOT use `cealign` in the prototype (tiny fixture); reserve it for Phase 7 real structures (≥16 CA).

**Warning signs:** `KeyError: 0` on a `cealign` return; `CmdException: selection too short` on a small structure; the wrong object moved after a `cealign` call.

### Pitfall 3 — `cmd.align` outlier rejection silently discards a shifted domain (good or bad, depending)

**What goes wrong:** `align`/`super` do `cycles=5` outlier-rejection cycles by default (`fitting.py:335-336`, `fitting.py:243-244`). For a domain-shift mutant, the shifted-domain atoms are outliers → rejected → the alignment fits only the stable core, and `ret[1]` (matched atoms) is much smaller than the total. The reported RMSD (`ret[0]`) is over the core only. This is **desirable** for the convention (align on the stable core, see the shift as the offset) — but it's **silent**: a developer reading `ret[1]=120` on a 300-residue protein may not realize 180 atoms were rejected as outliers.

**How to avoid:** document that the WT-aligned load's `ret[1]` is the post-outlier-rejection matched count, not the total. For a domain-shift mutant, this is why scoping to a stable-core `align_sele` (§C) is preferred over a global all-atom align — it makes the "fit on the core" intent explicit instead of relying on outlier rejection to find the core. To get the all-atom RMSD (no rejection), pass `cycles=0` (`fitting.py:359-361`) — but that gives a poor fit for a domain shift, so it's for diagnostics, not the convention.

### Pitfall 4 — `cmd.rms` does NOT transform (vs `cmd.fit` which does)

**What goes wrong:** a developer uses `cmd.rms(mobile, target)` to align, expecting it to move `mobile`. It does NOT — `rms` computes the post-fit RMSD internally but leaves both objects untouched (`fitting.py:620-664`; empirically `rms("wt","mut")` returned 0.0 and `wt` stayed at its translated position, §A.5). `cmd.fit` is the one that superposes (transforms `mobile`). `cmd.rms_cur` is the raw current RMSD (no fit, no transform).

**How to avoid:** for the WT-aligned load, use `cmd.super`/`cmd.align` (both transform by default, `transform=1`). Use `cmd.rms_cur` AFTER an align to *measure* the residual divergence, not to align. Do not confuse `rms` with `fit`.

### Pitfall 5 — `transform=1` transforms the WHOLE object, not just the matched selection

**What goes wrong (or right):** when scoping `cmd.super("wt and name CA and resi 100-160", "mut and name CA and resi 100-160")`, the transform is applied to the **whole `wt` object**, not just the `100-160` CA atoms (empirically confirmed §A.5: scoping to `name CA` moved the whole `wt`). This is **desired** for the convention (the stable core defines the frame; the whole WT slides into it; the shifted domain shows as the offset). But a developer who expects only the core to move is surprised.

**How to avoid:** document that `align_sele` scopes the MATCHING, not the TRANSFORMATION — the whole mobile object always moves. To transform only a fragment, you'd `cmd.create` the fragment into its own object first (not needed for the convention).

### Pitfall 6 — `cmd.superpose` does not exist

**What goes wrong:** a planner/developer looks for `cmd.superpose` (the natural English verb for "superpose two structures"). It does NOT exist in PyMOL 2.5.0 (`fitting.py` read in full — 756 lines, no `superpose` def). Using `cmd.superpose(...)` raises `AttributeError`.

**How to avoid:** use `cmd.super` (or `cmd.align`/`cmd.cealign`). The noun "superposition" appears in docstrings; the verb commands are `align`/`super`/`cealign`/`fit`/`pair_fit`.

### Pitfall 7 (from `PITFALLS.md`) — WSL/Windows path resolution for `cmd.load` of the fixtures

The prototype loads fixtures via `c14.paths.data_path(...)` (cwd-independent, `__file__`-relative — `asset_manager.py:89`), NOT relative paths. A relative `cmd.load("data/.../fixture.pdb")` resolves against the cmd.exe cwd and breaks headlessly (`PITFALLS.md` Pitfall 1). The `tools/edit_smoke.py` pattern (Gotcha #2: `__file__` in a PyMOL-run script is wrong; `c14.paths.__file__` is correct) is already the established fix — the WT-align prototype reuses it verbatim.

## Don't hand-roll

**`align`/`super`/`cealign`/`fit`/`pair_fit` are BUILT-IN `cmd.*` — do NOT reimplement structural alignment.** Pairwise structural superposition is a non-trivial algorithm (sequence alignment + Kabsch rotation + outlier rejection for `align`/`super`; CE combinatorial extension for `cealign`). The only things to hand-roll for Phase 5.3 are:

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Structural superposition of WT onto mutant | a custom RMSD-minimizing rotation (Kabsch by hand) | `cmd.super` (default) / `cmd.align` (same-protein) | `fitting.py:242`/`:306` — battle-tested, handles sequence alignment + outlier rejection + multi-state; reimplementing invites the mobile/target-order + outlier-silent-discard pitfalls |
| RMSD computation | manual `numpy` RMSD over coordinate lists | `cmd.rms_cur` (current) / `cmd.rms` (post-fit) / the `ret[0]` of `align`/`super` | `fitting.py:666`/`:620`/`:306` — atom-matching (`matchmaker`) + state handling is already correct |
| Multi-object alignment | a loop calling `super` per pair | `cmd.extra_fit` / `cmd.alignto` (`fitting.py:137`/`:199`) if ever needed | already handles the reference + method dispatch (`extra_fit` lines 173-191) |
| Selection scoping | manual sub-object extraction + re-merge | pass a sub-selection as `mobile`/`target` (the whole object transforms) | empirically confirmed §A.5 / §C |

**Key insight:** the ONLY custom code Phase 5.3 adds is (a) the `op="align"` `elif` branch in `molops.py` (a ~10-line dispatch that calls the right `cmd.<method>` with the right arg order), and (b) the convention spec (a doc). The structural-alignment math is entirely PyMOL's. The `op="align"` dispatch's value-add is **encapsulating the footguns** (cealign arg-order reversal, mobile/target naming) so story authors never hit them — not reimplementing the alignment.
