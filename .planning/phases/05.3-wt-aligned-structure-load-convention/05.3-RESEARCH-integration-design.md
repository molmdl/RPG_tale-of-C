## Summary

This is a DESIGN phase (0 requirements). It produces a **reviewable convention artifact** + a **headless prototype** + a **human design-review checkpoint**. The convention specifies *when* the WT-aligned experimental structure loads after a correct (disease-reversing) edit, *what* it loads, *how* it aligns, and *how* it's presented — so Phase 5.4 (scene templates), Phase 6 (Qt MVP), and Phase 7 (content) can consume it without re-designing.

The integration map is now traced end-to-end: a correct edit routes via `EditRouter.route` → `engine._enter(branch_node)` → the **branch node's `on_enter` MolActions** fire (`c14/engine.py:155-161`, `c14/engine.py:163-194`). The WT-aligned load is a **scene-template / `on_enter` concern** that fires in that branch-node `on_enter` sequence, positioned **AFTER** the reverse-mutation `MolAction(op="edit",...)`. It is the spec's "reveal correct 3D model for smooth gameplay" mechanism (`spec.md:28`, item 4) re-cast as the restoration narrative's "this is what healthy looks like" payoff.

The key scientific-design finding: the WT-aligned load is **conditionally meaningful**. Under mutant-reveal approach **(a) apply-edit** (load WT 6CFO → `cmd.alter` to disease), the live object's pre-disease backup **IS** 6CFO (the WT experimental structure), so `MolAction(op="restore",...)` and "load WT + align" **converge** — the reveal is almost trivial. Under approach **(b) load-mutant-PDB** (fetch 6CER directly), the backup is the *mutant* (6CER), so `restore` does NOT yield the WT; the WT-aligned load (fetch 6CFO + `cmd.super` to the 6CER object) is the **distinct, scientifically meaningful** operation — and this is exactly where the phase goal's "major conformational difference (domain shift)" case arises. The convention must be **compatible with both approaches** (Phase 7 decides per-enzyme via OQ-DM2) and must **NOT pre-decide** the mutant-reveal approach.

**Primary recommendation:** Specify the WT-aligned load as a **branch-node `on_enter` MolAction sequence** — `edit` (reverse-mutation) → `load` (WT experimental PDB as a SEPARATE `<enzyme>_wt` object) → `align`/`super` (the `_wt` object onto the restored/edited `<enzyme>` object, **scoped to a stable substructure** for domain-shift mutants) → presentation MolActions. Default presentation = **overlay** (two objects, different colors) for major-conformational-difference mutants; **replace** (or the `restore` shortcut under approach a) as the fallback for minor mutants. Keep it a **convention**, not a framework — minimum contract surface only.

## §A. Where the WT-aligned load fires in the data flow (recommendation + trace)

### The exact trace, from the player's correct edit to the reveal

Verified against `c14/engine.py:135-194`, `c14/edit_router.py:122-149`, `c14/pymol_layer/molops.py:112-196`, `c14/pymol_layer/edit_ops.py:106-149`, and the 05.1-DESIGN §5 5-step data-flow (`05.1-DESIGN.md:563-595`):

1. **Player triggers an edit** in the (Phase 6) UI; the controller builds an `EditIntent(op, target, args, enzyme_id)` (`c14/story/model.py:105-151`).
2. The controller reads the **current edit-allowed node's** `edit:enzyme:<id>` tag (`05.1-DESIGN.md:607-624`) and calls `engine.apply_player_edit(intent, enzyme_id)` (`c14/engine.py:135`).
3. `engine.apply_player_edit` (`c14/engine.py:135-161`):
   - `node_id = self.edit_router.route(intent, enzyme_id, self.rng)` (`c14/engine.py:155`). A **KNOWN** edit (exact `signature` match in the enzyme's `edits` list, `c14/edit_router.py:141-143`) → returns `entry["branch_node"]` (the defined story node for this correct edit). An unknown edit → bad-ending pool (`c14/edit_router.py:144-149`).
   - `self.state.add_edit({...})` (`c14/engine.py:156-160`).
   - `return self._enter(node_id)` (`c14/engine.py:161`) — **reuses the existing `_enter`**, so the branch node's `on_enter` MolActions flow to the existing `molaction_sink` (`c14/engine.py:163-194`).
4. **The branch node's `on_enter` MolActions fire**, dispatched **per-action** to the sink (`c14/engine.py:187-189` → `molops.apply(action)` in the Phase 4+ controller). Per the fixture (`tests/fixtures/edit_routing/story.json:9-15`, cited at `05.1-DESIGN.md:587-594`), the branch node's `on_enter` carries `MolAction(op="edit", target=..., args={edit_type, sele, new_resn})` → `molops` dispatches to `EditOps.point_mutation` (`molops.py:157-159`) → `apply_edit` takes a backup + `cmd.alter` + `cmd.sort` + `cmd.rebuild` (`edit_ops.py:106-149`). **This is the reverse-mutation being applied** (the player's correct edit executes; the live object now has the WT residue identity but approximate geometry — the 002-SUMMARY caveat, `.planning/quick/002-.../002-SUMMARY.md:69-71`).
5. **→ The WT-aligned load fires HERE, in the SAME branch-node `on_enter` sequence, AFTER the `edit` MolAction.** (Recommended — option iii; see below.)

### The three placement options analyzed

The prompt posits (i) before restore, (ii) after restore = the WT is the restored state, (iii) after the edit as the payoff reveal. The key disambiguation: **"restore" in the prompt conflates two different things**, and the 05.1-06 Note 2 phrasing ("the restore after a correct edit is where the WT-aligned load would fire", `05.1-06-SUMMARY.md:183`) is **imprecise**. Two distinct mechanisms exist in the codebase:

- **`MolAction(op="restore",...)`** → `EditOps.restore(target)` (`molops.py:184-190`, `edit_ops.py:217-257`) → `restore_from_handle` → `cmd.delete` live + `cmd.create` from the backup + `cmd.sort` + `cmd.rebuild` + round-trip verify. This is the **"reveal correct 3D model / smooth-gameplay safety net"** from `spec.md:28` (item 4). It is the path that fires when a *wrong* edit needs undoing for smooth gameplay, OR (under approach a) can serve as the WT reveal (see §B).
- **A correct edit** does **NOT** trigger the restore safety net — it routes to a **branch node** whose `on_enter` applies the reverse-mutation `edit`. The WT-aligned load is a **branch-node `on_enter` concern**, not a restore-safety-net concern.

| Option | Where it fires | Narrative + scientific tradeoff |
|--------|----------------|---------------------------------|
| **(i) BEFORE the reverse edit** | branch-node `on_enter`: load+align WT, then `edit` reverse-mutation | Narratively **backwards** — you'd show the healthy WT reveal *before* the player's restoration act lands. Reject. |
| **(ii) The restored state IS the WT** (restore ≡ WT reveal) | branch-node `on_enter` = `MolAction(op="restore",...)` only (no separate WT load) | **Converges with the WT-aligned load ONLY under approach (a)** (backup = 6CFO WT). **Fails under approach (b)** (backup = 6CER mutant; restore yields the mutant, not the WT). Adopting this as the *sole* mechanism would **pre-decide mutant-reveal approach (a)** — violates OQ-DM2 (deferred to Phase 7). |
| **(iii) AFTER the reverse edit → load+align WT as the payoff** | branch-node `on_enter`: `edit` (reverse-mutation) → `load` WT PDB (`<enzyme>_wt`) → `align`/`super` `_wt` onto `<enzyme>` → present | **Recommended.** Narratively sound (player's act triggers the reveal); scientifically honest (shows the *experimentally determined* WT geometry as ground truth, since the `cmd.alter`-restored model has approximate coordinates per the 002-SUMMARY caveat); **compatible with BOTH mutant-reveal approaches** (under a it's an explicit equivalent of the restore shortcut; under b it's the distinct meaningful operation). |

### Recommendation (§A)

**The WT-aligned load fires in the BRANCH NODE's `on_enter` MolAction sequence, AFTER the `MolAction(op="edit",...)` reverse-mutation (option iii).** The canonical `on_enter` order for a restoration-reveal branch node:

```
1. MolAction(op="edit", edit_type="point_mutation", target=<enzyme>,
             sele=<disease_resi>, new_resn=<WT_resn>)          # the player's restoration
2. MolAction(op="load", source="pdb", code=<WT_PDB>,
             object="<enzyme>_wt")                              # real WT experimental structure
3. MolAction(op="align", target="<enzyme>_wt",
             args={mobile:"<enzyme>_wt", target:"<enzyme>",
                   method:"super", align_sele:<optional>})       # align WT onto restored/edited obj
4. presentation MolActions (show_as / color / zoom)              # Phase 5.4 layers these
```

**Clarifications the spec must state:**
- The WT-aligned load is the spec's **"reveal correct 3D model"** (`spec.md:28`, item 4) under the restoration narrative (`002-SUMMARY.md`).
- It fires on the **correct-edit branch path** (EditRouter known → branch node), **NOT** on the `MolAction(op="restore",...)` safety-net path (which serves wrong-edit smooth gameplay). The 05.1-06 Note 2 phrasing is corrected: a correct edit routes to a branch node; the WT-aligned load is a branch-node `on_enter` concern.
- **Exception under approach (a):** when the edit-allowed node's pre-edit `on_enter` loaded the WT base (6CFO) and altered it to disease, the backup **IS** 6CFO (WT), so step 2+3 can be **replaced by `MolAction(op="restore",...)`** as an equivalent shortcut (returns the WT base; no separate `_wt` object). The convention supports BOTH; Phase 7 picks per-enzyme (see §B + §H).
- `tca.citrate_synthase` (the `edit:structural` exception, `05.1-DESIGN.md:662, 676-682`) has **NO disease mutant** — the restoration narrative does NOT apply, so the WT-aligned load does **NOT** fire there. The convention applies only to the 12 `DIS-*-cand` disease-mutant nodes (`05.1-DESIGN.md:657-672`).

## §B. Composition with the 6CFO/6CER mutant-reveal approaches (conditionality recommendation)

### The locked + deferred decisions (do not re-litigate)

- **6CFO (WT, 2.70 Å, Whitley 2018 PubMed:29970614) is the pyr.pdh CAST** — CONFIRMED (`05.1-06-SUMMARY.md:49, 109-113`; `05.1-DESIGN.md:661, 690-698`).
- **6CER (V138M mutant, 2.69 Å, same paper) is the matching mutant PDB** — referenced as a Phase 7 option (`05.1-DESIGN.md:661, 690-698`).
- **The mutant-reveal approach — (a) apply-edit vs (b) load-mutant-PDB — is DEFERRED TO PHASE 7** (OQ-DM2, `05.1-06-SUMMARY.md:49, 111, 128`). The convention must **NOT pre-decide** it.

### Analysis under each approach

**Under approach (a) apply-edit** (load 6CFO WT → `cmd.alter resi 138` → diseased state):
- The edit-allowed node's pre-edit `on_enter` does `load pdb:6CFO` (object `pdh`) → `edit` (V→M). The **backup taken by that `edit` IS 6CFO (WT)** (`edit_ops.py:191-211` — `take_backup` copies the pre-alter state).
- The "mutant" is 6CFO-with-one-residue-altered (approximate geometry — the 002-SUMMARY caveat).
- The WT-aligned reveal is **almost trivial**: the WT experimental structure is *already* the base. Two equivalent mechanisms:
  - (a1) `MolAction(op="restore",...)` on the live `pdh` object → returns 6CFO (WT) from the backup. **One object, no align needed** (the restored coords ARE the WT coords). This is the `restore` shortcut.
  - (a2) explicit `load pdb:6CFO` as `pdh_wt` + `align pdh_wt, pdh` — produces a second object aligned to the (now-reverse-edited) `pdh`. Redundant (same structure, one residue), but uniform with approach (b).
- **Is the WT-aligned reveal even meaningful under (a)?** Mostly **no** for the reveal's pedagogical purpose: the reverse-edit already restored the residue identity, and the restored model's geometry is the WT base's geometry (6CFO). The "before/after" comparison the overlay offers is between "6CFO-with-one-residue-as-M" and "6CFO-WT" — a single-residue swap, **not** a conformational reveal. The major-conformational-difference case the phase goal calls out **does not arise under (a)** (alter doesn't move the backbone).

**Under approach (b) load-mutant-PDB** (fetch 6CER directly):
- The edit-allowed node's pre-edit `on_enter` does `load pdb:6CER` (object `pdh`). The **backup is 6CER (mutant)**.
- The "mutant" is 6CER (real mutant geometry — possibly a domain shift, the conformational difference the phase goal targets).
- `MolAction(op="restore",...)` would return **6CER (mutant)**, NOT the WT — so restore ≠ WT reveal.
- The WT-aligned reveal = `load pdb:6CFO` as `pdh_wt` + `super pdh_wt, pdh` → loads **real WT geometry** aligned to the **real mutant**. **THIS is the scientifically meaningful case** — the overlay directly shows the conformational difference (domain shift visible as misalignment of peripheral regions after an active-site-core superposition; see §C).
- **The "major conformational difference" case arises HERE, under (b).**

### Conditionality recommendation (§B)

The convention should be **CONDITIONAL on the mutant-reveal approach + the per-enzyme conformational-difference flag**, NOT unconditional. Document it so Phase 7 can decide per-enzyme without re-planning 5.3:

1. **The mechanism is ALWAYS specified** (the `load` + `align`/`super` + present MolAction sequence exists and is headless-prototyped). The convention is a *capability*, always available.
2. **Whether it FIRES is a per-enzyme Phase 7 decision**, gated on:
   - the mutant-reveal approach chosen for that enzyme (a vs b), AND
   - whether the mutant has a **major conformational difference** (a `conformational_difference: "major" | "minor" | "none"` per-enzyme metadata field, Phase 7-authored + source-approved).
3. **Default firing rule (recommendation, human may override at the checkpoint):**
   - Approach (b) + `conformational_difference: "major"` → **FIRE the WT-aligned overlay** (the scientifically strong reveal; the phase goal's target case).
   - Approach (b) + `"minor"`/`"none"` → **optional** (the reverse edit may suffice; Phase 7 may still fire a replace-style WT reveal for clarity).
   - Approach (a) + any → **the `restore` shortcut suffices** (the backup IS the WT); an explicit `_wt` overlay is redundant. Phase 7 MAY still use the explicit form for uniformity, but it is not required.
4. **OQ-DM2 disposition honored:** the convention specifies the WT-aligned load *mechanism* that *complements* whichever approach Phase 7 chooses; it does **NOT** pick (a) or (b). The conditionality above is the contract that lets Phase 7 decide without re-planning 5.3.

## §C. Scientific validity for major conformational differences (substructure align + honest narrative framing)

### Is aligning a WT experimental structure to a domain-shift mutant scientifically sound?

**Yes, as a *visualization aid* — NOT as a proof of restoration.** The nuance:

- A **global** `cmd.align`/`cmd.super` over all atoms will be **poor** for a domain-shift mutant (high post-outlier RMSD; the outlier-rejection cycles will discard the shifted domain). The resulting global superposition is misleading as a "restored" picture.
- A **substructure / local** superposition — aligning on a **stable reference** (the active-site core / a conserved domain / conserved catalytic residues) — is scientifically sound: it places the WT and mutant in a common frame *at the catalytic center*, so the player sees "the active site looks like this when healthy" while the **domain shift remains visible** as the misaligned peripheral region. The conformational difference is the *pedagogical payload*, not something to hide.

### The substructure-align design recommendation (the spec MUST contain this)

- **Default alignment method: `cmd.super`, NOT `cmd.align`.** Per `tmp/pymol-src/modules/pymol/fitting.py:316-320` (the `align` docstring): *"`align` does a good job on proteins with decent sequence similarity (identity >30%). For comparing proteins with lower sequence identity, the `super` and `cealign` commands perform better."* A domain-shift mutant is exactly the structurally-divergent case `super` is designed for. (`cmd.super`: `fitting.py:242-304`; `cmd.align`: `fitting.py:306-394`.)
- **Scope the alignment to a stable substructure** via atom selections: `cmd.super("<enzyme>_wt and <align_sele>", "<enzyme> and <align_sele>")`. Both `super` and `align` accept arbitrary atom selections (`fitting.py:259, 331-333`), so the alignment can be restricted to e.g. `name CA and resi 100-160` (an active-site-core / conserved-domain CA selection). `transform=1` (default, `fitting.py:245, 308`) transforms the **whole** `_wt` object using the transform derived from the substructure — so the active site lines up and the shifted domain shows the conformational difference.
- **`align_sele` is a per-enzyme metadata field** (Phase 7-authored, source-approved — which residues define the stable core). The convention specifies the *field*; Phase 7 fills it per enzyme. Default when unspecified: `name CA` (whole-CA superposition, the standard fallback — acceptable for minor/no-conformational-difference mutants).
- **Do NOT use `cmd.cealign` in the headless prototype on a tiny placeholder.** `cealign` requires `len(selection) >= 2*window` with `window` default 8 → ≥16 CA atoms (`fitting.py:81-92`), and its arg order is `(target, mobile)` — reversed vs `align`/`super` (`fitting.py:27`). A hand-written tiny PDB will fail cealign. (The counterpart API-verifier's scratch `_scratch_verify_align.py:41-48` explicitly tests this expected failure.) `super`/`align` work on small selections.

### Honest narrative framing (the spec must provide `text_teaching` wording)

The reveal is a **visualization aid, not a proof of restoration**. Suggested `text_teaching` wording (template; Phase 7 finalizes with citations):

> "Your reverse-mutation restored the residue's identity. Because the editing tool changes residue identity without re-packing the side chains, your restored model has approximate coordinates. Here we show the **experimentally determined wild-type structure** (PDB `<WT_PDB>`, `<resolution>` Å), aligned to your enzyme on the active-site core, as a reference for what the healthy enzyme looks like. The regions that don't overlap show the conformational difference of the disease mutant."

**Constraints honored:**
- **Hero-identity anti-confusion (AGENTS.md):** the restoration reveal is about the **ENZYME's** health, NOT the hero carbon's fate. At `pyr.pdh` specifically, the placeholder `text_dramatic` is "PDH strips your first carbon as CO2" (`pyr.pdh` JSON) — the hero **carbon body IS shed as CO2** at PDH (correct decarboxylation), while the hero's **electrons** continue via NADH → ETC → ATP (soul-jump reframing, `PROJECT.md` Key Decisions row 107; `05.1-DESIGN.md:30-37`). The WT-aligned reveal must **NOT** imply the carbon becomes ATP or enters oxidative phosphorylation — it shows the PDH *enzyme* restored, while the carbon substrate is processed (released as CO2). Keep the two framings separate.
- **No fabricated science (AGENTS.md / `spec.md:66`):** 6CFO + 6CER are already Phase 5.1 candidate-cast references (`05.1-DESIGN.md:661`) — still CANDIDATE pending Phase 7 per-claim approval, NOT yet approved. Any **other** WT/mutant PDB pair, disease association, or `align_sele` residue-range needed for other enzymes is **Phase 7 to source + approve** — do NOT invent PDB IDs, DOIs, or disease links here.

## §D. Presentation: side-by-side vs replacement vs overlay (recommendation + 5.4 interaction)

### The three options

| Presentation | What it shows | Pedagogy | Scientific clarity | Phase 6 cost |
|-------------|---------------|----------|--------------------|--------------|
| **Replacement** | hide/delete the edited-mutant; show only the aligned WT | Cleanest "this is what healthy looks like" | Loses the before/after comparison | Low (existing `hide`/`delete`/`show_as` ops) |
| **Side-by-side** | edited-mutant + aligned WT in separate viewports/offsets | Best for direct comparison | Clear (two separate frames) | **High** — PyMOL multi-viewport (`set grid_mode`, `cmd.viewport`) is a Phase 6 UI concern; non-trivial headless verification |
| **Overlay** | both objects visible, aligned, different colors | Shows the conformational difference DIRECTLY (the domain shift is visible as misalignment of peripheral regions after active-site-core `super`) | Strongest for the "major conformational difference" pedagogical case the phase goal targets | Low-medium (existing `color` op; two objects coexist) |

### Recommendation (§D)

**DEFAULT = OVERLAY for `conformational_difference: "major"` mutants** (the phase goal's target case): the edited/restored `<enzyme>` object in one color, the `<enzyme>_wt` aligned WT object in another color, both visible after the active-site-core `super`. The domain shift is the *visible pedagogical payload*.

**Fallback = REPLACE for `"minor"`/`"none"` mutants** (or under approach (a) where the `restore` shortcut yields a single WT object): hide the edited-mutant, show only the WT-aligned object. Cleaner; no redundant overlay.

**Side-by-side (multi-viewport) is a Phase 6 UI concern, NOT a 5.3 data-level concern.** 5.3 only ensures the **two objects exist + are aligned** so that 5.4 (scene template) and 6 (Qt UI) can *choose* to present them overlaid OR split into viewports. The data-level mechanism is presentation-agnostic.

### Interaction with Phase 5.4 (the split 5.3 owns vs 5.4 owns)

5.3 owns the **data-level mechanism** (which objects exist, their names, their alignment state). 5.4 owns the **presentation directive** (representations, colors, zoom, viewport layout) layered on top. Concretely:
- **5.3 specifies:** after the reveal, the object set is `{<enzyme>, <enzyme>_wt}` (overlay case) OR `{<enzyme>}` (replace/restore case). `<enzyme>_wt` is aligned (transformed) to `<enzyme>`'s frame via `cmd.super` on `align_sele`. A `present` directive field (`"overlay" | "replace"`, default per the conformational-difference flag) records which case.
- **5.4 specifies:** given that object set + `present` directive, which `show_as`/`color`/`zoom`/viewport MolActions fire (e.g. overlay → `<enzyme>` cartoon green + `<enzyme>_wt` cartoon blue + `zoom <enzyme>_wt`; replace → `hide <enzyme>` + `show_as cartoon <enzyme>_wt` + `zoom`). 5.4 does **not** re-decide the object set or the alignment.

## §E. Verification post-condition for the headless prototype (recommendation)

### Robustness on a PLACEHOLDER structure

The prototype runs on a **placeholder/bundled structure** (hand-written tiny PDB, approximate/arbitrary coordinates) — NOT real science. The project's existing headless smokes (`tools/edit_smoke.py`, `tools/protonation_smoke.py`) use **atom-count + residue-signature** post-conditions (`04-05-SUMMARY.md:77-78`; `edit_ops.py:246-255`). For alignment verification on a placeholder:

- **A hardcoded RMSD threshold is NOT robust** — the placeholder has arbitrary coordinates; the "expected" RMSD is meaningless. A threshold would either always pass (too loose) or be brittle to fixture tweaks.
- **Atom-count / matched-atom-count + finite-RMSD is robust** — it proves the align API was called correctly + produced a finite alignment, without claiming a scientific RMSD.

### What "aligned" means as a machine-checkable post-condition

Recommended post-conditions for the prototype (all assertable headlessly via `run-conda-pymol.bat -cq`, AGENTS.md):

1. **Both objects non-empty after `load`** — `cmd.count_atoms("<enzyme>") > 0` AND `cmd.count_atoms("<enzyme>_wt") > 0` (reuses the `asset_manager.load_bundled`/`fetch_pdb` post-condition pattern, `asset_manager.py:72-77`). HIGH confidence — matches existing smokes.
2. **The align call returned a finite result** — `r = cmd.super("<enzyme>_wt", "<enzyme>")` (or `cmd.align`); assert `r is not None` and `float(r) >= 0.0` and `math.isfinite(float(r))`. Per `fitting.py:306-394` (`align`) and `fitting.py:242-304` (`super`), the return `r` is the post-outlier-rejection RMSD. **MEDIUM confidence on the exact return type** (bare float vs a (RMSD, n_atoms) tuple varies across PyMOL builds) — the prototype should assert robustly: `val = r if isinstance(r, (int, float)) else r[0]` then check finiteness. (The counterpart API-verifier's scratch `_scratch_verify_align.py:68-77` section G empirically tests exactly this `ret[0]`/`ret[1]` question — cross-reference their result before finalizing the assertion.)
3. **The mobile object's coordinates changed** (proves `transform=1` worked) — capture one CA coordinate of `<enzyme>_wt` BEFORE align (e.g. via `cmd.get_model("<enzyme>_wt and name CA").get_coord_list()[0]`), translate it away (as the scratch does, `_scratch_verify_align.py:18-19`), run `super`, then assert the coordinate CHANGED. This proves the superposition transformed the mobile object in place. HIGH confidence `transform=1` is the default (`fitting.py:245, 308`).
4. **(Optional) matched-atom-count > 0** — `cmd.align`/`cmd.super` raise `pymol.CmdException` if the match fails (`fitting.py:303, 393`), so a non-exception return already implies ≥1 matched pair. The finite-RMSD assertion (2) subsumes this.

### Honesty note (the spec must state this)

This prototype proves the **`cmd.super`/`cmd.align` API contract** (load → align → finite RMSD → mobile transformed), NOT real science. The placeholder's RMSD value is meaningless as a restoration-quality threshold. A *real* RMSD-quality gate (e.g. "post-align active-site-core RMSD < 2 Å implies a meaningful restoration") is **Phase 7 content** evaluated per-enzyme on real PDBs with source approval — explicitly out of scope for 5.3. The 5.3 prototype's `SMOKE_RESULT: PASS` asserts the *mechanism*, not the *science*.

## §F. Integration contract for downstream phases 5.4 / 6 / 7 (minimum surface)

The convention spec must specify this **minimum contract surface** so downstream phases don't re-design it. Keep it minimal — a convention, not a framework.

### F.1 — For Phase 5.4 (scene-template / cast-reveal)

5.4 needs to know **which objects exist after the reveal + their alignment state + naming**:

- **Object set after reveal:**
  - overlay case: `{<enzyme>, <enzyme>_wt}`
  - replace/restore case: `{<enzyme>}` (the live object, restored to WT)

  ```
  MolAction(op="align", target="<enzyme>_wt",

  ```

Both defensible — human decides at the checkpoint.
- The controller (Phase 6) emits the branch node's `on_enter` MolActions (`load`, `edit`, `align`, `show_as`, `color`, `zoom`) per-action to `molops.apply` — no new "reveal" super-op, no new controller branch. Composability from existing ops + one new `align` op keeps the dispatch surface flat.

## §H. Open questions / decisions to defer to the human at the checkpoint

1. **Always-fire vs conditional-fire:** Should the WT-aligned load fire on **every** correct edit, or only for mutants with a **major conformational difference** (primarily under approach b)? **Recommendation:** conditional (per §B). The human may prefer "always fire for uniformity" (simpler content authoring, more consistent reveals) — flag the tradeoff (uniformity vs avoiding redundant/redundant reveals under approach a).
2. **Default presentation (overlay vs replace):** **Recommendation:** overlay for major-conformational-difference, replace otherwise. The human may prefer **replace as the sole default** (simplest UI; lose the before/after comparison but cleaner). Flag that overlay is the scientifically richer choice for the domain-shift pedagogical case the phase goal explicitly targets.
3. **Where the `op="align"` molops dispatch lands:** **Recommendation:** 5.3 specifies the op shape + prototypes `cmd.super` headlessly (direct calls in the smoke); the `molops` `op="align"` addition + unit test land in Phase 6 (keeps 5.3 a pure design+prototype phase, avoids touching `molops.py` in a 0-requirement design phase). **Alternative (04-05 precedent):** add `op="align"` to `molops.py` in 5.3 alongside the smoke. Human decides — both defensible.
4. **`align_sele` authoring boundary:** Is `align_sele` (which residues define the stable active-site core) a **per-enzyme Phase 7 metadata field** (source-approved per enzyme) OR a **convention default** (e.g. `"name CA"` for all, with Phase 7 overriding only for domain-shift cases)? **Recommendation:** per-enzyme field, default `"name CA"`. Flag that per-enzyme `align_sele` requires a structural-rationale citation in Phase 7.
5. **Side-by-side (multi-viewport) scope:** Confirm side-by-side is **out of 5.3's data-level scope** (a Phase 6 UI concern) and that 5.3 only guarantees the two objects exist + are aligned. **Recommendation:** yes (per §D).
6. **Approach (a) reveal redundancy:** Under approach (a), is the explicit `<enzyme>_wt` overlay **ever** warranted, or does the `restore` shortcut (returns the WT base) always suffice? **Recommendation:** `restore` suffices under (a); the explicit overlay is redundant. Phase 7 may still use the explicit form for content-authoring uniformity — flag as Phase 7 discretion.
7. **PDB sourcing boundary:** 6CFO + 6CER are already 5.1 CANDIDATE references. Any **other** WT/mutant PDB pair, disease association, or `align_sele` residue range needed for the other 11 disease-mutant enzymes is **Phase 7 to source + approve** (AGENTS.md no-fabricated-science; `spec.md:66`). The 5.3 convention + prototype must NOT invent PDB IDs, DOIs, or disease links. (Flagged — not a 5.3 decision.)
8. **`conformational_difference` source:** The `conformational_difference: "major"|"minor"|"none"` metadata field drives the firing + presentation. What source justifies a "major" classification per enzyme? **Recommendation:** Phase 7 evaluates per enzyme (structural comparison of the WT vs mutant PDB; a citation). 5.3 defines the *field*; Phase 7 fills + approves it. Flag that "major" is a structural-science claim needing a source.
