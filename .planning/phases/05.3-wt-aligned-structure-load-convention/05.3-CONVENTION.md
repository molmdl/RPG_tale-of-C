## §1. Purpose & scope

This convention specifies the **WT-aligned experimental structure load** that fires after a correct (disease-reversing) edit to show what the healthy enzyme looks like — especially for mutants with **major conformational differences** (e.g. a large domain shift), where the edited-mutant model alone (`cmd.alter` changes residue identity but does NOT repack side chains, so coordinates are approximate) is not scientifically illustrative of the healthy state. Loading + aligning the **experimentally determined** WT structure gives the restoration reveal a real-geometry ground truth.

This is a **0-requirement design / convention phase** (per the Phase 10 + 5.1 + 5.2 design-phase precedent). It produces a reviewed SPEC (this file, SC1) + a headless mechanism proof (Plan 02, SC2); it does NOT ship code. It enables **EDIT-02 restoration-reveal delivery in Phase 6 / 7** by making the convention an already-reviewed artifact those phases consume WITHOUT re-designing it.

**Scope — applies ONLY to the 12 `DIS-*-cand` disease-mutant edit-allowed nodes** in the approved glucose skeleton (`05.1-DESIGN.md:657-672`): `gly.pfk`, `gly.pyruvate_kinase`, `pyr.pdh`, `tca.aconitase`, `tca.isocitrate_dh`, `tca.succinyl_coa_synthetase`, `tca.fumarase`, `tca.malate_dh`, `etc.complex_i`, `etc.complex_ii`, `etc.complex_iii`, `etc.complex_iv` — each carrying a `DIS-*-cand` candidate disease claim (Phase 7 per-claim approval pending).

**EXPLICIT EXCLUSION:** `tca.citrate_synthase` (the `edit:structural` exception, `05.1-DESIGN.md:662, 676-682`) has **NO disease mutant** — its 7 ClinVar Pathogenic records are all structural variants (inversions / CN-gains), not implementable via `cmd.alter`. The restoration narrative does NOT apply there (the host's CS is NOT diseased; the hero just explores it). The WT-aligned load does **NOT** fire for `tca.citrate_synthase`. (The 14th edit-allowed node, `tca.shuffle`, is a SHARED secondary edit point for `tca.aconitase` — it shares the aconitase enzyme_id, so the convention fires for the aconitase restoration, not as a separate case.)

**The real in-game human-verify is Phase 6** (the Qt MVP) — this phase produces a reviewed SPEC + a headless mechanism proof (Plan 02). The Plan 02 checkpoint is a **design-review** (approves the *convention*), not a visual in-game test.

## §2. When it fires (the placement decision)

*(Per RESEARCH-integration-design §A; traced against `c14/engine.py:135-194`, `c14/edit_router.py:122-149`, `c14/pymol_layer/molops.py:112-196`.)*

### The numbered trace

1. The player triggers an edit in the (Phase 6) UI; the controller builds an `EditIntent(op, target, args, enzyme_id)` (`c14/story/model.py:105-151`).
2. The controller reads the current edit-allowed node's `edit:enzyme:<id>` tag (`05.1-DESIGN.md:607-624`) and calls `engine.apply_player_edit(intent, enzyme_id)` (`c14/engine.py:135`).
3. `engine.apply_player_edit` (`c14/engine.py:135-161`):
   - `node_id = self.edit_router.route(intent, enzyme_id, self.rng)` (`c14/engine.py:155`). A **KNOWN** edit (exact `signature` match, `c14/edit_router.py:141-143`) → returns `entry["branch_node"]` (the defined story node for this correct edit). An unknown edit → bad-ending pool (`c14/edit_router.py:144-149`).
   - `self.state.add_edit({...})` (`c14/engine.py:156-160`).
   - `return self._enter(node_id)` (`c14/engine.py:161`) — reuses the existing `_enter`, so the branch node's `on_enter` MolActions flow to the existing `molaction_sink` (`c14/engine.py:163-194`).
4. **The branch node's `on_enter` MolActions fire**, dispatched per-action to the sink (`c14/engine.py:187-189` → `molops.apply(action)` in the Phase 4+ controller). Per the fixture (`tests/fixtures/edit_routing/story.json:9-15`), the branch node's `on_enter` carries `MolAction(op="edit", target=..., args={edit_type, sele, new_resn})` → `molops` dispatches to `EditOps.point_mutation` (`molops.py:157-159`) → `apply_edit` takes a backup + `cmd.alter` + `cmd.sort` + `cmd.rebuild` (`edit_ops.py:106-149`). **This is the reverse-mutation being applied** (the player's correct edit executes; the live object now has the WT residue identity but approximate geometry).
5. **→ The WT-aligned load fires HERE, in the SAME branch-node `on_enter` sequence, AFTER the `edit` MolAction.** (Option iii — see below.)

### The three placement options analyzed

| Option | Where it fires | Tradeoff | Verdict |
|--------|----------------|----------|---------|
| **(i) BEFORE the reverse edit** | branch-node `on_enter`: load+align WT, then `edit` reverse-mutation | Narratively **backwards** — you'd show the healthy WT reveal *before* the player's restoration act lands. | **REJECT** |
| **(ii) The restore safety-net IS the WT reveal** | branch-node `on_enter` = `MolAction(op="restore",...)` only (no separate WT load) | Converges with the WT-aligned load ONLY under mutant-reveal approach (a) (backup = WT). **Fails under approach (b)** (backup = mutant; restore yields the mutant, not the WT). Adopting as the *sole* mechanism would **pre-decide mutant-reveal approach (a)** — violates **OQ-DM2** (deferred to Phase 7). | **REJECT as sole mechanism** (kept as an equivalent shortcut under approach a — see below) |
| **(iii) AFTER the reverse edit → load+align WT as the payoff** | branch-node `on_enter`: `edit` (reverse-mutation) → `load` WT PDB (`<enzyme>_wt`) → `align`/`super` `_wt` onto `<enzyme>` → present | Narratively sound (player's act triggers the reveal); scientifically honest (shows the *experimentally determined* WT geometry as ground truth); **compatible with BOTH mutant-reveal approaches** (under a it's an explicit equivalent of the restore shortcut; under b it's the distinct meaningful operation). | **RECOMMENDED** |

### Correction of the 05.1-06 Note 2 imprecision

The 05.1-06 Note 2 phrasing (*"the restore after a correct edit is where the WT-aligned load would fire"*, `05.1-06-SUMMARY.md:183`) is **imprecise**. Two distinct mechanisms exist in the codebase:

- **`MolAction(op="restore",...)`** → `EditOps.restore(target)` (`molops.py:184-190`, `edit_ops.py:217-257`) → `restore_from_handle` → `cmd.delete` live + `cmd.create` from the backup + `cmd.sort` + `cmd.rebuild` + round-trip verify. This is the **"reveal correct 3D model / smooth-gameplay safety net"** from `spec.md:28` (item 4). It is the path that fires when a *wrong* edit needs undoing for smooth gameplay, OR (under approach a) can serve as the WT reveal (see below).
- **A correct edit** does **NOT** trigger the restore safety net — it routes to a **branch node** whose `on_enter` applies the reverse-mutation `edit`.

**A correct edit does NOT trigger the restore safety net — it routes to a branch node.** The WT-aligned load is a **branch-node `on_enter` concern, NOT a restore-safety-net concern.** This is the correction.

### Exception under mutant-reveal approach (a) — the restore shortcut

When the edit-allowed node's pre-edit `on_enter` loaded the WT base (e.g. 6CFO for `pyr.pdh`) and altered it to disease, the **backup taken by that `edit` IS the WT** (`edit_ops.py:191-211` — `take_backup` copies the pre-alter state). Under this approach, the WT-aligned reveal can be **replaced by `MolAction(op="restore",...)`** as an equivalent shortcut (returns the WT base; no separate `_wt` object). The convention supports BOTH the explicit load+align form AND the restore shortcut; **Phase 7 picks per-enzyme** (see §3 conditionality + §8 Q6).

### The canonical `on_enter` order for a restoration-reveal branch node

1. `MolAction(op="edit", edit_type="point_mutation", target=<enzyme>, sele=<disease_resi>, new_resn=<WT_resn>)` — the player's restoration
2. `MolAction(op="load", source="pdb", code=<WT_PDB>, object="<enzyme>_wt")` — load the real WT experimental structure as a SEPARATE object
3. `MolAction(op="align", target="<enzyme>_wt", args={reference:<enzyme>, method:..., align_sele:...})` — align WT onto the restored/edited enzyme
4. presentation MolActions (show_as / color / zoom) — Phase 5.4 layers these

The WT-aligned load is the spec's **"reveal correct 3D model"** (`spec.md:28`, item 4) re-cast as the restoration narrative's "this is what healthy looks like" payoff (`002-SUMMARY.md` restoration frame).

## §3. Conditionality (the convention is CONDITIONAL, not unconditional)

*(Per RESEARCH-integration-design §B.)*

The convention is **CONDITIONAL**:

- **The MECHANISM is always specified** — the `load` + `align`/`super` + present MolAction sequence exists and is headless-prototyped in Plan 02. The convention is a **capability**, always available.
- **Whether it FIRES is a per-enzyme Phase 7 decision**, gated on:
  - **(a)** the mutant-reveal approach chosen for that enzyme (`mutant_reveal_approach: "apply_edit"` vs `"load_mutant_pdb"` — Phase 7 decides per **OQ-DM2**, `05.1-06-SUMMARY.md:49, 111, 128`), AND
  - **(b)** whether the mutant has a major conformational difference (`conformational_difference: "major" | "minor" | "none"` per-enzyme metadata field, Phase 7-authored + source-approved — see §7.3 metadata table + §8 Q8).

### Default firing rule (recommendation; human may override at the Plan 02 checkpoint)

| `mutant_reveal_approach` | `conformational_difference` | Fires? | Mechanism |
|--------------------------|------------------------------|--------|-----------|
| **(b) `load_mutant_pdb`** | `"major"` | **YES — FIRE the WT-aligned overlay** (the scientifically strong reveal; the phase goal's target case) | `load` WT PDB + `super` + overlay (two objects) |
| (b) `load_mutant_pdb` | `"minor"` / `"none"` | optional (Phase 7 discretion) | explicit overlay OR replace; the reverse edit may suffice |
| (a) `apply_edit` | any | the `restore` shortcut **suffices** (backup IS WT); explicit `<enzyme>_wt` overlay **redundant** | `MolAction(op="restore",...)` yields a single WT object (Phase 7 MAY still use the explicit form for uniformity — Phase 7 discretion) |

**OQ-DM2 is honored:** the convention specifies the mechanism that **COMPLEMENTS** whichever approach Phase 7 chooses; it does **NOT** pick (a) or (b). The conditionality above is the contract that lets Phase 7 decide per-enzyme without re-planning 5.3.

## §4. How it aligns — substructure superposition for domain-shift mutants

*(Per RESEARCH-integration-design §C + RESEARCH-pymol-align-api §B / §C / §G; all API facts empirically verified against PyMOL 2.5.0 via `run-conda-pymol.bat -cq`.)*

### Default alignment method: `cmd.super`, NOT `cmd.align`

Per `tmp/pymol-src/modules/pymol/fitting.py:316-320` (the `align` docstring): *"`align` does a good job on proteins with decent sequence similarity (identity >30%). For comparing proteins with lower sequence identity, the `super` and `cealign` commands perform better."* A domain-shift mutant is exactly the structurally-divergent case `super` is designed for (`fitting.py:242-304`). `super` also works on the tiny placeholder fixture (empirically confirmed, `05.3-RESEARCH-pymol-align-api.md` §A.5), so it is the right default for BOTH the prototype and the real-structure convention.

- **`cmd.super`** — sequence-INDEPENDENT structural alignment + refinement. The right tool for low homology / conformational divergence / domain shifts. **DEFAULT METHOD.**
- **`cmd.align`** — sequence alignment + structural refinement. For same-protein / >30% identity (e.g. a same-protein point mutant like the 6CFO WT vs 6CER V138M pair — identical sequence, one residue). Available as `args["method"] = "align"` for Phase 7 same-protein cases.
- **`cmd.cealign`** — CE algorithm; reserved for very-low-homology Phase 7 cases (NOT the headless prototype — needs ≥16 CA atoms, `fitting.py:81-92`, fails on tiny fixtures; ALSO has a **reversed arg order** `(target, mobile)` + a dict return `{"RMSD","alignment_length","rotation_matrix"}`, `fitting.py:27, 135` — the dispatch normalizes both; see §6).
- **Do NOT use `cmd.fit` / `cmd.pair_fit`** — they assume matched atom ordering, which a domain-shift mutant violates. `cmd.superpose` does NOT exist in PyMOL 2.5.0 (`05.3-RESEARCH-pymol-align-api.md` §B).

### Scope the alignment to a stable substructure via atom selections

A **GLOBAL** all-atom `cmd.super` is **POOR** for a domain-shift mutant: the outlier-rejection cycles silently discard the shifted domain (`fitting.py:335-336`, `fitting.py:243-244`; `05.3-RESEARCH-pymol-align-api.md` §G Pitfall 3), the post-outlier RMSD is dominated by the shift, and the "restored" overlay looks misleadingly wrong.

The scientifically sound approach is a **substructure / local superposition on a stable reference** (active-site core / conserved domain / conserved catalytic residues):

```python
# mobile = WT object (moved); target/fixed = edited enzyme (stays)
cmd.super("<enzyme>_wt and <align_sele>", "<enzyme> and <align_sele>")
```

- `transform=1` (default, `fitting.py:245, 308`) transforms the **WHOLE `<enzyme>_wt` object** using the transform derived from the substructure — empirically confirmed (`05.3-RESEARCH-pymol-align-api.md` §A.5: scoping to `name CA` moved the whole `wt` object). The active site lines up; the shifted domain shows the conformational difference as the **visible pedagogical payload** (the offset between the aligned WT and the mutant — "this is what healthy looks like; here's where the mutant differs").
- **`align_sele` scopes MATCHING, not TRANSFORMATION** — the whole mobile object always moves (`05.3-RESEARCH-pymol-align-api.md` §G Pitfall 5). To transform only a fragment you'd `cmd.create` the fragment into its own object first (not needed for the convention).

### `align_sele` is a per-enzyme metadata field (Phase 7-authored, source-approved)

The convention specifies the **FIELD**; Phase 7 fills it per enzyme with a source-approved stable-core selection (which residues define the stable core — a structural-science claim needing a citation, `05.3-RESEARCH-integration-design.md` §H Q4 / Q8).

- **Default when unspecified:** `"name CA"` — the standard structural-alignment choice (CA-only, residue-paired, robust for both the prototype and real structures; the standard fallback for minor/no-conformational-difference mutants).
- **`None`** = whole object (no substructure scoping).

> **Why `"name CA"` is the right default (not whole-object all-atom):** a whole-object all-atom `super` on a domain-shift mutant hits Pitfall 3 (`05.3-RESEARCH-pymol-align-api.md` §G) — outlier rejection silently discards the shifted domain, giving a misleading "good" RMSD over only the stable core. CA-only matching makes the intent explicit (residue-paired, backbone-frame) and avoids the silent-discard trap. Per-enzyme stable-core overrides (`"name CA and resi 100-160"`) are the Phase 7 domain-shift refinement.

### Argument-order gotcha — `target` = FIXED reference, NOT "the thing aimed at"

*(Per RESEARCH-pymol-align-api §G Pitfall 1; empirically verified §A.5.)*

PyMOL's `target` arg means the **FIXED reference**, NOT English "target = thing aimed at = the thing that moves". `cmd.super(mobile, target)` **MOVES `mobile`, leaves `target` fixed** (empirically: `align("wt","mut")` moved `wt` [x: 5→0], left `mut` at 0, `05.3-RESEARCH-pymol-align-api.md` §A.5).

For the restoration reveal:
- **mobile = `<enzyme>_wt`** (the WT slides into the edited enzyme's frame so the camera doesn't jump)
- **target / fixed = `<enzyme>`** (the edited enzyme the player is looking at)

RMSD is **symmetric** (the optimal superposition minimizes the same quantity regardless of which object moves), so this is a **VISUAL choice, not a scientific one** — picked so the player's view doesn't jump when the WT slides in.

### Do NOT reimplement alignment

`align` / `super` / `cealign` are BUILT-IN `cmd.*` (AGENTS.md). The only custom code is the ~10-line `op="align"` dispatch in `molops.py` (specified in §6, **deferred to Phase 6** per §8 Q3). The structural-alignment math is entirely PyMOL's; the dispatch's value-add is **encapsulating the two API footguns** (the `cealign` reversed arg order + the `target=fixed` naming collision) so story authors never hit them.

## §5. How it is presented + the honest narrative

*(Per RESEARCH-integration-design §C / §D.)*

### Presentation table

| Presentation | What it shows | Pedagogy | Scientific clarity | Phase 6 cost |
|--------------|---------------|----------|--------------------|--------------|
| **Replacement** | hide/delete the edited-mutant; show only the aligned WT | Cleanest "this is what healthy looks like" | Loses the before/after comparison | Low (existing `hide` / `delete` / `show_as` ops) |
| **Side-by-side** | edited-mutant + aligned WT in separate viewports/offsets | Best for direct comparison | Clear (two separate frames) | **High** — PyMOL multi-viewport (`set grid_mode`, `cmd.viewport`) is a Phase 6 UI concern; non-trivial headless verification |
| **Overlay** | both objects visible, aligned, different colors | Shows the conformational difference DIRECTLY (the domain shift is visible as misalignment of peripheral regions after active-site-core `super`) | Strongest for the "major conformational difference" pedagogical case the phase goal targets | Low-medium (existing `color` op; two objects coexist) |

### Defaults

- **DEFAULT = OVERLAY for `conformational_difference: "major"` mutants** (the phase goal's target case): the edited/restored `<enzyme>` in one color, `<enzyme>_wt` aligned WT in another color, both visible after the active-site-core `super`. The domain shift is the visible pedagogical payload.
- **FALLBACK = REPLACE for `"minor"` / `"none"`** (or under approach (a) where the `restore` shortcut yields a single WT object): hide the edited-mutant, show only the WT-aligned object. Cleaner; no redundant overlay.
- **Side-by-side (multi-viewport) is a Phase 6 UI concern, NOT a 5.3 data-level concern.** 5.3 only ensures the **two objects exist + are aligned** so 5.4 / 6 can *choose* to present them overlaid OR split into viewports. The data-level mechanism is presentation-agnostic.

A **`present` directive field** (`"overlay" | "replace"`, default per `conformational_difference`) records which case for 5.4 (see §7.1). 5.4 layers `show_as` / `color` / `zoom` / `viewport` on top; it does **NOT** re-decide the object set or re-align.
