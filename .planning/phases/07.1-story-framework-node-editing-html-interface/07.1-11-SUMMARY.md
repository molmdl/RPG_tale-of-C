## Confidence statement (the Firefox file:// policy reasoning)

- **fetch() cannot read file:// URLs in Firefox: VERY HIGH.** Verified against MFSA 2019-21 (mozilla.org, fetched during this session): CVE-2019-11730 is titled "Same-origin policy treats all files in a directory as having the same-origin" and its description names the Fetch API as the exfiltration primitive; removing file: URLs from fetch is the closure of exactly that hole.
- **Same-directory-or-below classic reads are permitted: HIGH.** `security.fileuri.strict_origin_policy` defaults to true and has always permitted same-dir-or-below file reads for classic subresources; the user's own `tmp/network_all.html` → same-dir iframe works in their Firefox today — the policy in question demonstrably permits it on their machine.
- **XHR sits in the same permitted class as the iframe: HIGH** — XHR is a classic subresource read (pre-dates fetch; no documented carve-out excludes it from the same-dir policy; the pre-68 world read local files with XHR routinely). This is the one inferential step; it is exactly what the re-verification proves or disproves.
- **The pick live-FileList fix: the snapshot is correct regardless of browser internals** (it cannot regress anything); MEDIUM-HIGH that it was THE cause of the dead pick in the user's Firefox (Firefox's input.files is a live view; the symptom — total silence, no console error — matches the early return exactly).
- **What remains genuinely unproven from WSL:** whether the real Firefox XHR read of `data/story_glucose/manifest.json` (a SUB-directory of the HTML's dir) is granted on the user's machine. Everything else is machine-proven.
