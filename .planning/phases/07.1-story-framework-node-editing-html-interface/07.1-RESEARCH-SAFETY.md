## Summary

This research answers: "How does the editor keep the engine + test battery green, and how do undo/redo/draft/save interact with the repo's existing safety conventions?"

**What was found.** The gate battery is small, fully scripted, and almost entirely data-driven — which makes nearly every check **portable to client-side JS as pre-save validation**. All gate invocations were re-run live and match the 07-18-SUMMARY gate table exactly: suite 345 OK; citation gate exit 1 at the sanctioned 2-stub residual; edit coverage 12/12 exit 0; both AST gates exit 0; the 57/21/4-tier/15-edit-allowed invariants re-verified against the raw JSON in this session. The one gap: **5.4 template conformance is NOT a committed automated gate** — it was a one-off data-level verification pass (07-17, harness in gitignored `tmp/opencode-0717/`); the only committed artifact is the fixture-based PyMOL mechanism smoke.

**Key structural findings the planner must design around:**

1. **Pinned-count tests make add/delete node a TEST-UPDATE event, not just a data edit.** `test_manifest_loads_all_57_nodes` asserts `== 57` exactly; `test_15_edit_allowed_nodes` asserts exactly 15; `test_reachability_green_all_four_tiers` asserts exactly 21 endings (1T+3G+2N+15B); the viewer pins `EXPECTED_NODES=57` / `EXPECTED_TIER_COUNTS` / `EXPECTED_EDIT_ALLOWED` (viewer lines 96-105). The editor cannot silently ship a topology change that moves these counts — the pre-save validator must DETECT the count change and force an explicit "pinned counts will change: 57→N, endings 21→M, edit-allowed 15→K; the pinned tests + viewer constants must be updated in the same commit" acknowledgment.
2. **The house JSON style is NOT `json.dumps` default.** All data files use indent=2 with short scalar arrays and small flat objects inlined on one line (`"claim_ids": ["GLY-INTRO-01"]`, cast entries as one-line objects, edits.json signatures inline). A naive reserializer would reflow every file → massive spurious diffs (this repo's precedent is byte-identical diffs as the successful outcome, 07-17). The editor needs a house-style serializer + a diff-hygiene check in the human-verify script.
3. **The browser cannot write repo files directly** except via the **File System Access API** (Chrome/Edge 86+, Windows — the human-verify script's target browsers). Drafts go to git-ignored `tmp/` (rule `tmp` at HEAD .gitignore line 14, verified via `git check-ignore -v`); `dist/` is also git-ignored (line 25), so the committed editor HTML must live at a non-ignored path — `tools/story_editor.html` recommended. The plugin zip is unaffected: `build_plugin_zip.sh` zips only `rpg/` + a copy of `data/story_glucose`, and its sanity check REJECTS any entry outside `rpg/` — so a committed `tools/*.html` can never be bundled, no build change needed.
4. **No existing tool backs up data JSONs.** The `_bak_` convention is PyMOL in-session object backups only (`rpg/pymol_layer/edit_ops.py:199`). Git is the real safety net. Recommendation: editor writes `pre-save` backups into `tmp/story_editor_drafts/backups/` (ignored) before overwriting, and the human-verify script checks `git diff` shows only intended changes.

**Primary recommendation:** Reuse the viewer's pinned-invariant pattern as the editor's pre-save validator (JS port of: reachability BFS, tier/edit-allowed counts, dangling-divert/dangling-pool/coverage/claim checks, two-layer/no-TBD scans, house-style serialization), gate every save on it; drafts as git-ignored JSON snapshots under `tmp/story_editor_drafts/` with fingerprint-based stale-draft detection; undo/redo as an in-memory command stack invalidated on draft-reload/save; every save is human-verified by the gate battery + `git diff` review.

## Draft / Save / Undo Semantics — Design Recommendation

### Where drafts live (repo facts + recommendation)
- **Repo fact:** `tmp` is git-ignored at HEAD — `.gitignore` line 14, bare rule `tmp` (verified `git check-ignore -v tmp/` → `.gitignore:14:tmp`). Anything under `tmp/` is ignored, incl. nested dirs. Precedent: `tmp/opencode-0717/` scratch harnesses.
- **Recommendation (MEDIUM — design proposal, no repo prior art):** drafts at `tmp/story_editor_drafts/`:
  - `draft.json` — the single rolling draft: `{fingerprint, saved_at, model, changed_files:[...], undo_meta}`.
  - `snapshots/snapshot-YYYYMMDD-HHMMSS.json` — explicit named checkpoints (cheap, git-ignored).
  - `backups/<origname>-<ts>.json` — pre-save copies of real data files before overwrite.
- **Write mechanics (browser reality):** the browser cannot silently write repo paths. Primary path: **File System Access API** (`showOpenFilePicker`/`showSaveFilePicker`/writable streams) — Chrome/Edge 86+ on Windows, works from `file://` pages, one permission grant per file per session (MEDIUM confidence — well-established API, but verify the exact `file://` + permission behavior in the human-verify pass). Fallback: `<a download>` Blob download of the draft JSON into Downloads + the human moves it into `tmp/story_editor_drafts/` (drag in Explorer). **Third layer regardless: localStorage autosave** keyed by the bundle fingerprint — crash/refresh recovery that needs zero permissions. The spec's "draft = tmp file" is satisfied by the explicit Save-draft action; localStorage is the invisible autosave underneath.

### Draft fingerprint / stale-draft invalidation (danger case)
- Compute a fingerprint over the loaded bundle at open time (e.g. sha-256 over the concatenated file contents, or `{n_nodes, n_endings, per-file byte lengths}` as a cheap approximation — JS `crypto.subtle` works on `file://` in Chrome/Edge; a byte-length+count tuple is an acceptable weaker fallback).
- Store the fingerprint + a git rev (`git rev-parse HEAD` value pasted into the editor, or just the fingerprint) INSIDE the draft.
- On draft load: if the current data's fingerprint ≠ the draft's fingerprint → **warn loudly: "Data changed since this draft was saved (e.g. a real save landed, or another agent edited the data). Loading may clobber newer changes."** Offer: load anyway (draft wins) / discard draft. After a successful real save, the editor marks the draft stale/superseded and clears the autosave for the saved files (a draft older than the last save of the same files must never silently resurrect old content).

### Save-edit semantics for multi-file edits (atomicity options, decision material)
The edit surface spans `data/story_glucose/*.json` (7 story files + manifest), `rpg/data/edits.json`, `rpg/data/cast.json`. Browser writes are per-file; there is NO atomic multi-file write. Options:

| Option | Mechanism | Atomicity | Assessment |
|--------|-----------|-----------|------------|
| **A. Per-file saves, only-changed-files (RECOMMENDED)** | "Save edit" lists every modified file; each is written separately (FS Access API) or downloaded individually; a pre-save backup of each goes to `tmp/story_editor_drafts/backups/` first | None across files — mitigated by: git working tree (diff + `git checkout -- <file>` per file is the true atomic undo), pre-save backups, and the immediate gate battery | Matches repo reality: git IS the atomicity layer; content commits were single-file-ish (`git log -- data/story_glucose/`: one commit per segment). Simplest to build, simplest to review |
| B. Single bundle download | One `editor_change_bundle.json` containing every new file body; a small Python applier writes them | All-or-nothing inside the applier | Adds a new tool + a two-step human flow; only worth it if multi-file consistency proves fragile in practice |
| C. One-file-per-save discipline | The editor only ever allows one logical file to be dirty | N/A | Too restrictive — a cast add (B7) legitimately touches cast.json + edits.json together |

- **Recommended save sequence (per file):** 1) pre-save validation green (breakage map above); 2) backup current bytes to `tmp/story_editor_drafts/backups/<name>-<ts>.json`; 3) serialize house-style; 4) write; 5) show the file list written + "now run the gate battery" checklist.
- **Backup convention finding:** NO existing tool backs up data JSONs — the `_bak_` convention (`rpg/pymol_layer/edit_ops.py:199`) is PyMOL in-session molecular-object backup only; content data changes relied on git history. The `tmp/backups` step above is a NEW convention (recommend it; git remains the primary safety net; a sibling `.bak` beside the data file would show as untracked noise in `git status` — keep backups under git-ignored `tmp/`).

### Serialization: the house JSON style (HIGH-confidence repo fact, HIGH-impact pitfall)
All data JSONs are hand-styled: indent=2, short scalar arrays inline (`"claim_ids": ["GLY-INTRO-01"]`), small flat objects inline on one line (cast entries, edits.json `signature` dicts), long strings unbroken, trailing newline. Verified: `json.dumps(d, indent=2)` does NOT round-trip glycolysis.json byte-identically (first divergence at line 6 — the inline claim_ids array). `json.dumps(indent=1)` (the viewer's model dump, viewer :1891) is a DIFFERENT style used only for the viewer's derived payload, not the data files.
**Consequence:** a naive reserializer reflows entire files → review-hostile diffs that bury the intended change (and this repo's precedent treats byte-identical diffs as the gold outcome, 07-17). **Recommendation (MEDIUM):** implement a deterministic JS house-style serializer (indent 2; inline an array/object when its compact form fits ~100 chars on one line; stable key order = insertion order of the loaded JSON, JS objects preserve it for string keys) + add a **diff-hygiene check** to the human-verify script: `git diff --stat` must show changes confined to the intended regions, and `git diff` of a no-op save must be empty (save-without-edit ⇒ byte-identical). If the house-style serializer proves too costly, the fallback (accept full reflow) must be an explicit user decision — do not slip it in.

### Undo/redo (recommendation — LOW/MEDIUM, no repo prior art; the viewer is read-only and nothing in rpg/ or tools/ implements undo)
- **Model:** command-stack over the in-browser document (deep-clone snapshots or command objects). Snapshot-per-edit is simplest and safe at this data size (whole bundle ≈ 130 KB JSON).
- **Depth:** 50–100 entries (generous; memory trivial at this size). Redo stack cleared on any new edit (standard semantics).
- **Persistence:** undo history does NOT survive draft reload — on draft load, history resets to a single "loaded draft" base state (keep the pre-load session state in the previous autosave slot for one-level back-out). Undo never reaches across a real save: after "save edit", undo remains available in-session for further edits, but the saved baseline is git; the pre-save backups in `tmp/` cover the save-action itself.
- **Danger cases to handle:** (a) undo across a structural delete that other edits referenced — snapshot semantics handles this naturally (full-state restore), another argument for snapshots over command-inversion; (b) stale draft resurrecting pre-save content — covered by fingerprint invalidation above; (c) undo after an external data change (another agent editing data mid-session) — the fingerprint check on save catches it: re-verify the on-disk bytes still match the fingerprint captured at load before writing (FS Access API gives a fresh File handle; compare `lastModified`+size or re-read).

## Common Pitfalls (phase-specific)

### Pitfall S1: Naive JSON reserialization reflows files
**What goes wrong:** `json.dumps`-equivalent save rewrites every inline array/object → whole-file diffs; intended change unreviewable; violates the repo's byte-hygiene precedent.
**Avoid:** house-style serializer (indent 2, inline short containers) + the no-op-save byte-identical check in human-verify step 5c.

### Pitfall S2: Editor green ≠ battery green (count pins)
**What goes wrong:** the editor's pre-save validator passes a topology edit (it's structurally valid), but the 345-suite fails on the pinned 57/21/15 counts.
**Avoid:** the count-shift detector (Breakage Map B1/B2) — make pinned-count movement an explicit, acknowledged event with a checklist naming the exact tests + viewer constants to update.

### Pitfall S3: Stale draft clobbers a real save
**What goes wrong:** draft restored after data moved forward (real save or concurrent agent) → silent content regression.
**Avoid:** fingerprint at load + stored in draft + compared on restore AND on save (re-verify on-disk bytes before overwrite); clear/supersede the draft after a successful save.

### Pitfall S4: Pre-save validator drifts from the Python gates
**What goes wrong:** JS validation semantics diverge (e.g. JS BFS follows conds; JS treats empty per-enzyme pool as error) → editor blocks valid saves or passes invalid ones.
**Avoid:** port from the cited Python lines; each JS rule in the plan cites its source (path:line), same convention as the repo's `# src:` citations.

### Pitfall S5: Editor HTML lands in dist/
**What goes wrong:** committed into an ignored path → silently absent from git; or placed in rpg/ → bundled into the plugin zip.
**Avoid:** `tools/story_editor.html` (tracked, unzipped — verified above); never `dist/`, never `rpg/`.

### Pitfall S6: citation-gate sanctioned residual mis-encoded in JS
**What goes wrong:** JS pre-save check demands literal zero MISSING → the 2 sanctioned stubs block every save; or the opposite — JS allows PLACEHOLDER_PHASE8 anywhere → new stub nodes slip through and break `test_placeholder_phase8_only_on_documented_stubs`.
**Avoid:** encode the residual EXACTLY: `PLACEHOLDER_PHASE8` permitted only as fa.stub/alc.stub's claim_id; any other node/claim combination referencing it is an error.
