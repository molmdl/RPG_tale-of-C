## 2. Node-type taxonomy (SC1)

### The 5 SC1 types as a DERIVED property + a tags declaration (ZERO schema change)

SC1 requires every node TYPED as one of `story` / `choice` / `rng-shuffle` /
`edit-allowed` / `ending`. Reading the actual `Node` class
(`c14/story/model.py:239-329`), the model fields are: `id`, `text_dramatic`,
`text_teaching`, `claim_ids[]`, `choices[]`, `on_enter[]`, `is_ending`
(None|"true"|"good"|"normal"|"bad"), `tags[]`, `on_enter_divert`. There is
**no** `node_type` field.

The 5 SC1 types map to existing fields as follows (research Q1 Option c
RECOMMENDED):

| SC1 type | Existing field(s) that express it | Source (file:line) | Derivable? |
|----------|-----------------------------------|--------------------|------------|
| `ending` | `Node.is_ending is not None` | `model.py:269`, `:311-314` | YES — derived |
| `rng-shuffle` | any `Choice.weight is not None` among `Node.choices` | `model.py:189`, `interpreter.py:61` | YES — derived |
| `choice` | `len(Node.choices) > 0` | `model.py:267`, `interpreter.py:60` | YES — derived |
| `edit-allowed` | NONE — declared via `tags` entry `edit:enzyme:<id>` | (see §5) | NO — must be declared |
| `story` | default: not ending, no choices, no edit declaration | `model.py:259-271` | YES — derived (the "none of the above" case) |

### The 5 types are a SET of roles, NOT a single enum

A node can hold several of these at once. The canonical example is the
ARCHITECTURE.md TCA shuffle node (`tca.shuffle` in the skeleton) which is
SIMULTANEOUSLY `rng-shuffle` (it has 2 weighted choices) AND `choice` (it has
non-weighted choices — an edit:offer + a cond-gated cycle-trap) AND
`edit-allowed` (it carries `edit:enzyme:tca.aconitase` in its tags). A
single-valued `node_type` field CANNOT represent this reality — it would
force a false classification. **A single-valued `node_type` field is REJECTED**
(it breaks the engine's mixed weighted/non-weighted choices on one node,
`interpreter.py:60-73`).

### The classifier helper (documentation reference — NOT new runtime code)

The interpreter already dispatches on these exact fields; the following
pure-Python helper is a DESIGN-DOC reference that documents the derivation:

```python
def node_types(node):
    """Return the SET of structural roles a node plays (SC1 taxonomy).

    Documentation reference only -- the interpreter already dispatches on
    these exact fields. A node can hold several roles at once (e.g. the TCA
    shuffle node is rng-shuffle + choice + edit-allowed).
    """
    types = []
    if node.is_ending is not None:                          # model.py:269
        types.append("ending")
    if any(c.weight is not None for c in node.choices):     # model.py:189
        types.append("rng-shuffle")
    if len(node.choices) > 0:                               # model.py:267
        types.append("choice")
    if any(t.startswith("edit:enzyme:") for t in node.tags):  # Q3 declaration
        types.append("edit-allowed")
    if not types:                                           # none of the above
        types.append("story")
    return types
```

**Why this is correct and backward-compatible:**
- Uses ONLY existing fields. `Node.from_dict` (`model.py:273-293`) already
  parses `is_ending`, `choices` (as `Choice` objects), and `tags` via `.get`.
  No `from_dict`/`to_dict` change needed.
- Matches the interpreter's actual dispatch: `pick_choice` splits weighted vs
  non-weighted on the SAME node (`interpreter.py:60-73`); `enter_node` checks
  `is_ending` (`interpreter.py:97`); the engine presents `node.choices` as
  `eligible_choices` (`engine.py:193`).
- Multi-role nodes are first-class (the TCA shuffle node →
  `["rng-shuffle", "choice", "edit-allowed"]`).

### Structural type (SC1) vs SC5 class — ORTHOGONAL axes

- **Structural type (SC1, this section):** the MECHANISM a node uses —
  `ending` / `rng-shuffle` / `choice` / `edit-allowed` / `story`. A node has a
  SET. Derived from fields + the edit tag.
- **SC5 classification (§6):** the GAMEPLAY role — `MC-choice` / `edit-allowed`
  / `both` / `neither`. A node has ONE. A per-node DESIGN decision.

They correlate but are NOT identical: an `rng-shuffle` node (structural) is
`MC-choice` (gameplay — the RNG is the "multiple-choice" agent). A `story`
node with a single forced "Continue" choice (structural type = `choice`
because `len(choices)>0`) is `neither` (gameplay role = narrative progression,
NOT a branching choice). The SC5 class is a gameplay design decision per node,
informed by but NOT mechanically equal to the structural type set (see §6 for
the full derivation rule + the per-node table).

### on_enter_divert DORMANCY (affects the `story` type)

`Node.on_enter_divert` ("auto-advance target node id", `model.py:255`) is
defined, round-tripped by `from_dict`/`to_dict` (`model.py:292`, `:307`), and
tested for default-None + round-trip (`tests/test_model.py:64`, `:129`) — but
it is **NEVER referenced by `interpreter.py` or `engine.py`** (verified via
grep: `on_enter_divert` appears only in `model.py` + `test_model.py`).
Consequence: a non-ending node with NO `choices` is a **dead end** —
`engine.choose` calls `pick_choice` which returns `[]` (empty eligible list,
`interpreter.py:60`), then `index >= len(pick)` raises `IndexError`
(`engine.py:124-127`).

**Skeleton resolution:** every non-ending node has ≥1 `choice` (a single-option
"Continue" choice whose `goto` is the next node — `choices: [{label: "Continue",
goto: "next.node"}]`). This requires ZERO engine changes and keeps
`on_enter_divert` reserved for a future engine extension. The BFS
(`check_reachability`) follows `choice.goto` edges ONLY (not `on_enter_divert`),
so using choices for forward paths is also the reachability-critical design
(see §7). `on_enter_divert` dormancy is flagged as an open question (§9 OQ8).

## 4. Choice-point contract (SC3)

### The 5-facet spec per choice node

The "text MC → graph edge" mechanism is fully implemented in `interpreter.py`
+ `engine.py`. The contract makes it an explicit, reviewable spec. For each
choice/rng-shuffle node, the design doc captures these 5 facets (research Q2
table):

| Facet | What it is | Existing mechanism (file:line) |
|-------|------------|-------------------------------|
| **(a) Player-facing options** | The list of labels the UI shows the player | `Choice.label` (`model.py:171`); engine returns `node.choices` as `TurnResult.eligible_choices` (`engine.py:193`) |
| **(b) The edge each selects** | The target node id advancing to | `Choice.goto` (`model.py:172`); `engine.choose` advances via `self._enter(choice.goto)` (`engine.py:133`) |
| **(c) MolActions fired on traversal** | What fires when the player picks — in order | `choice.effects` applied to GameState FIRST (`engine.py:132` → `interpreter.apply_effects`, `interpreter.py:137-154`), THEN the target node's `on_enter` MolActions emitted (`engine.py:133` → `_enter` → `interpreter.enter_node`, `interpreter.py:75-99`; dispatched per-action to sink at `engine.py:187-189`) |
| **(d) How `cond` gates options** | A choice with a falsy `cond` is hidden (not eligible) | `interpreter._cond` (`interpreter.py:101-135`): `None`→always eligible; else `eval(cond, {"__builtins__":{}}, {flags, char, counters, visits})`; ANY exception → `False` (fail-safe hide) |
| **(e) How `weight` makes an RNG branch** | A weighted choice is RNG-picked (not player-picked) | `interpreter.pick_choice` (`interpreter.py:43-73`): eligible = cond-passing; if ANY eligible has `weight` AND total>0 → single RNG pick (`rng.random()*total` + cumulative sum); else → full eligible list for the player to pick by index |

### Key distinctions the contract MUST state

1. **`choice.effects` are STATE mutations, NOT MolActions.** `effects` is a dict
   with optional `"set"` (flags) and `"incr"` (counters) sub-dicts
   (`interpreter.py:137-154`). It mutates `GameState`; it does NOT emit
   `MolAction`s. The MolActions that change the molecular scene come from the
   **target node's `on_enter`**. Do not conflate them.
2. **Order of operations on a choice traversal:** (i) `pick_choice` resolves
   (RNG or player-index) → one `Choice`; (ii) `apply_effects(choice)` mutates
   state (`engine.py:132`); (iii) `_enter(choice.goto)` emits the target's
   `on_enter` MolActions + records the visit + detects ending
   (`engine.py:133` → `interpreter.enter_node`). Authors put state changes in
   `choice.effects` and scene changes in `target.on_enter`.
3. **`cond` vs `weight` are orthogonal.** `cond` filters ELIGIBILITY (a
   falsy-cond choice is hidden from BOTH the player and the RNG). `weight`
   decides WHO picks among the eligible (RNG if any weighted, else player). A
   choice can have both (a weighted, conditionally-gated branch).
4. **`on_enter_divert` is NOT followed** (see §2 dormancy). Edges are
   `choice.goto` ONLY. Do not author auto-advance nodes expecting
   `on_enter_divert` to work.

> **Note on `tca.shuffle` RNG mechanics:** when the player triggers the choice
> resolution, `pick_choice` (`interpreter.py:43-73`) sees 4 eligible choices:
> 2 weighted (turn1=0.5, turn2=0.5, total=1.0) + 2 non-weighted (edit:offer +
> cycle-trap, if their conds pass). Because ANY eligible has weight AND total>0,
> the RNG picks ONE among ALL eligible via `rng.random()*total` + cumulative sum.
> The non-weighted choices (edit:offer, cycle-trap) are effectively
> player-triggered but RNG-decided WHEN a weighted choice is present. The
> cycle-trap choice has `cond: "visits.get('tca.shuffle', 0) > 5"` — it only
> becomes eligible after 5+ visits; before that, the RNG picks turn1/turn2. The
> edit:offer choice is always eligible (no cond) but the RNG may not pick it
> (it has no weight, so it's not in the weighted cumulative sum — it's only
> pickable if the player explicitly chooses it by index when NO weighted
> choice is eligible, which never happens here since turn1+turn2 are always
> eligible). **Phase 6 UI design must clarify how the player triggers the
> edit:offer vs the RNG shuffle** — this is a UI/UX open question for Plan 06.

## 5. Edit-node contract (SC4)

### The 5-step data-flow (player edit → routed node → applied edit)

The contract documents this 5-step data-flow (verified against
`engine.py:135-161` + `edit_router.py:122-149` + the fixture
`tests/fixtures/edit_routing/`):

```
1. Player triggers an edit in the UI (pick residue, choose mutation).
2. Controller builds an EditIntent(op, target, args) — op ∈ {point_mutation,
   substrate_edit, protonation_change} (model.py:91-93).
3. Controller reads the CURRENT story node's enzyme_id binding (the
   edit:enzyme:<id> tag — see "enzyme_id binding mechanism" below) and calls
   engine.apply_player_edit(intent, enzyme_id)  (engine.py:135).
4. engine.apply_player_edit  (engine.py:135-161):
   a. node_id = edit_router.route(intent, enzyme_id, rng)  (edit_router.py:122-149)
      - KNOWN edit (exact signature match in enzymes[enzyme_id].edits)
        → branch_node  (the defined story node for this known edit)
      - UNKNOWN edit (no match, or enzyme_id not in table)
        → bad-ending pool node  (per-enzyme override else global fallback;
          uniform rng.weighted_pick(pool, [1.0]*len(pool)))
   b. state.add_edit({enzyme: enzyme_id, intent: edit_intent.to_dict(),
      route: node_id})  (records in edits_history)
   c. return self._enter(node_id)  (reuses existing _enter: on_enter MolActions
      flow to the existing molaction_sink; engine.py:163-194)
5. The routed node's on_enter applies the edit:
   - branch node on_enter has MolAction(op="edit", target=...,
     args={edit_type, sele, new_resn})
     (see fixture: tests/fixtures/edit_routing/story.json:12)
   - molops dispatches op="edit" → edit_ops (04-05) → cmd.alter + cmd.sort +
     cmd.rebuild
   - bad-ending pool nodes are ENDINGS (is_ending="bad") — on_enter is just
     scene reset (hide_all)
```

### enzyme_id binding mechanism (RECOMMENDED: tags entry `edit:enzyme:<id>`)

**Option 1 (RECOMMENDED — ADOPTED in the skeleton): a `tags` entry
`edit:enzyme:<enzyme_id>`.** Zero schema change. The existing `tags` list
(`model.py:270`) is the documented home for "game-side hook tags"
(`model.py:253`). One tag carries BOTH the edit-allowed declaration AND the
enzyme_id binding:

```json
"tags": ["stage:glycolysis", "edit:enzyme:gly.pfk"]
```

The controller extracts it:
```python
enzyme_id = next((t.split(":", 2)[2] for t in node.tags
                  if t.startswith("edit:enzyme:")), None)
```
If `None`, the node is not edit-allowed. Backward-compatible: `Node.from_dict`
already parses `tags` via `.get` (`model.py:291`); old nodes without the tag
load fine. No `to_dict` change (tags already round-trips, `model.py:306`).
No gate impact (see §8).

**Option 2 (ALTERNATIVE — flagged, NOT adopted): a new optional
`Node.edit_enzyme_id` field** (None when not edit-allowed). Cleaner/more
explicit; the binding is a first-class field. Backward-compatible with
`from_dict` if added as `d.get("edit_enzyme_id")`. REQUIRES a `to_dict` update
(`model.py:295-308`) for round-trip. A 4-line additive change. Flagged as an
open question (§9 OQ10) but NOT adopted (the tags approach needs zero
changes).

**Node-level vs choice-level tags:** the skeleton uses a NODE-level
`edit:enzyme:<id>` tag (the enzyme_id binding is a node property — the whole
node binds to one enzyme context for the EditRouter) AND a CHOICE-level
`edit:offer` tag (marks which choice launches the edit UI). They coexist:
the node tag declares "this node's enzyme context"; the choice tag declares
"this choice opens the edit UI". (ARCHITECTURE.md puts `edit:offer` on a
choice — the skeleton follows this AND adds the node-level binding.)

### The `edit.prompt` stub (structural vs runtime distinction)

The skeleton has ONE shared `edit.prompt` stub node (in `bad_endings.json`)
with 3 `choice.goto` edges to the edit-related bad endings:
- `bad.critical_residue_break` (the known-critical-residue edit route)
- `bad.lost_connection` (unknown edit, structural path A)
- `bad.released_from_host` (unknown edit, structural path B)

These are **STRUCTURAL edges for the BFS, NOT player-facing options.** At
runtime, the EditRouter (`c14/edit_router.py`) routes directly via
`engine.apply_player_edit(intent, enzyme_id)` — known → branch_node, unknown →
bad-ending pool — **BYPASSING the stub's choices entirely.** The stub exists
so `check_reachability` (the BFS) sees the 3 edit-related bad endings as
reachable (SC2); without the stub, those bad endings would have no incoming
`choice.goto` edge and would be flagged as `unreachable_endings` → RED.

**The stub has NO cancel/return choice** — at runtime, the player does not
visit `edit.prompt` as a story node; the controller calls
`apply_player_edit` which routes via the EditRouter. Phase 6+ implements the
real edit UI (the controller builds the `EditIntent`, reads the current
node's `edit:enzyme:<id>` tag, and calls `apply_player_edit`). The stub's 3
choices are structural BFS paths, documented in the SC3 table above as a
placeholder MC-choice node.
