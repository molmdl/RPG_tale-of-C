The OTHER track covers the story CONTENT/topology (the specific glucose node list, edges, branch points, endings). ## Summary

The Phase 2/4 engine is complete and the `Node`/`Choice`/`MolAction`/`EditIntent` data model (`c14/story/model.py`) is the hard contract the glucose skeleton JSON must fit. The model already has every field the 5 SC1 node "types" need EXCEPT an explicit edit-allowed/enzyme-binding declaration — and that gap can be closed with ZERO schema change by using the existing `tags` list (its documented purpose is "game-side hook tags", `model.py:253`). The 4 structural types (`ending` / `rng-shuffle` / `choice` / `story`) are a **derived property** computed from existing fields (`is_ending`, `choices[].weight`, `len(choices)`); the 5th (`edit-allowed`) is a **declared** tag. A node can hold several types at once (the ARCHITECTURE.md TCA shuffle node is simultaneously `rng-shuffle` AND `edit-allowed`), so SC1's 5-entry list is really a set of roles, not a single-valued enum — a single-valued `node_type` field would be wrong.

The choice-point contract (SC3) is almost fully implicit in the existing interpreter+engine: `Choice.label` = player-facing options, `Choice.goto` = the edge, `choice.effects` (state mutation) then `target.on_enter` (MolActions) fire on traversal, `cond` gates eligibility against `{flags,char,counters,visits}`, `weight` makes an RNG-weighted branch. The only surprise: `Node.on_enter_divert` is a **DORMANT field** — defined in the model and round-tripped by `from_dict`/`to_dict`, but NEVER referenced by `interpreter.py` or `engine.py`. Auto-advance nodes do not currently work; every non-ending node MUST have ≥1 `choice` or the player cannot advance (`engine.choose` raises `IndexError` on an empty eligible list).

The edit-node contract (SC4) has the biggest gap: `GameEngine.apply_player_edit(edit_intent, enzyme_id)` (`engine.py:135`) takes `enzyme_id` as a SEPARATE out-of-band argument — there is NO node-level declaration of "this node allows edits against enzyme X". The model anticipates this (`EditIntent.enzyme_id` docstring, `model.py:100-102`: "The current story node determines this; the controller passes it") but leaves the binding unspecified. Phase 5.1 must specify it. Recommended: a `tags` entry `edit:enzyme:<enzyme_id>` (zero schema change, backward-compatible, greppable, reviewable in a design-doc table). Alternative: a new optional `edit_enzyme_id` field (cleaner, also backward-compatible via `from_dict` `.get`, but requires a `to_dict` round-trip update + a planner decision).

Two location discrepancies are flagged for the planner: (1) `edits.json`/`cast.json` live at `c14/data/` (hardcoded by `tools/check_edit_coverage.py:42`), while ARCHITECTURE.md says `data/edits.json` (repo-root) — the tooling-bound path wins; do NOT move it without updating the tool. (2) story JSON lives at repo-root `data/story/` (dev-time, per ARCHITECTURE.md + existing `intro.json` + all tests), with a bundled `c14/data/story/` copy at runtime — the glucose skeleton goes at repo-root `data/story/`.

**Primary recommendation:** Express the 5 node types as a DERIVED property (no schema change) + a `tags`-based `edit:enzyme:<id>` declaration for edit-allowed; document the choice-point + edit-node contracts + the per-node SC5 classification in a single reviewable `05.1-DESIGN.md` companion doc with a per-node table; prove SC2 with the existing `check_reachability` green/red pattern already proven in `tests/test_integration.py:336-362`.

## Q1. Node-type taxonomy (SC1): how to express the 5 types using the EXISTING Node model

### The 5 SC1 types and what the existing model already gives them

SC1 requires every node TYPED as one of `story` / `choice` / `rng-shuffle` / `edit-allowed` / `ending`. Reading the actual `Node` class (`c14/story/model.py:239-329`), the model fields are: `id`, `text_dramatic`, `text_teaching`, `claim_ids[]`, `choices[]`, `on_enter[]`, `is_ending` (None|"true"|"good"|"normal"|"bad"), `tags[]`, `on_enter_divert`. There is **no** `node_type` field.

Mapping each SC1 type to existing fields:

| SC1 type | Existing field(s) that express it | Source (file:line) | Derivable? |
|----------|-----------------------------------|--------------------|------------|
| `ending` | `Node.is_ending is not None` (one of "true"/"good"/"normal"/"bad") | `model.py:269`, `:311-314` (`is_ending_node` property) | YES — derived |
| `rng-shuffle` | any `Choice.weight is not None` among `Node.choices` | `model.py:189` (Choice.weight), `interpreter.py:61` (weighted list) | YES — derived |
| `choice` | `len(Node.choices) > 0` (a node that offers player picks; may also contain weighted choices) | `model.py:267`, `interpreter.py:60` | YES — derived |
| `edit-allowed` | NONE — no existing field. The node must DECLARE it (binds to an `enzyme_id`) | (gap; see Q3) | NO — must be declared |
| `story` | default: not ending, no choices, no edit declaration (pure narrative/scene node) | `model.py:259-271` | YES — derived (the "none of the above" case) |

### Critical insight: the 5 "types" are a SET of roles, NOT a single enum

A node can hold several of these at once. The authoritative example is the ARCHITECTURE.md TCA shuffle node (`.planning/research/ARCHITECTURE.md:247-251`):

```json
"choices": [
  {"label": "Continue (luck decides)", "weight": 1.0, "goto": "tca.resolve", "tags": ["rng:weighted"]},
  {"label": "Try to edit the enzyme", "goto": "edit.prompt", "tags": ["edit:offer"]}
]
```

This single node is **simultaneously** `rng-shuffle` (it has a weighted choice) AND `choice` (it has a non-weighted "edit" choice the player picks) AND `edit-allowed` (it offers an edit). A single-valued `node_type` field CANNOT represent this reality — it would force a false classification. Therefore option (b) "a new optional `node_type` field" is **rejected**: it contradicts the engine's own design (the interpreter handles mixed weighted/non-weighted choices on one node, `interpreter.py:60-73`).

### The three options evaluated

**(a) `tags`-based convention** — e.g. `"type:story"`, `"type:choice"`, `"type:rng-shuffle"`, `"type:edit-allowed"`, `"type:ending"` as entries in `Node.tags`. Pros: zero schema change; `tags` is the documented home for "game-side hook tags" (`model.py:253`). Cons: redundant — 4 of the 5 are already derivable from existing fields, so a `type:ending` tag just duplicates `is_ending` and can drift out of sync; "type:" prefix is a misnomer for a set. **Verdict: redundant for 4/5, acceptable only for edit-allowed.**

**(b) new optional `node_type` field** — single-valued string. Pros: explicit. Cons: WRONG for the multi-role reality (see above); forces a false single classification on nodes that are choice+rng-shuffle+edit-allowed. **Verdict: rejected** (breaks the engine's mixed-choice design).

**(c) DERIVED property (computed from existing fields) + a `tags` declaration for edit-allowed** — Pros: zero schema change; zero redundancy (4/5 derived, never drift); the one non-derivable type (`edit-allowed`) uses `tags` for its designed purpose; naturally handles multi-role nodes (a node's "type" is a set, computed); matches how the interpreter actually works. Cons: the "type" is not a single JSON field a reviewer sees at a glance — BUT the per-node SC5 classification table in the design doc (Q4) makes it reviewable. **Verdict: RECOMMENDED.**

### Recommended approach: DERIVED types + `tags` for edit-allowed (zero schema change)

Define a pure-Python helper (design-doc reference, NOT a runtime requirement — the interpreter already dispatches on these fields) that classifies a node into a SET of structural roles:

```python
# Illustrative classifier (design-doc reference; the interpreter already
# dispatches on these exact fields, so this is documentation, not new runtime code).
def node_types(node):
    # type: (Node) -> list
    types = []
    if node.is_ending is not None:                      # model.py:269
        types.append("ending")
    if any(c.weight is not None for c in node.choices): # model.py:189
        types.append("rng-shuffle")
    if len(node.choices) > 0:                           # model.py:267
        types.append("choice")
    if any(t.startswith("edit:enzyme:") for t in node.tags):  # Q3 declaration
        types.append("edit-allowed")
    if not types:                                       # none of the above
        types.append("story")
    return types
```

**Why this is correct and backward-compatible:**
- It uses ONLY existing fields. `Node.from_dict` (`model.py:273-293`) already parses `is_ending`, `choices` (as `Choice` objects), and `tags` via `.get(...)`. No `from_dict`/`to_dict` change needed.
- It matches the interpreter's actual dispatch: `pick_choice` splits weighted vs non-weighted on the SAME node (`interpreter.py:60-73`); `enter_node` checks `is_ending` (`interpreter.py:97`); the engine presents `node.choices` as `eligible_choices` (`engine.py:193`).
- Multi-role nodes are first-class (the TCA node → `["rng-shuffle", "choice", "edit-allowed"]`).

**Relationship to SC5 (clarify — they are ORTHOGONAL axes):**
- **Structural type (SC1, this section):** the MECHANISM a node uses — `ending`/`rng-shuffle`/`choice`/`edit-allowed`/`story`. A node has a SET. Derived from fields + the edit tag.
- **SC5 classification (Q4):** the GAMEPLAY role — `MC-choice` / `edit-allowed` / `both` / `neither`. A node has ONE. A design decision per node.

They correlate but are not identical: an `rng-shuffle` node (structural) is `MC-choice` (gameplay — the RNG is the "multiple-choice" agent). A `story` node (no choices, no edit) is `neither`. A `choice`+`edit-allowed` node is `both`. The SC5 class is DERIVED from the structural type SET (see Q4 table), so the design doc only needs to AUTHOR the structural fields + the edit tag; the SC5 class is then determined and listed in the classification table for review.

### Flag: `on_enter_divert` is DORMANT (affects the `story` type)

`Node.on_enter_divert` ("auto-advance target node id", `model.py:255`) is defined, round-tripped by `from_dict`/`to_dict` (`model.py:292`, `:307`), and tested for default-None + round-trip (`tests/test_model.py:64`, `:129`) — but it is **NEVER referenced by `interpreter.py` or `engine.py`** (verified: `grep on_enter_divert` finds only `model.py` + `test_model.py`). Consequence: a `story` node with no `choices` and no `is_ending` is a **dead end** — `engine.choose` calls `pick_choice` which returns `[]` (empty eligible list, `interpreter.py:60`), then `index >= len(pick)` raises `IndexError` (`engine.py:124-127`). The planner has two options for auto-advance narrative nodes:
1. Give every non-ending `story` node at least one `choice` (e.g. a single "Continue" choice whose `goto` is the next node) — works today, no engine change.
2. Wire `on_enter_divert` into the engine (a Phase 5.1-proposed additive behavior — `engine._enter` would follow `node.on_enter_divert` after emitting `on_enter` if no choices are offered). This is a PROPOSED engine change and must be flagged for the planner; it is NOT required if option 1 is used.

**Recommendation:** use option 1 (a "Continue" choice) for the skeleton — it requires zero engine changes and keeps `on_enter_divert` reserved for a future engine extension. Flag option 2 as an open question (Q9).

## Q2. Choice-point contract (SC3): the EXACT spec the design doc must capture per choice node

### What the existing engine already does (the "text MC → graph edge" mechanism)

The mechanism is fully implemented in `interpreter.py` + `engine.py`. The contract makes it an explicit, reviewable spec instead of implicit code. For each choice node, the design doc must capture these 5 facets:

| Facet | What it is | Existing mechanism (file:line) |
|-------|------------|-------------------------------|
| **(a) Player-facing options** | The list of labels the UI shows the player | `Choice.label` (`model.py:171`); engine returns `node.choices` as `TurnResult.eligible_choices` (`engine.py:193`) |
| **(b) The edge each selects** | The target node id advancing to | `Choice.goto` (`model.py:172`); `engine.choose` advances via `self._enter(choice.goto)` (`engine.py:133`) |
| **(c) MolActions fired on traversal** | What fires when the player picks — in order | `choice.effects` applied to GameState FIRST (`engine.py:132` → `interpreter.apply_effects`, `interpreter.py:137-154`), THEN the target node's `on_enter` MolActions emitted (`engine.py:133` → `_enter` → `interpreter.enter_node`, `interpreter.py:75-99`; dispatched to sink at `engine.py:187-189`) |
| **(d) How `cond` gates options** | A choice with a falsy `cond` is hidden (not eligible) | `interpreter._cond` (`interpreter.py:101-135`): `None`→always eligible; else `eval(cond, {"__builtins__":{}}, {flags, char, counters, visits})`; ANY exception → `False` (fail-safe hide) |
| **(e) How `weight` makes an RNG branch** | A weighted choice is RNG-picked (not player-picked) | `interpreter.pick_choice` (`interpreter.py:43-73`): eligible = cond-passing; if ANY eligible has `weight` AND total>0 → single RNG pick (`rng.random()*total` + cumulative sum); else → full eligible list for the player to pick by index |

### Key distinctions the contract MUST state (to avoid planner/author confusion)

1. **`choice.effects` are STATE mutations, NOT MolActions.** `effects` is a dict with optional `"set"` (flags) and `"incr"` (counters) sub-dicts (`interpreter.py:137-154`). It mutates `GameState`; it does NOT emit `MolAction`s. The MolActions that change the molecular scene come from the **target node's `on_enter`**. The contract must not conflate them.
2. **Order of operations on a choice traversal:** (i) `pick_choice` resolves (RNG or player-index) → one `Choice`; (ii) `apply_effects(choice)` mutates state (`engine.py:132`); (iii) `_enter(choice.goto)` emits the target's `on_enter` MolActions + records the visit + detects ending (`engine.py:133` → `interpreter.enter_node`). The contract documents this order so authors know WHERE to put state changes (choice.effects) vs scene changes (target.on_enter).
3. **`cond` vs `weight` are orthogonal.** `cond` filters ELIGIBILITY (a falsy-cond choice is hidden from BOTH the player and the RNG). `weight` decides WHO picks among the eligible (RNG if any weighted, else player). A choice can have both (a weighted, conditionally-gated branch).
4. **`on_enter_divert` is NOT followed** (see Q1 flag). Edges are `choice.goto` ONLY. Do not author auto-advance nodes expecting `on_enter_divert` to work.

## Q3. Edit-node contract (SC4): the EXACT spec

### The gap: there is NO node-level edit declaration today

The edit ROUTING mechanism is complete (`c14/edit_router.py`), but the node→enzyme_id BINDING is not. `GameEngine.apply_player_edit(edit_intent, enzyme_id)` (`engine.py:135-161`) takes `enzyme_id` as a SEPARATE argument — the engine does NOT read it from the current node. The `EditIntent.enzyme_id` docstring (`model.py:100-102`) explicitly says: *"The current story node determines this (Phase 5.1 edit-node contract); the controller passes it."* — i.e. the model ANTICIPATES this contract but leaves the binding mechanism to Phase 5.1. This research specifies it.

### The full data-flow (player edit → routed node → applied edit)

The contract must document this 5-step data-flow (verified against `engine.py:135-161` + `edit_router.py:122-149` + the fixture `tests/fixtures/edit_routing/`):

```
1. Player triggers an edit in the UI (pick residue, choose mutation).
2. Controller builds an EditIntent(op, target, args) — op ∈ {point_mutation,
   substrate_edit, protonation_change} (model.py:91-93).
3. Controller reads the CURRENT story node's enzyme_id binding (Q3a/b below)
   and calls engine.apply_player_edit(intent, enzyme_id).
4. engine.apply_player_edit (engine.py:135-161):
   a. node_id = edit_router.route(intent, enzyme_id, rng)  (edit_router.py:122-149)
      - KNOWN edit (exact signature match in enzymes[enzyme_id].edits) → branch_node
      - UNKNOWN edit (no match, or unknown enzyme) → bad-ending pool node
        (per-enzyme override else global fallback; uniform rng.weighted_pick)
   b. state.add_edit({enzyme, intent, route: node_id})  (records in edits_history)
   c. return self._enter(node_id)  (reuses existing _enter: on_enter MolActions
      flow to the existing molaction_sink; engine.py:163-194)
5. The routed node's on_enter applies the edit:
   - branch node on_enter has MolAction(op="edit", target=..., args={edit_type, sele, new_resn})
     (see fixture: tests/fixtures/edit_routing/story.json:12)
   - molops dispatches op="edit" → edit_ops (04-05) → cmd.alter + cmd.sort + cmd.rebuild
   - bad-ending pool nodes are ENDINGS (is_ending="bad") — on_enter is just scene reset.
```

### The 5 facets the design doc must capture per edit-allowed node

| Facet | What it is | Existing mechanism (file:line) |
|-------|------------|-------------------------------|
| **(a) Node declares edit-allowed** | The node says "edits are offered here" | NONE today — proposed: `tags` entry (see Q3a below) |
| **(b) enzyme_id binding** | The EditRouter lookup bucket the node binds to | NONE today — proposed: `tags` entry `edit:enzyme:<id>` OR a new field (Q3b) |
| **(c) EditIntent per player action** | The `op`/`target`/`args` each player-edit-action produces; must match `edits.json` `signature` after `EditIntent.signature()` normalization | `EditIntent.signature()` (`model.py:112-126`): `{op, target.strip().lower(), {k: _norm_val(v)}}`; compared with `==` against `edits.json` `signature` (`edit_router.py:142`) |
| **(d) Routing outcome** | known → `branch_node`; unknown → bad-ending pool node | `EditRouter.route` (`edit_router.py:122-149`): exact dict-equality match → `entry["branch_node"]`; else `rng.weighted_pick(pool, [1.0]*len(pool))` |
| **(e) Routed node applies the edit** | The branch node's `on_enter` MolAction(op="edit") executes via molops→edit_ops | `engine._enter` (`engine.py:163-194`); fixture branch node (`tests/fixtures/edit_routing/story.json:9-15`): `on_enter: [{"op":"edit", "target":"...", "args":{"edit_type":"point_mutation","sele":"...","new_resn":"ALA"}}]` |

### (a)+(b) How a node DECLARES edit-allowed + binds to enzyme_id — two options

**Option 1 (RECOMMENDED): a `tags` entry `edit:enzyme:<enzyme_id>`.** Zero schema change. The existing `tags` list (`model.py:270`) is the documented home for "game-side hook tags" (`model.py:253`). One tag carries BOTH the edit-allowed declaration AND the enzyme_id binding:

```json
"tags": ["stage:tca", "edit:enzyme:example_aconitase"]
```

The controller extracts it: `enzyme_id = next((t.split(":", 2)[2] for t in node.tags if t.startswith("edit:enzyme:")), None)`. If `None`, the node is not edit-allowed. Backward-compatible: `Node.from_dict` already parses `tags` via `.get` (`model.py:291`); old nodes without the tag load fine. No `to_dict` change (tags already round-trips, `model.py:306`). No gate impact (see Q8).

**Option 2 (ALTERNATIVE): a new optional `Node.edit_enzyme_id` field** (None when not edit-allowed). Cleaner/more explicit than parsing a tag; the binding is a first-class field. Backward-compatible with `from_dict` if added as `d.get("edit_enzyme_id")` (mirrors `on_enter_divert=d.get(...)`, `model.py:292`). REQUIRES a `to_dict` update (`model.py:295-308`) for round-trip + a decision. The controller reads `node.edit_enzyme_id` directly.

**Recommendation:** Option 1 (`tags`) for the skeleton — it requires zero schema change, is fully backward-compatible, and uses `tags` for its designed purpose. Flag Option 2 as an open question (Q9) for the planner if they prefer first-class explicitness. NOTE: the TCA shuffle example in ARCHITECTURE.md (`:250`) puts `edit:offer` on a CHOICE tag (a choice-level edit offer), not the node. This research recommends a NODE-level `edit:enzyme:<id>` tag instead, because the enzyme_id binding is a node property (the whole node binds to one enzyme context for the EditRouter), and the player-edit UI is offered while the node is current — a node-level tag is the cleaner model. The choice-level `edit:offer` tag can coexist (it marks which CHOICE launches the edit UI) but the enzyme_id binding belongs on the node.

### (c) The EditIntent signature contract (the UI ↔ table agreement)

The edit-node contract must list, per edit-allowed node, the EditIntent each player-edit-action generates, in the SAME canonical form `edits.json` stores (so `EditRouter.route`'s exact `==` match works). `EditIntent.signature()` (`model.py:112-126`) normalizes: `op` verbatim; `target` → `.strip().lower()`; `args` → `{k: _norm_val(v)}` where `_norm_val` stringifies scalars and `json.dumps(sort_keys=True)`s nested dicts/lists (`model.py:154-164`). The `edits.json` `signature` must be written in THIS canonical form (lowercased target, stringified args). ### (d) Routing outcome — known vs unknown

Per `EditRouter.route` (`edit_router.py:122-149`):
- **KNOWN** (exact `signature` match in `enzymes[enzyme_id].edits`) → returns `entry["branch_node"]` (a defined story node). The branch node's `on_enter` applies the edit (facet e).
- **UNKNOWN** (no match, or `enzyme_id` not in table) → `bad_ending_pool(enzyme_id)` (per-enzyme override else global, `edit_router.py:151-166`), then `rng.weighted_pick(pool, [1.0]*len(pool))` (uniform, reproducible via the seeded RngEngine). Pool nodes MUST be endings (`is_ending="bad"` — `validate_edits_table` flags `pool_node_not_ending`, `edit_router.py:232-234`).
- Empty pool → `EditRoutingError` (`edit_router.py:146-148`) — fail-loud.

## Q5. Reachability validation (SC2): HOW the planner's task proves green/red

### The existing checker (verified)

`check_reachability(nodes, start_id)` (`c14/story/validate.py:167-207`) runs a BFS from `start_id` over `choice.goto` edges, returning a `ReachabilityReport` (`validate.py:86-117`) with `all_endings`, `reachable_endings`, `unreachable_endings`, and an `is_ok` property (True iff `unreachable_endings` is empty). Critical behavior, verified at `validate.py:191-203`:

- **The BFS does NOT evaluate `cond` or `weight`.** It follows EVERY `choice.goto` that points to an EXISTING node (`validate.py:198-202`). So conditional edges and RNG-weighted edges are ALL traversed for reachability — the skeleton must route every ending via a REAL `choice.goto` chain, not rely on a `cond` to gate reachability.
- A `goto` to a nonexistent node is simply not traversed (flagging it is `validate_graph`'s job, `validate.py:214-235` — a separate check).
- Missing `start_id` → graceful: `is_ok=False`, all endings unreachable (`validate.py:187-189`).
- Duck-types on Node objects OR raw dicts via `_choices`/`_goto`/`_is_ending` (`validate.py:124-160`).

### SC2 green test shape (all 4 ending tiers reachable)

Follow the proven pattern in `tests/test_integration.py:336-346`:

```python

assert rep.is_ok, "glucose skeleton has no orphaned endings"
```

`StoryGraph.load` returns the merged `{id: Node}` dict via `g.all_nodes()` (`graph.py:99-106`); `g.start_node()` returns the manifest's `start` (`graph.py:108-111`).

### CRITICAL: the aerobic-only-True-ending concern (SC2 satisfiability)

The True ending is biochemically unreachable anaerobically (no O2 → no ETC → no electron harvest → no True ending, per the resolved SC#3 framing-d decision, PROJECT.md). BUT `check_reachability` does NOT model O2 — it follows ALL `choice.goto` edges regardless of `cond`. Therefore:

- **The True ending MUST be statically reachable via a real `choice.goto` chain** (the aerobic path) — the BFS will find it. ✓
- **The anaerobic guard is a RUNTIME `cond` on a choice, NOT a structural edge.** The choice that leads toward the True ending has `cond: "flags.get('host_o2_low') is not True"` (or similar); at runtime, when `host_o2_low` is True, that choice is hidden (`interpreter._cond` returns False, `interpreter.py:134-135`) so the player cannot take it — but the STRUCTURAL edge still exists in the JSON, so the BFS traverses it for reachability. ✓
- **DO NOT model the anaerobic block as a missing structural edge** (e.g. a separate anaerobic sub-graph with the True ending physically absent) — that would make the True ending `unreachable_endings` and FAIL SC2. The skeleton must keep the True ending structurally reachable (aerobic path) and gate it at runtime via `cond`.

This is the key design rule for the skeleton topology: **`cond` gates RUNTIME eligibility; `choice.goto` gates STRUCTURAL reachability.** SC2 (structural reachability of all 4 tiers) is satisfiable ONLY if every ending — including the True ending — has at least one real `choice.goto` path from `start`. The other research track (content/topology) must ensure this; this track supplies the rule.

The same logic applies to the anaerobic 3-ending branch (lactic=Good/ethanolic=Normal/crisis=Bad, per SC#3 framing-d): those endings must each be structurally reachable via a `choice.goto` chain from the pyruvate branch point; the `host_o2_low` `cond` gates which branch is OFFERED at runtime, not whether it's structurally reachable.
