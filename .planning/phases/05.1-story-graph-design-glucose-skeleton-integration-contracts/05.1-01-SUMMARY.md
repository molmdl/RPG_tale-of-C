## Decisions Made

1. **Cond-string verbatim transcription + Phase 6 refinement flag.** Transcribed the plan's exact cond strings (`not flags.host_o2_low` / `flags.host_o2_low`) rather than auto-"fixing" to the working `flags.get('host_o2_low')` dict-method form. Rationale: the plan explicitly states cond is a "RUNTIME cond concern, NOT a structural one" and the BFS ignores cond — so the cond syntax has zero effect on this plan's structural validation (SC2). Auto-"fixing" would substitute my judgment for the plan author's on a point the plan explicitly deferred to the runtime phase. The interpreter's `_cond` (interpreter.py:124-133) exposes `flags` as a dict, so attribute access `flags.host_o2_low` raises AttributeError -> fail-safe False -> both pyr.branch choices hidden at runtime; the refinement to `flags.get('host_o2_low')` (per research Q2 example) is flagged for Phase 6 (controller phase) in the Next Phase Readiness section.

2. **Cross-file consistency with sibling plan 05.1-02.** Adopted the sibling plan's two conventions: (a) `text_teaching` included on ALL nodes (`""` for PENDING nodes without teaching text, `"TBD — ..."` for approved-claim nodes); (b) `stage:<stage>` node tag on EVERY node (stage:intro / stage:glycolysis / stage:pyruvate / stage:anaerobic). The plan explicitly specified stage tags only on gly.pfk and pyr.pdh, but matching the sibling plan's universal convention avoids an inconsistent merged skeleton at Plan 04 manifest time and aids the SC5 per-node classification (stage grouping).

3. **intro.select effects:{} explicit.** Per the plan's "Use placeholder effects: {}" instruction, the 3 character-select choices carry `effects: {}` explicitly. This documents (visibly in the JSON) that the controller (Phase 6) owns character selection — it reads the chosen index and calls engine.start(character="glucose", ...), NOT the choice effects (per research OQ7).

4. **edit.prompt as a cross-file reference.** gly.pfk and pyr.pdh both have an edit:offer choice with `goto: "edit.prompt"`, but the edit.prompt stub node is NOT defined in this plan — it is authored in Plan 03's bad_endings.json. This is an intentional cross-file reference (the sibling tca.json references edit.prompt too); it resolves when Plan 04's manifest merges all skeleton files. The dangling reference is expected at this plan's scope and is NOT a structural error.
