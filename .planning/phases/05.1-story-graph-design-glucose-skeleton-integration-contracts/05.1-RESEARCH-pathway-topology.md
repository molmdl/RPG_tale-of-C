## Summary

The glucose skeleton is a directed story graph that walks the C14 hero from the character-select screen through glycolysis → pyruvate branch point → (aerobic) PDH → TCA (with the spec-mandated RNG-weighted citrate-prochirality shuffle) → ETC → ATP synthase (the True ending), with branch points that divert the carbon to Good endings (fatty-acid synthesis, amino-acid synthesis, lactic fermentation — carbon retained pre-oxidation), Normal endings (CO2 released without the full electron-harvest arc — the aerobic "unremarkable exit" + the anaerobic ethanolic CO2), and Bad endings (the failure pool: lost-connection, released-from-host, cycle-trap→host-death, critical-residue-break, anaerobic energy-crisis). The graph is anchored on ONE approved first-batch RNG node (`tca.shuffle`, weights 0.5/0.5, claim TCA-RNG-WEIGHT-01) and ONE approved first-batch glycolysis control-point (`gly.pfk`, claim GLY-PFK-01, cast CAST-PFK-PDB-01 / PDB-4PFK) plus the citrate-synthase cast (CAST-CSC-PDB-01 / PDB-1CSC); every other node's science is PENDING and uses `PLACEHOLDER_PHASE7` claim_ids.

The 4 ending tiers are distributed asymmetrically per the user-confirmed (2026-08-15) decision (PROJECT.md row 107): **1 True + 3 Good + 2 Normal + 5 Bad = 11 endings.** The anaerobic branch (option (d), PROJECT.md row 97) contributes 3 of those endings — lactic (Good), ethanolic (Normal), crisis (Bad) — reached via a CHOICE at the pyruvate branch point gated by `flags.host_o2_low`. The True ending is AEROBIC ONLY (biochemically unreachable without O2 — verified 05-RESEARCH-anaerobic.md); but because the Phase 2 reachability checker is a pure BFS over `choice.goto` edges that does NOT evaluate `cond`, the True ending is structurally reachable via the aerobic `choice.goto` chain and the aerobic/anaerobic split is a RUNTIME `cond` concern the BFS does not model — so the checker goes GREEN on the skeleton (all 4 tiers structurally reachable) and the "True unreachable anaerobically" property is enforced at playtime by `cond`, not by the static checker.

**Primary recommendation:** Build the skeleton with `start = "intro.select"` (character-select) → `gly.start` (glucose entry), split across 7 JSON files (`intro.json`, `glycolysis.json`, `pyruvate_branch.json`, `tca.json`, `etc_atp.json`, `endings.json`, `bad_endings.json`) per ARCHITECTURE.md line 459's per-pathway-file rationale. Every reachability path uses `choice.goto` (NOT `on_enter_divert` — the BFS does not traverse `on_enter_divert`; this is the single most important structural constraint for the planner). Flag the ethanolic anaerobic ending + the Normal-ending framing + the cycle-trap visit-cap as the 3 branch points needing human review before Phase 7.

### True ending is AEROBIC ONLY — how the static BFS validates it
**The key constraint (from the objective):** the True ending is biochemically unreachable anaerobically (no O2 → no ETC → no ATP synthase → no soul-jump — verified 05-RESEARCH-anaerobic.md, settled chemistry). The Phase 2 reachability checker (`c14/story/validate.py:check_reachability`) is a pure BFS over `choice.goto` edges that does NOT evaluate `cond` or `weight` — it follows ALL `choice.goto` edges to existing nodes and reports which ending nodes are reachable. So:

- **The True ending `end.true` MUST be reachable via a `choice.goto` chain from `intro.select`** for the checker to go GREEN. The chain is: `intro.select → gly.start → … → pyr.branch → pyr.pdh → tca.entry → … → tca.shuffle → tca.co2_turn1/turn2 → etc.entry → etc.complex_i → etc.complex_ii_iii_iv → etc.atp_synthase → end.true`. The `pyr.branch` aerobic choice has `cond: "not flags.host_o2_low"` — the BFS IGNORES this cond, so it traverses the aerobic `goto: "pyr.pdh"` edge. ✓ True is structurally reachable.
- **The "True unreachable anaerobically" property is a RUNTIME `cond` concern, NOT a static-graph property.** At playtime, if `flags.host_o2_low == true`, the `pyr.branch` aerobic choice is hidden (`_cond` returns False), so the player can only take the anaerobic choice → `anaer.entry` → the 3 anaerobic endings. The True ending is unreachable IN THAT PLAYTHROUGH. The static checker does not model this — it validates STRUCTURAL reachability (no orphaned endings), not runtime conditional reachability.
- **This is the intended design.** The static checker guards against authoring errors (orphaned endings); the aerobic/anaerobic split is enforced by `cond` at playtime. SC2's "all four ending tiers reachable from the glucose start node" is satisfied STRUCTURALLY (all 4 tiers reachable via `choice.goto` chains). The "True unreachable anaerobically" is documented in the teaching layer (the anaerobic nodes' `text_teaching` explains "no ETC without O2 — no soul-jump here" — AN-G-04 / AN-ETC-02 CANDIDATE claims), not enforced by the static checker.
- **The deliberately-orphaned RED variant (SC2 second half):** remove the `choice.goto` edge to `end.true` (e.g. change `etc.atp_synthase`'s choice to `goto: "end.normal.co2"` instead of `end.true`) → `end.true` becomes unreachable → `check_reachability` reports `unreachable_endings = ["end.true"]` → `is_ok == False` → RED. The planner should author a separate RED-test fixture (not the production skeleton) with this edge removed.

## Q6. RNG / stochastic nodes (the spec-mandated TCA shuffle; are there others?)

**The ONE spec-mandated RNG-weighted stochastic story node:** `tca.shuffle`.

- **Backed by:** `TCA-RNG-WEIGHT-01` (the 0.5/0.5 value — APPROVED) + `TCA-RNG-CITRATE-PROCHIRALITY-01` (the citrate prochirality / aconitase discrimination mechanism grounding the shuffle — APPROVED). Source LIBRETEXTS-METAB-TCA.
- **Spec mandate:** spec.md line 13 "some RNG decided stuff for pathways that is know to have some probability shuffle, e.g. in the TCA cycle" — the TCA shuffle is the explicit example.
- **Mechanism in the engine:** the interpreter's `pick_choice` (`c14/story/interpreter.py:43-73`) sees two weighted choices with total=1.0 > 0, picks one deterministically via `rng.random() * 1.0` + cumulative sum. The `RngEngine` is seeded at `engine.start` (seedable for classroom reproducibility — PROJECT.md row 34, ARCHITECTURE.md Pattern 2).

**Are there OTHER RNG nodes in the glucose skeleton? No.** The spec mandates the TCA shuffle; the skeleton should NOT invent additional RNG nodes. Specifically:
- **The bad-ending pool uniform pick (EditRouter fallback) is NOT a story node.** When an unknown edit routes to the bad-ending pool, the EditRouter picks one bad-ending node from `data/edits.json`'s `bad_ending_pool` list (Phase 4 fixture: `["bad.lost_connection", "bad.released_from_host"]`). Do NOT represent it as an `rng-shuffle` node in the story graph — the EditRouter owns it (the sibling researcher's edit-node-contract concern).
- **The cycle-trap → host-death bad ending is NOT an RNG node.** It's a `cond`-gated choice on `tca.shuffle` visit-count: `cond: "visits.get('tca.shuffle', 0) > N"` → `bad.cycle_trap_host_death`. This is a visit-count mechanism (Pitfall 8 cycle-cap, PITFALLS.md line 335), NOT a stochastic draw. The visit count accumulates from re-entering `tca.shuffle` (the TCA cycle literally turns again); after N visits, the cycle-trap choice becomes eligible and the player is forced toward the bad ending. The "RNG stays in a cycle long enough" (spec.md line 18) is modeled by the RNG-weighted shuffle re-entering the same node N times (the 0.5/0.5 keeps drawing the "next turn" loop), NOT by a separate RNG draw for the trap.

The real `intro.select` (character-select) is NOT RNG-weighted (the player picks the character). The skeleton should NOT carry the toy RNG pattern into `intro.select`.

**Summary:** exactly ONE `rng-shuffle` node (`tca.shuffle`, weights 0.5/0.5, APPROVED claims). All other stochastic behavior (bad-ending pool pick, cycle-trap) is mechanism, not story nodes.
