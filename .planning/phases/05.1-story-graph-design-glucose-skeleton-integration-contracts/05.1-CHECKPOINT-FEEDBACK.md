## New Requirement 1: More Bad-Ending Placeholders (CG-Collection Feel)

**Source:** User feedback during 05.1-06 checkpoint review (2026-08-22).

**Requirement:** Expand the bad-ending pool so that failure feels more like "CG collection" — the SAME wrong edit operation can lead to DIFFERENT bad endings (variety, not punishment). Use randomness (the RngEngine) so a repeated mistake doesn't always produce the identical ending.

**Current state:** The skeleton has 5 bad endings (bad.lost_connection, bad.released_from_host, bad.cycle_trap_host_death, bad.critical_residue_break, + edit.prompt stub which routes to 3 of them). The EditRouter's unknown-edit fallback currently picks from the global bad-ending pool via RngEngine (Phase 4 04-02: "per-enzyme bad-ending pool uses OVERRIDE semantics; RngEngine-weighted, reproducible"). So the routing mechanism EXISTS — this requirement is about EXPANDING the bad-ending POOL (more ending nodes) + possibly per-enzyme pools for variety.

**Design questions for the planner:**
- How many additional bad-ending nodes? (suggest ~8-12 total, up from 5, so the weighted pool has real variety)
- Are they generic (shared pool) or per-enzyme (each enzyme's wrong edits lead to enzyme-thematically-relevant bad endings)? Per-enzyme is more content load but more "CG collection" feel.
- The randomness is ALREADY wired (RngEngine-weighted bad-ending pool in EditRouter). The skeleton just needs MORE bad-ending nodes to pick FROM. The variety comes from the pool size, not new routing logic.
- Bad endings should carry teaching-layer text (not punitive — per Phase 10 SC3 "bad-endings carry explanatory teaching-layer text"). The text is Phase 7 content; the skeleton carries the NODES + their is_ending="bad" + PLACEHOLDER claim_ids.
- Naming convention: bad.<descriptive_name> (e.g. bad.enzyme_collapse, bad.wrong_substrate_trapped, bad.broken_active_site, bad.lost_in_cytosol, bad.proton_leak, etc. — be creative but scientifically grounded in what could go wrong from a bad edit).
- Each new bad ending is reachable via the EditRouter's weighted bad-ending pool (edit.prompt → EditRouter.route → RngEngine picks one). The reachability checker must confirm all new bad endings are reachable from the edit.prompt node (or they're orphaned).

**Must NOT change:** The 4 ending tiers (True/Good/Normal/Bad) stay. The ending distribution (1T+3G+2N+5B currently) will GROW on the Bad side (the user wants more Bad endings). The reachability checker + the 2 replan invariants (0 single-Continue, 14 edit-allowed) must still pass GREEN after adding the new bad-ending nodes.
